# Мета-скилл: какой скилл выбрать (русский обзор)

Перевод и краткое изложение `using-agent-skills/SKILL.md`. Агент читает оригинал на английском; этот файл — для вас.

## Блок-схема выбора

```
Задача
  │
  ├─ Не знаю, что хочу? ─────────────────→ interview-me
  ├─ Сырая идея, нужны варианты? ────────→ idea-refine
  ├─ Новая фича / изменение? ────────────→ spec-driven-development
  ├─ Есть спека, нужен план? ────────────→ planning-and-task-breakdown
  ├─ Пишу код? ──────────────────────────→ incremental-implementation
  │   ├─ UI? ────────────────────────────→ frontend-ui-engineering
  │   ├─ API? ───────────────────────────→ api-and-interface-design
  │   ├─ Нужен контекст? ────────────────→ context-engineering
  │   ├─ По официальной доке? ───────────→ source-driven-development
  │   └─ Высокие ставки? ────────────────→ doubt-driven-development
  ├─ Тесты? ─────────────────────────────→ test-driven-development
  │   └─ В браузере? ────────────────────→ browser-testing-with-devtools
  ├─ Что-то сломалось? ──────────────────→ debugging-and-error-recovery
  ├─ Ревью кода? ────────────────────────→ code-review-and-quality
  │   ├─ Слишком сложно? ────────────────→ code-simplification
  │   ├─ Безопасность? ──────────────────→ security-and-hardening
  │   └─ Производительность? ────────────→ performance-optimization
  ├─ Git / ветки? ───────────────────────→ git-workflow-and-versioning
  ├─ CI/CD? ─────────────────────────────→ ci-cd-and-automation
  ├─ Устаревание / миграция? ────────────→ deprecation-and-migration
  ├─ Документация / ADR? ────────────────→ documentation-and-adrs
  ├─ Логи / метрики? ────────────────────→ observability-and-instrumentation
  └─ Деплой / релиз? ────────────────────→ shipping-and-launch

  ★ В репозитории «Шишов» — сначала project-shishov (структура, стек, команды)
```

## Правила работы агента (кратко)

1. **Озвучивать допущения** — перед нетривиальной работой перечислить, что предполагается, и дать поправить.
2. **Не гадать при неясности** — остановиться, назвать противоречие, спросить.
3. **Спорить при необходимости** — не соглашаться с плохим решением молча.
4. **Простота** — меньше кода и абстракций, если хватает простого.
5. **Узкий scope** — не рефакторить «заодно» чужой код.
6. **Верификация** — задача не готова без тестов/сборки/доказательства.

## Типичная цепочка для новой фичи

1. interview-me → 2. idea-refine → 3. spec-driven-development → 4. planning-and-task-breakdown → 5. incremental-implementation → 6. test-driven-development → 7. code-review-and-quality → 8. shipping-and-launch

Для бага часто хватает: debugging-and-error-recovery → test-driven-development → code-review-and-quality.
