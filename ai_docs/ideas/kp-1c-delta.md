# Дельта КП в 1С

**Статус**: IDEATE ✅ · SPECIFY ✅ · PLAN
**Дата**: 2026-10-01
**Направление**: кнопка «Отправить исправление» пишет весь заказ файлом `delta_`, первая отправка — `new_`; номер и два УИД из ответа 1С лежат на КП
**Spec:** [../specs/kp-1c-delta.md](../specs/kp-1c-delta.md)
**Plan:** [../develop/plans/2026-10-01-kp-1c-delta.md](../develop/plans/2026-10-01-kp-1c-delta.md)

## Problem Statement

Как менеджеру в карточке уже принятого 1С коммерческого предложения одной кнопкой отправить весь новый состав так, чтобы 1С обновила тот же заказ клиента.

## Recommended Direction

Исходящий документ — JSON, который уже ушёл по КП 31 и который с 1С утвердили: «КоммерческоеПредложение», шапка и строки с суммами, НДС и видом цены. Новый файл называется `new_{kp_id}_{время}.json`, исправление — `delta_{kp_id}_{время}.json`. Оба имени попадают в маски `new_%.json` и `delta_%.json`.

Дельта — весь заказ после правки, не список изменений. В начале файла три поля из ответа 1С: `УИД_ЗК`, `Номер_ЗК`, `УИД_КП`. Их нет в `new_`. `Номер_КП` и `Описание` в исходящий файл не входят.

`Номер_ЗК` хранится в существующей колонке `order_number_1c`. Рядом две новые колонки под УИД заказа и УИД КП. Шапка, спецификация и «В производство» читают номер из `order_number_1c`. Кнопка «Отправить исправление» пишет дельту, когда все три поля заполнены и состав отличается от последнего ушедшего снимка. Для КП 31 три значения записываются один раз из уже присланного ответа, пока колонки пустые. Другой УИД поверх уже записанного не пишется. Разбор папки ответов в этот шаг не входит.

## Key Assumptions to Validate

- [x] Кнопку нажимает менеджер в карточке. Отдельной ручной выгрузки для каждой правки нет.
- [x] Тело файла — утверждённый `kp_offer` («КоммерческоеПредложение»), не текущий «Счёт на оплату».
- [x] В `delta_` лежит весь исправленный заказ. 1С загружает его вместо текущего состава.
- [x] Идентификаторы хранятся тремя полями на КП. Целый JSON ответа в базе не хранится.
- [x] По КП 31 состав уже сохранён: 24 строки, «Плиты ПБ 75-12-8п» 10 шт по 29 316 ₽, итог 1 859 443,20 ₽, НДС 335 309,43 ₽. GUID плиты в прайсе один: `cf7fc182-ee4c-11e9-8f4e-04d9f5387845`.
- [x] Поле `Статус` в JSON остаётся «в архиве», как в файле, который 1С уже принял.
- [ ] Следующий ответ 1С сам заполнит те же три колонки. Маска и каталог входящего файла ещё не названы.

## MVP Scope

Кнопка «Отправить исправление» пишет `delta_{kp_id}_{время}.json` телом утверждённого КП плюс три идентификатора. Первая отправка пишет `new_{kp_id}_{время}.json` тем же телом, без трёх идентификаторов. На КП 31 три значения из ответа записываются один раз, шапка показывает 469.

Уже отправленный `kp_offer_31_20260929.json` повторно не кладётся.

## Not Doing (and Why)

- Разбор входящего `otvet` и сторож папки — маска и каталог ответа ещё не названы. Колонки стоят так, чтобы разбор потом только заполнял их.
- Хранение всего JSON ответа в базе — номер начал бы жить вторым источником рядом с `order_number_1c`.
- Поле ввода номера и показ JSON менеджеру — менеджер не администрирует обмен.
- HTTP-вызов 1С — обмен по-прежнему файл в каталоге.
- Дельта из одной изменённой строки — в файл уходит весь состав.
- Имена `invoice_create` / `invoice_update` и документ «Счёт на оплату» — они не попадают в согласованные маски и не совпадают с утверждённым телом.
