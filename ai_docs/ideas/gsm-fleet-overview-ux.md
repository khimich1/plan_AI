# ГСМ: обзор флота и журналы (редизайн UX)

**Дата:** 2026-08-24. **Статус:** direction confirmed, к спеке.
**Источник:** idea-refine сессия 2026-08-24 (рамка: бухгалтер закрывает месяц; скоуп MVP: просмотр + массовые операции).

## Problem Statement

Как дать бухгалтеру за один взгляд видеть состояние ГСМ по всему автопарку —
транзакции, путевые листы, пробег — и закрывать месяц как журнал,
а не как слепую форму «машина + даты → Сгенерировать»?

## Recommended Direction

Главный экран модуля (/gsm, вкладка «Обзор») — **сводная таблица машин за
период с раскрывающимися строками**:

- Строка машины: статус («требуется генерация» / «N красных дней» /
  «готово к экспорту»), Σ литров по транзакциям, Σ км и дней по ПЛ,
  красные дни, итоговый остаток бака, чекбокс.
- Раскрытие строки — журнал ПЛ этой машины прямо под ней
  (дата, маршрут, км, бак нач/выд/кон, одометр, статус, warnings).
  Можно раскрыть все 4 машины — флот маленький, экран вмещает.
- Массовые действия из чекбоксов: «Сгенерировать выбранные»,
  «Экспорт zip выбранных» (бэкенд уже умеет `vehicle_ids: list`).

Статусы вычисляются дешёвым SQL без запуска солвера
(max дата транзакций vs max дата ПЛ, count `manual_intervention`,
статусы confirmed/exported). Генерация становится статус-driven:
кнопка живёт в строке машины, которой она нужна, — слепая форма
исчезает как точка входа.

Журналы — вкладки: «Транзакции» (сейчас заглушка → полноценный журнал
с фильтрами по машине/периоду/типу и итогами Σ литров / Σ суммы),
«Справочники» — как есть. Детальный вид машины (лента дней +
drawer правки) сохраняется как второй уровень — там лента на своём месте.

Красная нить: обзор отвечает «что делать», журналы — «что есть».

## Key Assumptions to Validate

- [ ] Статусы из данных не «врут»: если бухгалтер мысленно закрыл машину
  без confirm, система не должна вечно показывать «требуется».
  Тест: приёмка на реальном закрытии месяца, источник истины —
  confirmed/exported.
- [ ] Массовая генерация N машин подряд устойчива: ошибка одной машины
  (нет маршрутов/водителя) не валит остальные, отчёт по каждой.
  Тест: генерация 4 машин разом, одна заведомо сломанная.
- [ ] Расхождение «Σ литров по транзакциям vs Σ выданного по ПЛ» —
  достаточная контрольная цифра для бухгалтера.
  Тест: показать сводку без объяснений, спросить «что не так на экране».

## MVP Scope

**Входит:**
- Вкладка «Обзор» (главная по умолчанию): сводная таблица + раскрытие строк
- Backend: новый `GET /gsm/transactions` (фильтры vehicle_id/from/to/service_type)
- Backend: `vehicle_id` в `GET /gsm/waybills` становится опциональным (все машины)
- Backend: агрегирующий запрос сводки (1 SQL, солвер не трогаем)
- Массовые действия: generate / export по выбранным машинам
- Километраж: колонка км в журнале ПЛ + Σ км в сводке и подвалах журналов

**Не входит:**
- Inline-редактирование в таблицах (правка — через существующий drawer)
- Изменения солвера, схемы БД, экспорта бланка

## Not Doing (and Why)

- Календарная сетка «машины × дни» — дублирует сводку функционально,
  дорогой кастомный grid, не показывает цифры (км/литры)
- Auto-preview (dry-run солвера до нажатия) — удваивает ментальную модель
  («прогноз» vs «правда»), ноль новой информации: солвер детерминирован
- Лента дней как главный экран — горизонтальный скролл не масштабируется
  на флот; остаётся визуалом цепочки бака в детальном виде машины
- Inline-правки в таблицах — два пути редактирования = рассинхрон;
  drawer уже решает правку + downstream-пересчёт

## Open Questions

- Статус «готово» = все ПЛ confirmed или все exported?
  (exported закрывает цепочку бака — вероятно, он)
- Показывать ли расхождение литров (транзакции vs ПЛ) отдельным бейджем
  в строке машины, или достаточно двух колонок рядом?
- Период по умолчанию: текущий месяц или min/max дат транзакций?
