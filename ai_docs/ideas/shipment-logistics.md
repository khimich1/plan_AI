# Логистика и отгрузка (замена Excel-реестра)

> Ideation session: 2026-07-31  
> Контекст: модуль B «Выдача и отгрузка с СГП» из [`2026-07-28-development-roadmap-cifra-context.md`](../develop/plans/2026-07-28-development-roadmap-cifra-context.md).  
> Источники фактов: «Реестр отгрузок от 12082021.xlsx» (17 279 строк, 2021–2026, живой), лист «История» (инструкция), скриншоты 1С:КА 2.5 (КП ЯР-0000124, дерево заказов), карточка предприятия перевозчика (.docx), договор-заявка №11/07/26 (.doc).  
> Связанные модули: СГП MVP (`completed_plates`, `kp_plates`, `plate_status_log`), архив КП, `KpStatus.DONE`, ТЗ 1С-интеграции (`docs/specs/1c-integration-tz.md`).

## Problem Statement

**Как перенести управление отгрузкой из общего Excel-реестра в веб «Шишов», чтобы рейс собирался из реальных позиций СГП (а не вбивался текстом), статус был явным вместо цвета ячеек, факт выезда списывал склад и готовил событие для 1С, а договор-заявка на фрахт генерировался из данных системы?**

## Recommended Direction

### Выбор: раздел «Логистика» + propose→confirm из СГП + генерация договора-заявки

Новый раздел веб-приложения (не вкладка производства — у логистики свой контур ролей). Реестр рейсов (таблица с фильтрами по дате/заказу/перевозчику), карточка рейса, справочник перевозчиков.

Ключевой паттерн — **propose→confirm**, уже обкатанный в wizard СГП («Закрыть со склада»): логист создаёт рейс на дату и выбирает заказ → система предлагает состав партии из плит этого КП, лежащих на СГП (с весом, с учётом лимита ТС) → логист утверждает или корректирует (убрать/добавить, свободная строка для свай). Сейчас логист делает это вручную, глядя на резерв внутри счёта в 1С (ответ предприятия 1.2).

### Рейс — центральная сущность

Одна строка Excel = один рейс (ТС), а не один заказ. Медиана — 6–8 рейсов на заказ, максимум — 332. Рейс — контейнер под заказом `ЯР-XXXXXXX`:

- позиции плит — **ссылки на `completed_plates`** (СГП), не текст;
- свободные строки — марка + qty (+ вес) для свай/прочего: заказ ЯР-0001311 документально содержит и сваи, и ПБ;
- несколько КП/заказов в одном ТС допустимо (641 смешанный рейс в истории).

`№ заказа` в реестре = числовая часть `Номер счёта` (`ЯР-0001467` ↔ `1467`) — доказано скриншотом листа. Колонка «Номер счёта» — дубль (заполнена 31–43% против 93–98% у № заказа), отдельным полем не нужна. После 1С-интеграции ЯР-номер подтянется из КП автоматически (ТЗ обмена уже предусматривает связку `УИДКП/НомерКП`).

### Статусная модель — по факту, не по инструкции

Инструкция (лист «История»: 4 статуса × 5 ролей, цвет участка) **мертва**. Живая практика по заливке последних 600 строк:

| Цвет | Доля | Семантика |
|------|------|-----------|
| Красный | 96% | обработано / день прошёл |
| Голубой | только сегодня | в работе прямо сейчас |
| Жёлтый | ~3% | внимание / особое событие («Работа крана!», «Манипулятор», «Доски на завод!», «БЕЗ ЦЕН!») |

В системе: **два статуса** `в работе → обработано` + **флаг «внимание»** (с комментарием). Переход в «обработано» = факт выезда → атомарное списание СГП (audit `sgp_ship` в стиле `sgp_send`), прогресс КП «отгружено X/M», `KpStatus.DONE` только при отгрузке полного заказного qty. Событие `shipment_completed` проектируем сразу под папку обмена 1С.

КПП в реестре не работает: «№ пропуска», «Время въезда», «Время выезда» заполнены в 0–3 строках из 17 279 — пропуска не фиксируем, факт выезда ставит логист.

### Договор-заявка на фрахт (MVP-2)

Сейчас: перевозчик присылает **карточку предприятия** (реквизиты, ИНН, ОГРНИП, банк, **налоговый режим** — УСНО 6% → «без НДС» в реестре, паспорт водителя, машина+прицеп) → логист вручную составляет **договор-заявку** в Word.

Договор — шаблон с константами (заказчик, адрес погрузки, штрафы, возврат документов) и переменными из рейса (перевозчик, водитель, а/м, маршрут, груз/вес, адрес+контакт выгрузки, даты, стоимость). «Факсимильная копия действительна» — DOCX→email легально.

В системе: генерация DOCX из шаблона, номер **`N/MM/YY` с ежемесячным счётчиком** (№11/07/26 = 11-й договор июля; колонка «№ Заявки на фрахт ТС» в реестре — тот же номер). Самовывоз договора не требует. Реквизиты заказчика — конфиг, не код.

### Справочник перевозчиков

Импорт из листов «Перевозчики»/«Транспортные Компании» (с дедупликацией) + обогащение карточкой предприятия: реквизиты, банк, налоговый режим, направления. Под-сущности: `Carrier 1→n Driver` (ФИО, паспорт — **ПДн, доступ только у роли логистики**), `Carrier 1→n Vehicle` (марка, гос.номер, прицеп, класс 20т/30т+).

### Поля рейса — по эмпирии заполнения (2025–26, 5 231 строка)

**Ядро (>90%):** дата, № заказа ЯР, тип Д/С, УПД (готовится заранее, до приезда машины), перевозчик/доверенность №, водитель.  
**Важно (40–60%):** позиции партии, вес (автоподсчёт из справочника + ручной для свай, «ориентировочный»), ТС (назначается позже), № заявки на фрахт, стоимость план.  
**Опционально:** слот времени («утро/вечер» — умирает, 9% в свежих строках).

### Жизненный цикл рейса

```
логист: создать рейс (дата, заказ ЯР, тип Д/С)
   → propose: состав из СГП + свободные строки, вес, лимит ТС
   → confirm: партия утверждена → печатная форма для СГП
   → [наёмный] договор-заявка N/MM/YY (MVP-2), ТС+водитель
   → УПД готов (номер известен заранее — поле)
   → выезд → «обработано»: списание СГП, X/M, событие для 1С
```

## Key Assumptions to Validate

- [ ] **Логист примет веб вместо Excel** — файл ведётся с 2021 года, buy-in критичен. Тест: прототип реестра на его реальных данных до разработки.
- [ ] **К пилоту СГП актуален** — сейчас нет (модуль в обкатке, ответ предприятия). Gate пилота: сверка «в системе = на складе». Инвентаризация — шаг 0.
- [ ] **ЯР-номер известен к моменту отгрузки** (счёт формируется из КП в 1С и возвращается). Валидация: обязателен на переходе в «обработано», не при создании. Риск низкий, но проверить на пилоте.
- [ ] **Автопредложение состава покрывает типовой рейс** — если логисту приходится править >50% рейсов, предложение бесполезно. Метрика на пилоте: доля рейсов без ручной правки.
- [ ] **ПДн водителей** (паспорта) допустимо хранить в системе с ограничением доступа — согласовать с владельцем.

## MVP Scope

**In (MVP-1 — реестр и СГП):**

- Раздел «Логистика»: реестр рейсов (фильтры: дата, заказ, перевозчик, тип, «без УПД», «внимание»), карточка рейса
- Рейс: ядро-поля + важные (см. выше); статусы `в работе → обработано` + флаг «внимание»
- Propose→confirm состава из СГП; свободные строки (марка, qty, вес) для свай/прочего
- Мульти-заказный рейс (несколько ЯР в одном ТС)
- Автовес позиций + предупреждение перегруза класса ТС (20т/30т+)
- Списание СГП при выезде (атомарно, audit `sgp_ship`), прогресс «отгружено X/M» в архиве, `KpStatus.DONE` при полном qty
- Справочник перевозчиков: импорт из Excel, базовые поля
- Печатная форма «лист отгрузки» для СГП (позиции, порядок, заметки укладки)
- Событие `shipment_completed` (JSON по контракту папки обмена) — заложить в модель, отключено до интеграции

**In (MVP-2 — договоры, сразу следом):**

- Справочник полный: реквизиты, банк, налоговый режим, водители, машины (форма «карточка предприятия»)
- Права на ПДн водителей
- Генерация договора-заявки DOCX из шаблона (константы заказчика — конфиг)
- Номер `N/MM/YY` с месячным счётчиком; связь с рейсом («№ Заявки на фрахт ТС»)

**Out (Not Doing):**

- Пропуска, время въезда/выезда, роль КПП — 0% заполнения за 5 лет
- 4-статусный конвейер из инструкции, «документы закрыты», «статус оплаты» — мертво в данных
- НДС 5%/7%, факт-стоимость, маржа — <25% заполнения, фаза 2 (деньги фрахта — в 1С)
- Миграция 17k строк истории — Excel остаётся read-only архивом
- Склад свай/прочей номенклатуры — свободные строки; полноценный склад — отдельный эпик
- Услуги техники и входящая логистика (жёлтые строки: кран, манипулятор, доски) — тип события зарезервировать в модели, не реализовывать
- Умный подбор состава рейса (оптимизатор укладки, довесок) — фаза 2
- ЭДО/ЭТрН, ГИС ЭПД — через 1С (направление H роадмапа)
- GPS, приложение водителя — нет своего парка
- Расчёт штрафов/простоя, учёт оплат фрахта

## Not Doing (and Why) — ключевые отказы

- **Не вкладка производства, а свой раздел** — у логистики свои роли и фильтры; повторять ошибку Excel «всё в одном листе» нельзя.
- **Не 4 статуса** — инструкция мертва, живут два состояния + флаг. Лишние клики убьют adoption.
- **Не мигрируем историю** — закрытые рейсы не дают ценности в системе; Excel доступен для справок.
- **Не делаем «Номер счёта» полем** — дубль № заказа (доказано скриншотом).
- **Не требуем ЯР при создании рейса** — планирование идёт до документов (УПД часто готовится заранее, но не всегда); обязательность — на закрытии.
- **Не считаем учётный вес** — он в 1С для УПД; наш вес — ориентир для лимита ТС.

## Этапы реализации (предложение)

1. **Spec** `ai_docs/specs/shipment-logistics.md` по образцу sgp-warehouse (user stories, acceptance, API-черновик, границы)
2. **MVP-1:** модель рейса + реестр UI → propose→confirm из СГП → списание при выезде + прогресс КП → печатная форма СГП → справочник (импорт)
3. **Пилот MVP-1:** сверка СГП (шаг 0) → cut-over на сегменте → метрики (доля рейсов без правки, расхождения склада)
4. **MVP-2:** карточка перевозчика (ПДн-права) → генерация договора-заявки + счётчик N/MM/YY
5. **После:** событие в 1С (с интеграцией G), факт-стоимость/НДС (фаза 2), умный подбор (фаза 2)
