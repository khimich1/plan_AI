# Идея: GSM — ориентация круга с базы + домашний `route_id`

Дата: 2026-08-27. Статус: **direction confirmed**. Спека:
[`../specs/gsm-home-oriented-round-trip.md`](../specs/gsm-home-oriented-round-trip.md).

Предшественники: [`gsm-geo-lookahead-generator`](gsm-geo-lookahead-generator.md)
(день = 2 плеча, ночёвки — фаза 2),
[`gsm-fleet-pool-corridor`](gsm-fleet-pool-corridor.md)
(пул = маршруты с Кузнецкой 18Б).

Триггер: Tugella 952, 13.07.2026 — заправка в Костроме, сгенерированный круг
стартует из Владимира (`route_id=59`, «Маршрут для баланса»). Зеркало
дом → Владимир есть (`route_id=64`). Солвер копирует `addr_a` справочника.

## Problem Statement

How might we генерировать день путевого листа так, чтобы он всегда читался
как **Кузнецкая 18Б → объект → Кузнецкая 18Б**, если один конец маршрута —
база — без ложной ночёвки на объекте и без телепорта к следующему утру,
не меняя сходимость бака?

Сейчас солвер выбирает **км**, а плечи копирует как `addr_a → addr_b → addr_a`.
Импорт положил «обратные» ноги первыми (меньший `id`). Rank при равных км
берёт меньший `route_id` — объект-первым. `_is_home_base` фильтрует пул,
но не ориентирует день.

Пользователь: бухгалтер (`accountant`) на закрытии месяца `/gsm`.

## Recommended Direction

**Ориентировать круг при записи + подставить свой домашний `route_id`,
если есть зеркало.**

1. Хелпер (например `_home_oriented_legs`): ровно один конец
   `_is_home_base` → первая нога с Кузнецкой, вторая обратно. Оба конца
   база или ни одного (legacy без Кузнецкой) — порядок как в библиотеке.
2. Зеркало: та же `vehicle_id`, тот же `km`, концы переставлены,
   сравнение через `_norm_addr`. Нашли и маршрут свой → в ноги этот
   `route_id` (59→64). Нет зеркала → ноги всё равно перевёрнуты, id как
   выбрал солвер. Чужой пул: `route_id` по-прежнему `None`.
3. Тот же хелпер — когда бухгалтер в drawer выбирает строку справочника.
   Иначе повторный выбор 59 снова поставит Владимир первым.

Бак, lookahead, `balance_route` / `borrowed_route` не трогаем.
Точку «где вчера ночевали» не вводим: инвариант этого среза — всегда
круг с базы. Ночёвки остаются фазой 2.

## Key Assumptions to Validate

- [ ] `_norm_addr` склеивает пары июля 952 (59↔64; Вологда 330 и зеркало;
      Комсомольская 349 и зеркало). Проверка: SELECT по `gsm_route`
      машины 4, `km ∈ {4, 225, 280}`.
- [ ] Юнит: библиотека только «объект→дом», без зеркала → старт с дома,
      `route_id` исходный.
- [ ] Юнит: есть зеркало 59/64 → ноги дом→Владимир→дом, `route_id=64`.
- [ ] Регрессия `tests/test_gsm_generator.py`: км, бак, warnings те же;
      меняется только порядок ног / id.
- [ ] Drawer: выбор 59 даёт на превью дом→объект, не Владимир первым.

## MVP Scope

- `core/gsm/generator.py`: хелпер ориентации + поиск зеркала;
  `_round_trip_legs` / `_to_route_ref` отдают уже ориентированный день.
- Применение библиотечного маршрута в сервисе/drawer тем же хелпером
  (один код, не только `generate`).
- Юниты на ориентацию и зеркало; vitest на подпись маршрута в ленте,
  если сводка берёт `from` первой ноги.
- Live `plita.db` этим срезом не пишем. Уже `exported` июль останется,
  пока бухгалтер не перегенерирует.

## Not Doing (and Why)

- **Состояние «конец вчера = старт сегодня»** — ночёвки фаза 2; здесь
  инвариант «всегда круг с базы».
- **Миграция `gsm_route` (канонический `addr_a` = база)** — данные ради
  бага в emit; пары, frequency, typical разъедутся.
- **Только rank «предпочесть домашний id»** — не чинит дни, где в пуле
  только объект-первым.
- **Пересборка live июля в том же изменении** — exported/confirmed
  conflict; сначала солвер + тесты.
- **Ночёвки, соло-плечо** — отдельная модель бланка.
- **Склейка зеркал по `_city_key` + km** — разные дворы одного города
  (два адреса во Владимире) могут схлопнуться в чужой `route_id`.
  Нет пары по `_norm_addr` → переворот без смены id.
