# Сопоставление заводской марки сваи со справочником загрузки

> Ideation: 2026-09-14  
> Боль: на шаге итогов КП оранжевый блок «нет нормы загрузки» для `С110.35-12`, хотя в `pile_catalog` есть `С110.35` (6 шт./20 т)  
> Смежные: [`pile-bridge-trip-calculation.md`](pile-bridge-trip-calculation.md) (D4 мостовые уже по геометрии; D8/D13 ручной N только если `pcs_per_20t` пустой; D2 отгрузки не трогаем)  
> Spec: [`../specs/kp-pile-geometry-lookup.md`](../specs/kp-pile-geometry-lookup.md)

## Problem Statement

**Как менеджеру КП получить число рейсов по заводским маркам с нагрузкой, не спрашивая машины там, где завод уже дал шт. на 20 т для той же длины и сечения?**

Прайс и строка КП хранят `С110.35-12`. Логистический справочник — канон без нагрузки: `С110.35`. Lookup сначала требует точное совпадение, геометрический fallback ломается на суффиксе `-12` (`parse_pile_mark` читает сечение как `35-12`). Система врёт «нет нормы».

## Recommended Direction

Тихий матч **при чтении**, только КП и архив. Каталог не меняем: нагрузка на вес и шт. в машине не влияет.

Расширить уже существующий `resolve_catalog_for_mark`: после неудачного exact match отрезать заводскую нагрузку (`-12`, `-13и`) и снова искать по канону / геометрии — тем же путём, что мостовые `C11-35T6` → `С110.35`. Успех для менеджера: блока нет, рейсы считаются. UI расшифровку «взяли С110.35, 6 шт.» не показываем.

`С160.*` после матча по-прежнему без `pcs_per_20t` (в Excel «-»: 16 м не норма для обычного борта). Вопрос «сколько машин» остаётся — это длина, не баг парсера.

Отгрузки в этот срез не входят. Счастливый путь логиста — datalist `С60.30`; копипаст заводской марки из КП — отдельная дыра (фронт + поиск), не хвост к рейсам КП.

## Key Assumptions to Validate

- [ ] Нагрузка (`-12` / `-13и`) никогда не меняет `weight_kg` и `pcs_per_20t` в заводском листе «Вес и объем» — проверить на текущем xlsx: одна геометрия = одна строка.
- [ ] Все живые марки КП свай — `Сddd.dd-N` или `-Nи`; нет дефиса с другим смыслом, который отрежем по ошибке. Прогнать `kp_piles.mark` / типичные тексты мастера.
- [ ] После отрезания суффикса мостовые `C14-40T4` и канон `С137,5.40` не регрессируют (уже зелёные тесты).
- [ ] Для `С160.35-12` менеджер согласен видеть вопрос про машины — не «починить» через `ceil(кг/19800)`.

## MVP Scope

**In**

- `parse_pile_mark` / `resolve_catalog_for_mark`: понимать `С110.35-12` и `С120.35-13и` как геометрию `11.0 м × 350 мм` / канон `С110.35`.
- Расчёт рейсов КП + архив: тихий успех, если `pcs_per_20t ≥ 1`.
- Тесты: `С120.35-12` → каталог `С120.35` (5 шт.); `С160.35-12` → pending, пока нет override; регресс тендера 42 рейса и C18.

**Out** — см. Not Doing.

Минимум, который проверяет ставку: один КП с `С110.35-12` без оранжевого блока и с ненулевой доставкой свай после тарифа рейса.

## Not Doing (and Why)

- **Набивать `pile_catalog` полными марками из прайса** — дубли `-12`/`-13и`, вечный sync, каталог перестаёт быть таблицей геометрии.
- **Канон `logistics_mark` при парсинге строки / identity-модуль** — для тишины на итогах хватает lookup; старые черновики всё равно требуют read-time fallback.
- **Рейсы только по весу, выкинуть `pcs_per_20t`** — выбрасывает заводскую загрузку и ломает уже принятую формулу 42 рейсов.
- **Отгрузки (`pile_weight_for_mark` + datalist)** — другой UX: автовес от точного `С110.35`. Копипаст из КП чинится фронтом и поиском, не этим срезом. D2 spec рейсов оставляем в силе.
- **Показывать расшифровку нормы в UI** — выбран тихий успех; D16 и так запрещает «39 полных + 3 остатка».

## Open Questions

- Нужен ли отдельный хелпер «отрезать нагрузку» рядом с `_PILE_MARK_RE` в `pile_line_parser` (там суффикс уже часть марки), или достаточно починить только `pile_catalog.parse_pile_mark`?
  - **Решение в spec:** только `core/pile_catalog.py`. Прайс и парсер строки КП должны сохранять `-12`.
