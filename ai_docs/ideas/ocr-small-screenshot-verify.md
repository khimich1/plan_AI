# OCR мелких скриншотов: сначала Verify, потом 2×

> **Спека (этап B):** [`ai_docs/specs/ocr-small-screenshot-verify.md`](../specs/ocr-small-screenshot-verify.md)  
> **Следующее направление (2+4, после регресса):** [`ocr-verify-apply-and-upscale.md`](./ocr-verify-apply-and-upscale.md)

## Problem Statement

How might we вытаскивать из типичного скриншота Excel / PDF / переписки верный список марок и количеств — так, чтобы менеджер реже правил путаницу в марках и пропавшие строки, не выдавая интерполяцию пикселей за «новое разрешение»?

## Recommended Direction

Сначала **направление B**, затем **A** только если B не закрывает ошибку.

Типичный плохой вход — не размытое фото и не «низкий DPI». Это скриншот таблицы. Vision OCR (GigaChat / GPT-4o) получает файл как есть: `load_image_payload` → Extract → parser gate → Verify в режиме `auto`. Verify сегодня срабатывает на «грязный» extract (низкая confidence, строка не парсится, много строк, файл **больше** ~800 КБ). Мелкий чистый скрин с 5–8 строками и высокой уверенностью **уходит без второго прохода**. Модель спокойно путает марку (`66` / `66,2`, `6п` / `8п`) или теряет строку.

**Этап 1 (B):** не трогать пиксели. В `verify_policy` добавить порог «мелкий кадр» (короткая сторона ниже N px, либо эквивалент) и reason вроде `auto_small_image`. Все шесть пайплайнов в `core/ocr/pipeline.py` уже смотрят на политику — меняется одно место решения, не UI.

**Этап 2 (A), только если на корпусе плохих скринов B не хватает:** условный 2× Lanczos + лёгкий контраст *только* когда кадр мелкий. Без автокропа, без смены DPI, без нейросетевого SR. Препроцесс — одна функция перед `load_image_payload`.

Критерий перехода B → A: на 10–15 реальных плохих скринах режим «Verify на мелких» не снижает заметно ошибки марок и пропусков строк. Тогда гипотеза «ломается не разрешение, а пропуск Verify» опровергнута, и 2× имеет смысл.

## Key Assumptions to Validate

- [ ] Плохие скрины действительно мелкие (короткая сторона условно < 1000–1200 px), а не Full HD с мелким шрифтом в углу — замерить `width/height` на 10–15 фейлах
- [ ] Verify находит пропуск строки и путаницу марок, а не повторяет ту же ошибку Extract — прогнать те же файлы с `OCR_VERIFY_MODE=always` и сравнить правки менеджера
- [ ] Принудительный Verify на мелких не взрывает стоимость / latency (второй вызов на фото, цель по-прежнему < 15 с p95) — логи `ocr_api_calls`, `ocr_cost_rub`
- [ ] (только перед этапом A) Модель не апскейлит мелкие картинки внутри себя так, что внешний 2× ничего не меняет — A/B: B vs B+2× на том же корпусе

## MVP Scope

**Этап 1 — in:**

- Порог «мелкий кадр» в `OcrVerifySettings` / env (например `OCR_VERIFY_AUTO_MIN_SHORT_SIDE`)
- `should_run_*_verify`: если короткой стороны < порога → Verify, reason `auto_small_image`
- Тесты политики: мелкий чистый extract больше не пропускает Verify; крупный чистый — по-прежнему может skip
- Прогон на пачке реальных скриншотов (не синтетика)

**Этап 1 — out:** изменение пикселей, DPI, UI wizard, новые промпты.

**Этап 2 — in, только после провала B:**

- Одна функция препроцесса: контраст + 2× Lanczos при короткой стороне < порога
- PNG на выходе, без JPEG
- Те же пайплайны, без кропа

## Not Doing (and Why)

- **Всегда поднимать DPI / resolution перед отправкой** — DPI для vision-модели не существует; слепой апскейл всех файлов — витамин с риском выдумать штрихи на цифрах марок
- **Автокроп таблицы / deskew** — на скрине Excel таблица уже есть кадр; кроп сам создаёт пропуски строк
- **Нейросетевой super-resolution (Real-ESRGAN и аналоги)** — галлюцинации на `6п`/`8п` хуже, чем пропущенная строка
- **Отдельный table-OCR (Paddle / Azure DI)** — другой проект; сначала закрыть дыру в Verify
- **Смена UI «вставьте текст вместо скрина»** — хороший обходной путь уже есть в wizard; не чинит текущий канал
- **Telegram-бот** — web wizard only

## Open Questions

- Какой порог короткой стороны взять на старте — 800, 1000 или 1200 px? Нужна гистограмма реальных фейлов
- Считать ли «мелким» огромный кадр с мелким шрифтом (нужна высота глифа, её в MVP нет)?
- 2× раздует байты: не упрёмся ли в лимит провайдера и не сработает ли уже существующий `auto_file_too_large` случайно?
- Корпус: плиты, сваи, ступени, марши, ФБС — один порог на всех или сначала только плиты?
