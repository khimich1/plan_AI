# Подготовка строки заявки до парсера КП

> Ideation: 2026-09-15  
> Источник: живой мастер — `C 14.35-T7 80 шт` и `C14-35T7 80шт` красные, хотя марка в прайсе  
> Смежные: [`unparsed-line-live-highlight.md`](unparsed-line-live-highlight.md), [`kp-bridge-piles.md`](../specs/kp-bridge-piles.md)  
> Spec (источник правды): [`../specs/kp-lint-normalizer-parity.md`](../specs/kp-lint-normalizer-parity.md)  
> Plan: [`../develop/plans/2026-09-15-kp-lint-normalizer-parity.md`](../develop/plans/2026-09-15-kp-lint-normalizer-parity.md)

## Problem Statement

**Как менеджеру КП вставить список из письма, Excel или фото так, как написано в заявке, и попасть в ту же позицию прайса — не уча шесть грамматик парсера и не подставляя соседнюю марку?**

Сейчас система умеет считать только «чистый» канон. Заявка почти никогда такой не бывает. Живая красная подсветка смотрит в сырой текст, расчёт — в чуть почищенный. Менеджер видит «не попало в расчёт» и серую кнопку, хотя изделие на заводе есть.

## Что происходит сегодня

На шаге 1 менеджер вставляет строки. Через ~0,5 с фронт зовёт `POST /commercial/parse` (lint). Сервер гоняет **сырой** `parse_*_line` по типу карточки (плиты / сваи / мостовые / ФБС / марши / ступени). Не совпало — оранжевое «Не попало в расчёт», «Обработать текст» нельзя нажать.

После успешной отправки preview уже прогоняет `normalize_*`: у части типов срезается ` шт` с пробелом, тире. ГОСТ мостовых и слитное `80шт` там тоже не живут.

Фото идёт в OCR, затем тот же парсер (gate) — снова без общей подготовки.

Итог: красное часто значит «не тот синтаксис», а не «нет в прайсе».

## Что мы хотим сделать

Не умный поиск и не новый экран. **Один слой подготовки копии строки перед парсером** — lint, расчёт и OCR-gate смотрят в него одинаково.

Поле ввода **не переписываем**. Менеджер по-прежнему видит то, что вставил. Меняется только то, что считается «разобралось».

Два уровня правил:

### 1. Общая чистка — все шесть типов

Мусор заявки, не имя изделия:

| Было | Для парсера |
|------|-------------|
| `… 80 шт` / `80 шт.` / `80 штук` | `… 80` |
| `… 80шт` (без пробела) | `… 80` |
| `1. C14-35T7 80` / `1) …` | без номера списка |
| длинное тире, неразрывный пробел | обычные `-` и пробел |

`шт` срезаем **после цифры количества**, пробел необязателен. Не вырезаем из середины марки.

Это закрывает живой пример на мостовых: `C14-35T7 80шт` — марка уже канон, ломается только qty.

То же на плитах, сваях, ФБС, маршах, ступенях: у них qty тоже «последний токен — число», `5шт` падает так же.

### 2. Канон нотации — только мостовые сваи

Заводской парсер ждёт `C14-35T7`. В заявках часто ГОСТ: длина×сечение точкой и дефис перед классом.

| Заявка | Для парсера / прайса | В поле и в PDF |
|--------|----------------------|----------------|
| `C 14.35-T7 80 шт` | `C14-35T7 80` | как в заявке (после лёгкой чистки пробелов) |
| `C14-35T7 80` | без изменений | без изменений |
| `C 14.35 80` без `T7` | не переводим | красное: несколько SKU, класс не угадываем |

`T7` в строке уже есть — это перевод формата, не подбор соседней марки. `T6` вместо `T7` система сама не поставит.

### Что не меняем

- Карточки мастера, кнопки, «Список верен».
- Грамматику парсеров: канон `C14-35T7` / `ПБ 78-12-8п` остаётся одним.
- Точный прайс. Нет fuzzy, нет эмбеддингов.
- Тип изделия по строке не угадываем: мостовая марка на шаге «Плиты» останется красной — нужна карточка «Мостовые сваи».
- Слэш плит `ПБ 40,3/2,6-8п` — по-прежнему красный (отдельная нотация).

## Какие проблемы это закроет

1. **Ложные красные из‑за `шт`.** Письма и таблицы пишут `80 шт` и `80шт`. Сейчас серая кнопка при верной марке. После — зелёное на всех шести типах.
2. **Ложные красные из‑за нумерации списка.** Вставка `1. марка qty` с Word/Excel. Номер в гуттере редактора — UI, его не трогаем; номер **в тексте** срезаем.
3. **ГОСТ vs завод на мостовых.** `C 14.35-T7` не доходит до прайса `C14-35T7`. После — та же цена, в КП написание заявки.
4. **Щель lint ≠ расчёт.** Подсветка больше не врёт относительно того, что произойдёт по кнопке (для этих правил). `шт` не будет «красным в поле, но съедаемым после отправки».
5. **Лишний OCR-verify на ГОСТ.** Gate сегодня отклоняет candidate до нормализатора. Тот же prepare в gate — меньше ложных `parser_rejected`.

Не закроет (и не обещаем в этом срезе):

- Неверную карточку типа (сваи на плитах).
- Неполную марку без класса (`C 14.35` без T).
- Слэш и прочие отдельные грамматики плит.
- Кривой OCR, который прочитал `T6` вместо `T7` — это ошибка цифры, не формата.
- Опечатки вроде `C14-35T` без номера.

## Как это выглядит для менеджера

**Сценарий A.** Шаг «Мостовые сваи», вставил `C14-35T7 80шт` → не красное → обработать → цена как у канона.

**Сценарий B.** Тот же шаг, `C 14.35-T7 80 шт` → не красное → в PDF видно заявку, деньги как у `C14-35T7`.

**Сценарий C.** `C 14.35 80` без T → красное, правит сам или дописывает класс.

**Сценарий D.** Шаг «Плиты», та же мостовая строка → красное, как сейчас. Нужно сменить тип.

Поле не прыгает и не подменяет текст. Красное значит «эту строку парсер этого типа всё ещё не знает».

## Recommended Direction

Один `prepare_source_line(raw, product_type)` (имя ориентир):

1. общая чистка (все типы);
2. мостовой ГОСТ-rewrite только при явном `T`/`В`+номер;
3. затем существующий `parse_*_line`.

Вызов: `lint_source_lines` (по физической `\n`-строке, индекс не менять), preview-нормализаторы, OCR `parser_gate`.

Lookup цены и геометрия рейсов мостовых понимают ГОСТ-марку, если она ушла в `order_data.mark` как заявка.

Векторный поиск, диалог «это C14-35T7?», перепись textarea, ИИ вместо regex — нет.

## Key Assumptions to Validate

- [x] Оба канала (текст и фото) в одном срезе — зафиксировано.
- [x] Слитное `80шт` на всех типах — зафиксировано по живому скрину.
- [ ] `C 14.35-T7` в текущем прайсе = `C14-35T7` (тот же SKU, суффикс не бросаем). Проверить импорт «Прайс» при PLAN.
- [ ] Prepare на 30–100 строках укладывается в дебаунс 500 ms.
- [ ] Типичные заявки мостовых пишут класс (`T7`); голая геометрия редка и остаётся красной — ок.

## MVP Scope

**In**

- Общая чистка qty-единиц с пробелом и без, нумерация списка, тире/пробелы — 6 типов.
- ГОСТ→заводской prepare мостовых только с явным классом.
- Lint / preview / OCR-gate на одном prepare.
- Display мостовых — заявка; цена — канон.
- Тесты на таблицу ниже.

**Out** — Not Doing.

Проверка ставки: три вставки на мостовых (`канон+шт`, `канон+80шт`, `ГОСТ+шт`) зелёные с верной ценой; плиты со слэшем красные; мостовая марка на шаге плит красная.

## Not Doing (and Why)

- **Векторный / fuzzy прайс** — `T6`/`T7` соседи, неверная цена хуже красной строки.
- **«Это C14-35T7?»** — на однозначном формате лишний клик.
- **Перепись поля** — марка в КП должна остаться как в заявке.
- **Автовыбор типа изделия** — смешает каталоги; менеджер выбирает карточку.
- **Слэш плит / добор в lint** — другая грамматика; split ломает номера строк подсветки.
- **Новая грамматика парсера вместо prepare** — канон один.
- **Серить «Список верен»** — контракт live-highlight.
- **ИИ как парсер текста** — медленно и угадывает SKU.
