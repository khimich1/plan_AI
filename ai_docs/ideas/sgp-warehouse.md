# Склад готовой продукции (СГП)

> Ideation session: 2026-07-27  
> Контекст: производственное планирование плит, жизненный цикл после дорожки.  
> Связанные модули: `ProductionCompletionService`, `completed_plates`, `kp_plates`, `plate_status_log`, wizard создания плана.

## Problem Statement

**Как разделить «произведено физически» и «закрыта потребность КП», чтобы мастер производства отправлял плиты на СГП, система не теряла ни одной штуки при отвязке и перепривязке, а планирование могло использовать уже лежащие на складе плиты вместо повторного производства?**

## Recommended Direction

### Выбор: эволюция `completed_plates` + split-on-action

Не вводить параллельную систему учёта. Расширить существующий поток завершения дня:

1. **`complete_day` → `send_to_sgp`** — та же атомарная цепочка (pre-flight → списание → audit), но семантика «на склад», а не «заказ закрыт».
2. **Таблица `completed_plates`** (или переименование в `sgp_inventory`) — физический регистр склада: `kp_id` **nullable**, статус `on_sgp`.
3. **`kp_plates`** — регистр потребности (заказ): «в производстве» / «в плане».
4. **Любая частичная операция** (отвязка, перепривязка) — **split строки** по образцу `insert_kp_plate_remainder_row` + запись в `plate_status_log`.
5. **UI:** вкладка «Склад готовой продукции» в `ProductionTabs`; кнопка «Отправить на СГП» вместо «Отметить выполненным» в `DayDrawer`.

### Жизненный цикл

```
kp_plates                    sgp_inventory (completed_plates)
─────────                    ───────────────────────────────
«в производстве» ──plan──► «в плане»
                              │
                    send_to_sgp (день целиком)
                              │
                              ▼
                         qty − из kp_plates
                         qty + на СГП, kp_id = X
                              │
              ┌───────────────┼───────────────┐
              │               │               │
         unlink (qty)    relink на КП-2   wizard: «с СГП»
              │               │               │
    kp_id → NULL      kp_id: X → Y      резерв без дорожки
    +1 потребность    ± потребность     при commit плана
    в пул             обоих КП
```

### Статус КП

Три этапа (отгрузка — позже):

| Этап | `kp_meta.status` | Где видно |
|------|------------------|-----------|
| Планируется / в производстве | «в работе» | Архив → «В производстве» |
| Все позиции на СГП и привязаны | **«На СГП»** | Там же + бейдж **«N/M на СГП»** |
| Отгружено покупателю | «выполнено» | «Выполненные» (не в MVP) |

**«На СГП»** выставляется автоматически, когда **все** позиции КП лежат на складе **и** у каждой есть `kp_id` (нет «висящих» без привязки).

**Промежуточный прогресс:** бейдж «7/10 на СГП» показывается **везде**, где фигурирует КП (архив, wizard, день производства, список СГП).

**Изменение в коде:** `check_and_update_kp_completion` сегодня ставит «выполнено», когда `SUM(qty)` в `kp_plates` = 0. Нужно заменить на проверку «всё на СГП и привязано» → «На СГП», а не «выполнено».

### Операции и инварианты

| Операция | sgp_inventory | kp_plates | kp_meta | plate_status_log |
|----------|---------------|-----------|---------|------------------|
| **Отправить на СГП** | +qty, kp_id=X | −qty из «в плане» | пересчёт «На СГП» / прогресс | `to_status=on_sgp`, `reason=sgp_send` |
| **Отвязать qty** | split; часть kp_id→NULL | +qty «в производстве» (пул) | «На СГП» → «в работе», если не все на СГП | `reason=sgp_unlink` |
| **Перепривязать на КП-2** | kp_id: 1→2 (strict match) | +qty КП-1 в пул; −qty у КП-2 | пересчёт статусов | `reason=sgp_relink` |

**Инвариант сохранения:** каждый переход qty фиксируется в audit-логе; split не удаляет историю родительской строки.

**Отвязка — две стороны одной операции:**
- **Физика:** плита остаётся на СГП без КП (`kp_id = NULL`).
- **Потребность:** у исходного КП +qty в «в производстве» (заказ снова ждёт изготовления, если не закроем перепривязкой).

**Перепривязка обратно на КП:** автоматически **уменьшает** открытую потребность этого КП (не нужно производить заново).

### Правила перепривязки

- **Strict match:** `plate_name` + `length_m` + `width_m` + `load_class` — иначе блок.
- **Целевой КП:** только если у него есть **открытая позиция** с такой номенклатурой в «в производстве».
- **UI:** plate-first — выбрали плиту на СГП → система предлагает подходящие КП; неподходящие не показываются / с подсказкой.

### Отправка на СГП (день)

- **Гранулярность:** весь день/план целиком (как сейчас `complete_day`).
- **Брак:** разрешён — годные → СГП, брак → возврат в «в производстве» (текущая логика `return_rejected`).
- **Кнопка:** «Отправить на СГП»; `plan.completed` / `completed_days` — семантика «день отправлен на склад».

### Wizard планирования и свободные плиты (MVP)

При создании плана, на шаге выбора КП/плит:

1. **Отдельная секция «Свободные плиты на СГП»** — плиты с `kp_id IS NULL`.
2. Пользователь отмечает, какие использовать в этом плане.
3. В плане появляется строка **«с СГП»** — **без слота на дорожке** (уже произведена).
4. При commit: выбранные плиты **привязываются к КП** (`kp_id`), потребность закрывается без производства.
5. **Перепривязка на вкладке СГП** остаётся доступной в любой момент.

### UI: вкладка «Склад готовой продукции»

- Новая вкладка в `ProductionTabs` (рядом с «Производственный календарь»).
- **Плоская таблица:** плита, размер, КП, заказчик, срок КП, qty, дата производства, plan/day.
- **Фильтры:** с КП / без КП / все.
- **Действия:** отвязать (с qty), перепривязать (plate-first).
- Плиты «под перепил» (v2) — бейдж в общей таблице, без отдельной вкладки.

### Краевые случаи

| Ситуация | Решение |
|----------|---------|
| Удалили план, часть плит уже на СГП | Плиты **остаются на СГП**; привязки из плана снимаются; при необходимости kp_id → NULL |
| Откат дня после СГП | **Не в MVP** — поведение как сейчас |
| Существующие `completed_plates` | Данных в боевой БД нет / не критично |
| КП частично на СГП (5/10) | Статус «в работе» + бейдж «5/10 на СГП» |

### Связь с текущим кодом

| Сейчас | После |
|--------|-------|
| `DayDrawer`: «Отметить выполненным» | «Отправить на СГП» |
| `move_plates_to_completed` | `move_plates_to_sgp` (или параметр статуса) |
| `completed_plates.kp_id NOT NULL` | `kp_id NULLABLE` |
| `PlateStatus.COMPLETED` в audit | `ON_SGP = "on_sgp"` |
| `check_and_update_kp_completion` → «выполнено» | → «На СГП» при условии all-linked |
| Архив: «Выполненные» после списания | «На СГП» остаёт в «В производстве» с бейджем |

## Key Assumptions to Validate

- [ ] Мастер производства справится и с отправкой, и с перепривязкой без отдельной роли кладовщика
- [ ] Strict match номенклатуры покрывает ≥95% реальных перепривязок
- [ ] Split-on-action не создаст неуправляемое число строк при типичных объёмах (нужна группировка или свёртка в UI при необходимости)
- [ ] Бейдж «N/M на СГП» везде не перегрузит интерфейс
- [ ] Строка «с СГП» в плане без дорожки понятна мастеру на производстве
- [ ] Авто-«На СГП» только при all-linked не блокирует работу при временных отвязках

## MVP Scope

**In:**

- `send_to_sgp` (замена `complete_day` по семантике)
- Миграция схемы: `kp_id NULLABLE`, статус `on_sgp`, новый `KpStatus.ON_SGP = "На СГП"`
- Вкладка «Склад готовой продукции» + API list/filter/unlink/relink
- Отвязка (qty) и перепривязка (plate-first, strict match, только КП с открытой позицией)
- Прогресс «N/M на СГП» на карточках КП
- Секция «Свободные плиты на СГП» в wizard + строка «с СГП» в плане
- Брак при отправке (как сейчас)
- Audit в `plate_status_log` для всех операций

**Out (Not Doing — v2+):**

- **Перепил:** брак → СГП «под перепил» без КП → выбор «во что пилить» → привязка к КП (двухшаговый сценарий, бейдж «перепил»)
- **Замена из запланированных дней** при перепиле (требует перепланировки)
- **Отгрузка покупателю** и ручное «Выполнено»
- **Поштучный учёт** (QR, qty=1 на каждую физическую плиту)
- **Откат дня** после отправки на СГП
- **Telegram-бот** для СГП
- **Экспорт** списка СГП (Excel/PDF)
- **True swap** двух плит между КП (только reassign)
- **Перепривязка «похожих»** плит с warning

## Not Doing (and Why)

- **Отдельная таблица WMS с нуля** — дублирует `completed_plates` и `plate_status_log`; дороже миграция
- **Статус «на СГП» в `kp_plates`** — смешивает потребность и физику; ломает планирование
- **КП → «выполнено» сразу после СГП** — плиты ещё не у клиента; вводит в заблуждение
- **Перепил в MVP** — сложная связка с перепланировкой; согласовано отложить
- **Блокировка удаления плана при наличии СГП** — мешает операционной гибкости; плиты на складе остаются
