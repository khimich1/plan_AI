# Целостность плана производства (A24 + A25 + A26)

> Дата: 2026-09-21. Статус: к реализации.
> Источник: форензик-расследование логов и `plita.db` за 2026-09-21;
> реестр находок `ai_docs/develop/audits/FINDINGS.md` —
> A24 (High, P1), A25 (Critical, P0), A26 (High, P1).

## Problem Statement

How might we сделать так, чтобы сохранённый план производства всегда совпадал с тем,
что реально поедет на формы: у каждой физической плиты на трассе есть хозяин
(`kp_plate_id`), марка бетона и ровно одна строка в БД — by construction,
а не по надежде?

## Три утечки — что найдено в живых данных (уточнено deep-dive 2026-09-21)

```
 КП (заказ)         оптимизатор              трассы (JSON)            БД (kp_plates)
 ────────────       ──────────────────────   ──────────────────────   ──────────────────────
 плиты с маркой →   ILP: спрос ТОЧНЫЙ (==) →  items БЕЗ марки     →   строки «в плане»
                     overproduction           cross-KP МИСАТТРИБУЦИЯ   day_number=NULL (сирота)
                     НЕВОЗМОЖНО (доказано)    (плита не того КП)      item без pid (призрак)
                      ▲ A26: только детекция    ▲ A24 + A25 (источник)  ▲ A25 (симптом)
```

- **A25 (сироты/призраки, Critical).** Источник — **двойная атрибуция одной геометрии
  к разным КП**: assignment-side (slot-ledger) и track-side (`_pick_best_order`,
  max-remaining) используют разные правила выбора и намеренно нешаренные
  consumed-счётчики (`plate_attribution.py:111–114`). Живой кейс
  `plan_20260904_124248`, плита «ПБ 20,6-7,2-8п»: заказано КП#4=3 (id=160 qty=2 +
  id=197 qty=1), КП#5=1 (id=179); физически на трассе 2026-09-14 лежат 4 плиты
  (итог сходится!), но атрибуция распределила их 2/2 вместо 3/1. Дальше
  симптом-механика: pro-rated ветка (`plan_commit.py:614–641`) → сирота id=197 с
  `day_number=NULL` (pool guard `:650`; orphan-rollback `:711–743` её не ловит);
  у КП#5 pool=1 < items=2 → призрак (silent `continue`, `:703–708`). **Канал
  точного фикса:** assignments и track items несут один и тот же `unit_id`
  (`finalize.py:224–226` ↔ `from_plan.py:693–694`) — матчинг по нему вместо
  геометрии устраняет кросс-КП полностью.
- **A24 (марка бетона, High).** Точка потери найдена точно:
  `from_plan.py:_build_sequence_from_plan_impl` — три места сборки item
  (`:676`, `:747`, `:944`) копируют из cut `kp_id`/`plate_name`, но НЕ
  `concrete_grade` (хотя `finalize.py:209` его на cuts ставит). Skip-путь
  `plate_attribution.py` (шаг 1, `:319`) добивает grade только items без identity —
  поэтому бэкфилл не спасает. Марка не критерий группировки (`builder.py`),
  стартера (`layout.py`), донора (`track_top_up.py`) — там grade-blind by design
  до решения завода о политике смешения.
- **A26 (перепроизводство, High → переформулировано).** ILP **не может**
  перепроизводить: все переменные `LpInteger` (`ilp_model.py:173–254`), спрос
  точный (`:261`, `z_prim + z_sec + unmet == qty`), `>=` в `:289` ограничен
  сверху тем же `==`. Рассинхрон `ceil`/`round` в `extract_cuts.py:61–62` vs `:140` —
  латентный дефект (сработает только если переменные сделают continuous).
  Живых surplus в планах не найдено: в кейсе КП#4/#5 физика сходится с заказом
  (4=4). Реальное содержание A26 — **слепота детекции**: `coverage_verify.py:60`
  (`ok = not missing`) молча пропускал surplus, пока были живы no_sources
  force-adds (умерли 10.09). Это tripwire-фикс, а не починка солвера.

## Recommended Direction

Четыре PR в порядке «атрибуция → источник → гейт → сигнал»:

```
 КП → orders → ILP → extract → attribution → tracks → [ГЕЙТ] → commit → БД
                      │           │             │         │
                      PR-2        PR-1          PR-1      PR-3: observe → enforce
                   единый round,  марка на      марка —   сверка «плита ↔ строка»
                   surplus=fail   каждом item   критерий   в обе стороны,
                                                 группировки  day_number=NULL
                                                              запрещён
                                                        │
                                                        PR-4: бейдж мастеру
                                                     «план чист / N расхождений»
```

| PR | Что делаем | Чем закрывает | Риск / приёмка |
|----|-----------|---------------|----------------|
| **PR-1. Марка end-to-end** | копировать `concrete_grade` из cut в трёх точках сборки item (`from_plan.py:676,747,944`); skip-путь `plate_attribution.py` добивает grade; убрать фолбэк `""` в day_view. **Без** смены группировки/доноров — это политика завода, отдельный шаг | A24 | Не меняет выход оптимизатора → hash-тесты раскладки ловят регресс. Приёмка: 100% root items с маркой в новом плане |
| **PR-2. Видимость surplus** | `coverage_verify`: surplus попадает в отчёт и становится fail-сигналом (`ok = not missing and not surplus`); единый rounding-helper в `extract_cuts` (гигиена, не корень); post-correction/force-add считаются в coverage явно | A26 | Детекция, не смена поведения солвера. Приёмка: искусственный surplus → fail в отчёте и логе |
| **PR-3. Источник (unit_id) + коммит-гейт** | **Источник:** track-side backfill матчит по `unit_id` — предпочитает `kp_id`, выбранный assignment-side для того же `unit_id`; reconciliation-pass — вторая линия (audit-лог). **Сеть:** гейт `_verify_plan_integrity` после `:710` (item→pool, NULL-день, rescue-leftovers), observe → enforce с обязательным откатом. Двусторонний ремонт id=197 (строка + item в JSON) | A25 | Enforce только ПОСЛЕ источника + неделя observe, иначе блокируем прод. Приёмка: кейс КП#4/#5 закрывается unit_id-матчингом; enforce-откат не оставляет пометок (тест) |
| **PR-4. Бейдж мастеру** | UI-бейдж «здоровье плана» поверх отчёта гейта: сироты / surplus / без марки | видимость A24–A26 | Дешёвый, когда гейт уже считает. Приёмка: мастер видит расхождение до печати |

## Почему так лучше

- **Сначала атрибуция (PR-1), потом детекция (PR-2).** Пока идентичность плит битая,
  surplus не атрибутируем — непонятно, ЧТО лишнее. PR-1 не трогает оптимизатор,
  поэтому безопасен и проверяем hash-тестами.
- **Гейт — сеть, а не лекарство; сначала источник (reconciliation), потом enforce.**
  Блокирующий гейт без починки мисатрибуции остановил бы сохранение планов на проде.
- **ILP-модель не трогаем — и не из-за осторожности, а потому что она невиновна:**
  доказано по коду (`ilp_model.py:261` точный `==`, все переменные `LpInteger`),
  перепроизводство солвером невозможно. surplus может родиться только после солвера
  (post-correction, force-add) — поэтому PR-2 про видимость, а не про солвер.
- **Каждый PR самостоятельно ценен и откатываем.** Нет «большого взрыва»:
  марка, точность, гейт и бейдж дают эффект по отдельности.

## Key Assumptions to Validate

- [ ] Hash-тесты раскладки покрывают `from_plan.py` / `plate_attribution` — иначе сначала тесты
- [ ] Единое округление в `extract_cuts` не уводит раскладку по существу (golden-master diff пуст или объясним)
- [ ] Observe-фаза гейта за N дней показывает, что расхождения — только исторические (id=197), а не текущие

## Locked decisions

| Тема | Решение |
|------|---------|
| Широкие плиты (>1.2 м) | Отсекаются на уровне создания КП — подтверждено данными: 0 строк >1.21 м в `kp_plates`, 0 событий `no_sources` с 11.09 (11 чистых дней). Действий нет; ERROR-лог «❌ НЕТ ИСТОЧНИКОВ» оставить канарейкой — не глушить |
| Стратегия гейта | observe → enforce; enforce по критерию «0 расхождений за N дней» |
| ILP-модель | Не меняем: спрос уже точный; surplus — дефект пост-обработки |
| Порядок работ | марка → surplus → гейт → бейдж; RESCUE/fallback-трассы не трогаем (0 срабатываний за 2 недели логов) |

## MVP Scope

**Входит**

- PR-1 целиком (марка end-to-end)
- PR-3, фаза observe (гейт-отчёт в лог при коммите) + ремонтный скрипт для id=197

**Не входит** — см. Not Doing.

## Not Doing (and Why)

- **Дедлайны КП vs дни производства (ПРОБЛЕМА 4)** — отдельная идея: это политика
  планирования (`fill_targets`), а не целостность данных
- **Запрет смешения марок на одной трассе** — политика завода, решение с производством;
  PR-1 даёт данные для этого решения, но не навязывает его
- **Ремонт всех исторических планов** — только id=197 (активный план); старые планы
  архивны, трогать их дороже, чем пользы
- **Изменение ILP-ограничений** — см. Locked decisions

## Критерии приёмки (сводно)

- Новый план: 100% root items трасс имеют `concrete_grade` (проверка скриптом по JSON плана)
- `coverage_verify`: `surplus > 0` → fail-сигнал в логе/отчёте, не `ok=true`
- Гейт enforce: план с item без `kp_plate_id` или строкой `day_number=NULL` не коммитится
- id=197: привязан к дню или снят со статуса «в плане» ремонтным скриптом с записью в лог
