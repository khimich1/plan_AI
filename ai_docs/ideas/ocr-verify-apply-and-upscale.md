# OCR: не затирать Extract без diff + 2× на мелких

## Problem Statement

How might we не давать второму проходу по мелкому скрину молча заменить более верный Extract — и дать обоим проходам чуть больше пикселей на символ, не трогая DPI и не выдумывая обрезанные строки?

## Recommended Direction

На пилотном скрине (`short_side_px=416`, `auto_small_image`, 2 вызова) Verify вернул `corrections=[]` и 10 строк. Пайплайн всё равно подставил `verified_plates` вместо Extract. Тот же файл до этапа B (один вызов) читался лучше: второй взгляд затёр `ПБ36` → `ПБ 63` и кириллическую **и** → латинскую **u**. Обрезанную последнюю строку ни один апскейл не восстановит.

**Склеиваем 2 и 4, этап B (`auto_small_image`) оставляем.**

1. **Apply-policy:** брать список Verify только если `plates` не пустой **и** `corrections` не пустой. Иначе оставить Extract, `verify_applied=true`, reason вроде `verify_kept_extract_empty_corrections`. Молчаливая перезапись запрещена во всех шести пайплайнах (один helper).
2. **Препроцесс:** если короткая сторона *исходника* `< OCR_VERIFY_AUTO_MIN_SHORT_SIDE` (default 1000): 2× Lanczos + лёгкий контраст, в API уходит PNG. DPI не пишем, кропа нет. Extract и Verify смотрят уже увеличенный кадр. Порог «мелкий» для Verify по-прежнему считается по исходнику (416×2=832 всё ещё мелкий — второй вызов остаётся).

B без правила (2) на этом фото вреден. 2× без правила (2) снова отдаст Verify право затереть Extract. Вместе: первый проход видит больше сетки, второй может поправить только названный diff.

## Key Assumptions to Validate

- [ ] На том же скрине Extract без подмены Verify снова даёт хвост не хуже, чем «вчера» (один вызов) — прогнать до/после apply-policy, ещё без 2×
- [ ] GigaChat на таких таблицах часто возвращает другой `plates` при пустом `corrections` — если нет, правило (2) ничего не меняет
- [ ] 2× Lanczos снижает путаницу `36`/`63` на этом кадре — A/B: Extract на raw vs 2×, смотреть только марки хвоста
- [ ] Verify с непустым `corrections` на 2×-кадре не хуже Extract (иначе мы начнём применять вредный diff)

## MVP Scope

**In:**

- Helper вроде `select_ocr_plates(extract, verify_result)`: пустой verify → fail, оставить extract; пустой `corrections` → extract + reason; иначе `parser_gate(verified)`
- Проводка во все 6 runners в `core/ocr/pipeline.py`
- `image_preprocess_for_ocr(path)`: 2× Lanczos + autocontrast, только если `min(w,h) < min_short_side`; результат PNG во временный файл / bytes для `load_image_payload`
- Тесты: silent rewrite не применяется; непустой diff применяется; 2× не трогает кадр ≥ порога; файл не мутируется на диске исходника
- Прогон на том же скрине 416 px

**Out:** откат `auto_small_image`; таблица омоглифов `u`→`и`; автокроп; DPI; нейросетевой SR; отказ «переснимите»; отдельные пороги по типу изделия.

## Not Doing (and Why)

- **Откат B** — пользователь явно оставил второй вызов; страхуем его правилом apply, а не выключаем
- **Применять Verify, если plates отличаются, а corrections пустой** — это и есть регресс; «додумать» diff самим — второй скрытый overwrite
- **Автокроп / deskew** — на этом фото нижняя строка уже срезана; кроп сделает хуже
- **Real-ESRGAN / text SR** — дорисует `63` и `u` ещё увереннее
- **Пометка DPI 300** — модель её не видит
- **Восстановление обрезанной 10-й строки** — пикселей нет; менеджер переснимает или правит вручную

## Open Questions

- Autocontrast Pillow vs лёгкий линейный contrast: что меньше портит серый Excel?
- 2× раздует PNG: не упереться в лимит GigaChat file upload?
