# График поставки: партии с датами внутри одного заказа

Дата: 2026-08-07. Статус: направление зафиксировано, MVP не начат.
Приоритет: раньше ИЖБИ (меньше объём, нет LLM-рисков).

## Problem Statement

Как дать менеджеру за 5–10 минут разбить заказ на партии с датами
«произведено до» / «поставлено до», видеть, тянет ли производство эти
сроки (на момент составления И по ходу производства), и получать готовый
документ «График поставки» для клиента.

Контекст: график появляется после согласования счёта. Источник — файл
клиента (матрица позиции × этаж/подъезд × диапазон дат) или «на словах».
Пока счёта нет — привязка к КП. Сейчас срок — одно текстовое поле
execution_terms на всё КП, графика поставки в системе нет. Тяжёлый случай
из практики: счёт 234 — 31 марка × 7 этажей × 3 подъезда ≈ 21 временной
слот на один заказ.

## Как это работает для пользователя

1. **Составление (после согласования счёта).** Архив КП → кнопка
   «График поставки» → редактор: слева позиции заказа с остатками,
   справа партии. Наполнение: импорт нашего XLSX-шаблона (высылается
   клиенту) или ручное «со слов» — «Добавить партию»: имя, диапазон
   поставки, «произвести до», позиции с количеством. Индикатор
   «разбито N из M», Σ партий ≤ кол-ва в КП.
2. **Правда о сроках до подписания.** Светофор под каждой партией:
   «3 этаж — красный: к 13.07 не успеваем, не хватает ~4 дорожек,
   реалистично 21.07». Торг с клиентом до обещания, а не после срыва.
3. **Документ клиенту.** «Сформировать документ» → DOCX приложения к
   договору (этажи-колонки, диапазоны дат, подписи). Файл хранится в
   архиве КП; номер счёта дописывается позже, документ перегенерируется.
4. **Контроль по ходу.** Открытие графика пересчитывает светофор по
   остатку (qty − completed): «4 этаж — жёлтый, запас 2 дня» →
   перекидываем мощность за 2 недели до срыва.
5. **Пересогласование.** Правим партию, регенерируем документ → новый
   файл `График_счёт237_ред_2026-06-20.docx`, старый остаётся в архиве.

Производственный план строится как сейчас: график — обязательство,
план — факт, дорожки не резервируются.

## Recommended Direction

Направление B целиком:
1. Партии как сущность: kp → delivery_schedule → delivery_batch →
   delivery_batch_item. Свободная группировка позиций, название партии
   свободное («1 этаж, 2 подъезд»). Одна позиция делится между партиями.
   Обе даты задаёт менеджер вручную.
2. Кнопка «График поставки» в архиве КП (рядом с CurrentPlanButton).
3. «Живой» светофор: потребность = остаток партии в дорожко-метрах
   × коэф. 1,15; симуляция по свободной ёмкости days_info от сегодня,
   партии в порядке дат поставки. Зелёный (>5 дней запаса) / жёлтый /
   красный + подсказка «нужно +N дорожек до даты». Пересчёт при каждом
   открытии.
4. Импорт своего XLSX-шаблона (детерминированный парсинг, без LLM).
5. Генерация DOCX/PDF «График поставки» по существующему пайплайну
   документов; invoice_number nullable; дата редакции в имени файла,
   старые файлы не перезаписываются.

## Key Assumptions to Validate

- [ ] (Dealbreaker) Оценка в дорожко-метрах vs факт. Тест: прогнать
      3–5 прошлых заказов, сравнить расчётную дату готовности с реальной.
- [ ] (Dealbreaker) Менеджер разбивает заказ ≤10 мин. Тест: UX-прогон
      на счёте 234 (31 марка × 7 этажей × 3 подъезда).
- [ ] (Важно) Клиенты/менеджеры готовы работать с нашим шаблоном XLSX.
      Тест: выслать шаблон 2–3 текущим заказчикам.

## MVP Scope (~3 недели)

1. БД: delivery_schedule / delivery_batch / delivery_batch_item +
   миграция (рядом с KP DB, граница app vs core.kp_db).
2. API: CRUD партий + /check (светофор) + /document (генерация).
3. Frontend: кнопка в архиве, редактор партий (группировка, даты,
   остатки), светофор, превью документа.
4. Импорт XLSX-шаблона завода.
5. Сервис автопроверки (симуляция по days_info, коэф. 1,15).

## Not Doing (and Why)

- LLM-парсер чужих форматов — фаза 2, через общий экран сверки с ИЖБИ
  (паттерн parser gate уже спроектирован).
- Резервирование дорожек под партии — смешивает обязательство и факт,
  убьёт фичу рассинхроном.
- История версий со статусной машиной — подписанный скан живёт в почте,
  система не ECM. Вместо этого: архив сгенерированных файлов с датой
  редакции в имени (бесплатно). Append-only лог правок — только если
  практика покажет споры «кто поменял». Триггер пересмотра: реальный
  случай «не смогли восстановить обещанное» >1 раза за квартал.
- Клиентский портал — рано, нет трафика.
- ILP в проверке сроков — агрегата с коэффициентом достаточно.

## Фазы после MVP

2. LLM-парсер произвольных графиков клиентов (общий экран сверки с ИЖБИ).
3. Сводный экран «все активные графики со светофорами» (утренний контроль).
4. Append-only лог правок — по триггеру выше.
