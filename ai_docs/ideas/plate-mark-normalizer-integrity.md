# Целостность нормализации марок ПБ

> Ideation: 2026-09-01  
> Точка поломки: `core/plate_text_normalizer.py` → `parse_catalog_mark` / `canonicalize_plate_line`  
> Смежные: парсер `core/plate_line_parser.py`, добор `core/dobor_split.py`, предпросмотр КП (жёлтый блок warnings)  
> Не путать с OCR: левая сторона стрелок уже верная; ломает следующий шаг

## Problem Statement

**Как сделать так, чтобы нормализатор марок ПБ никогда молча не превращал одну плиту в другую — ни на `70.5-12-8п`, ни на форматах, которых мы ещё не видели?**

Сейчас каталожная регулярка принимает десятичную длину через точку за заводской формат `L.W`. Худшее — не «нет в прайсе» (честный сигнал), а тихая подмена с найденной ценой: `ПБ 70.5-12-8п` → `ПБ 70-5,0-12п` (7,0×0,5 м, нагрузка 12 вместо 7,05×1,2 м, 8).

## Recommended Direction

**Сторож целостности + дизамбигуация формата** (направление Б). Сначала решить, какой это формат, потом нормализовать разделители. Не унифицировать точки в запятые на входе.

### Почему запятая «лечит» без правок кода

Каталог матчится только на ASCII-точку: `(\d+)\.(\d{1,2})`.  
`ПБ 47,5-12-8п` каталог не видит → обычный парсер (уже ест и `.`, и `,`) разбирает верно.  
`ПБ 47.5-12-8п` каталог видит как L=47, W=5, нагрузка=12, хвост `-8п` и количество выбрасывает.

Следствие: ручная замена точки на запятую — обход сломанного шага, не исправление. Слепо менять все точки на запятые нельзя: сломается легитимный каталог `ПБ 59.12-8Вр1400-25`.

### Утверждённые решения

| Тема | Решение |
|------|---------|
| Критерий успеха | Точность важнее покрытия. Непонятная строка = не переписывать + явное предупреждение. Никогда не угадывать молча |
| Где чинить | Нормализатор (`normalize_order_text` / `canonicalize_plate_line`), не OCR и не прайс |
| Дизамбигуация | Каталог применять только если после ядра `L.W-нагрузка` нет остатка `-число`. Иначе точка = десятичная часть длины |
| Разделители | После выбора формата: в обычном `.` и `,` — один десятичный разделитель; в марке для прайса — запятая. Каталог не трогать |
| Сторож | После любой трансформации сверить значащие токены (числа длины/ширины/нагрузки + количество). Потерял или подменил — откатить, оставить исходник, предупредить |
| Что сторож не считает потерей | Слова (`петли`, `Вр1400-25`), пробелы, регистр |
| Добор в этом релизе | Не трогаем (в рабочей выборке его нет). Явные размеры `доб. L-W-N` — следующий кусок: парсить вторую марку; формула `12−W` только fallback (на ИПБ 10,7+1,25≠12) |

### Почему так

- Прогон рабочей ведомости: 10 из 14 строк сломаны, 32 плиты → 25 (съедено количество). Эскиз «остаток `-число` → не каталог»: 14/14 верно, каталог `59.12-8Вр1400-25` и `56.05-10` без регресса.
- Жёлтый блок предпросмотра — это warnings нормализатора, не OCR. После фикса для этого класса стрелок не будет: строки не переписываются.
- Сторож закрывает класс «тихая подмена», а не один regex. Следующий неизвестный формат получит честный отказ, а не другую плиту в КП.

## Key Assumptions to Validate

- [ ] Голый каталог `ПБ56.05-10` (без `Вр…`) — живой формат, его надо сохранить. *Как проверить:* выборка бота / заводских выгрузок за последние месяцы; есть в текущих тестах.
- [ ] Сигнал «остаток начинается с `-число`» не ломает ни один реальный каталог. *Как проверить:* прогнать архив нормализованных входов + тесты `test_plate_normalizer.py`; каталог с «п» после нагрузки, если всплывёт — отдельное правило.
- [ ] Сторож по числам+qty не даст ложных откатов на легитимном каталоге (`59, 12, 8` сохраняются). *Как проверить:* те же каталожные фикстуры до/после.

## MVP Scope

В фокусе — ноль тихих подмен на обычном формате с десятичной длиной.

**Входит**

- Правило дизамбигуации в `parse_catalog_mark` / `canonicalize_plate_line`.
- Сторож целостности токенов + откат + warning (не «я преобразовал каталог», а «не применил: потеря чисел/количества»).
- Регрессионные тесты на пул ниже + существующие каталожные кейсы.
- Прогон той же ведомости: 32 плиты, размеры как во входе, жёлтых стрелок этого класса нет.

**Не входит в MVP, но зафиксировано как следующий кусок:** добор с явными размерами.

### Пул вводов → один результат

| Вариант ввода | Ожидание |
|---|---|
| `ПБ 47.5-12-8п 2` / `ПБ 47,5-12-8п 2` / `ПБ 47,50-12-8 2 шт` | 4,75×1,2 м, 8п, 2 шт |
| `ПБ 47.5-10.7-8 4` / `ПБ 47,5-10,7-8п 4` / смешанное `47.5-10,7-8` | 4,75×1,07 м, 8п, 4 шт |
| `ПБ 43.0-12-8п` / `ПБ 43,0-12-8п` / `ПБ 43-12-8п` | 4,3×1,2 м, 8п |
| `ПБ 70.5-10.7-8п 3` | 7,05×1,07 м, 8п, **3** шт (сейчас qty→1) |
| `ПБ 59.12-8Вр1400-25` / `ПБ56.05-10` | каталог, как сейчас |
| `ПБ 57-7,2-8п + доб 5-шт` | текущий сплит, без регресса |

## Not Doing (and Why)

- Реестр форматов с приоритетами (направление В) — правильная конечная форма, сейчас пул мал; переписывать общий бот+веб парсер ради трёх правил рано
- Слепая замена всех точек на запятые — ломает каталог `59.12`
- Чинить «нет в прайсе» расширением справочника под `10,7` / `5,3` — после фикса отказ по нестандартной ширине будет честным, это не баг нормализатора
- Склейка дублей (`47.5-5.3-8п 1` ×4) — раздувает предпросмотр, не подменяет плиту
- ИПБ / «петли» на слое OCR/промпта — отдельный вход; нормализатор `ИПБ` сам не ломает
- Менять lookup прайса и формулы ширины в `make_plate_name`

## Open Questions
