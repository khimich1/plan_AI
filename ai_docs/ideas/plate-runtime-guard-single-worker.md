# Страж заказа плит и один воркер (A1 + A2)

> Дата: 2026-10-12. Статус: направление выбрано.
> Уточняет `ai_docs/ideas/explicit-process-state.md` (2026-09-21): из того плана
> в эту идею входят только страж и жёсткий один воркер.
> Схема: `~/.cursor/projects/home-roman-project/canvases/guard-and-single-worker.canvas.tsx`.

## Problem Statement

How might we сделать так, чтобы забытый контекст заказа плит не подставлял чужие
ширины в КП, а второй процесс uvicorn не мог тихо удвоить лимит входа и писать
в тот же SQLite — без переписывания оптимизатора раскладки?

## Recommended Direction

Две проверки в уже существующих точках. Веб-путь с middleware не переписываем:
`PlateMutableRuntimeIsolationMiddleware` уже кладёт свой `PlateOrderContext` в
ContextVar, и два одновременных расчёта получают два заказа.

**Страж (A1).** Единственная точка — `get_plate_mutable_runtime()` в
`core/plate_runtime_state.py`. Если ContextVar пуст, getter сегодня берёт
`threading.local`: один объект на поток из пула, прошлый заказ читается без
исключения. Прокси `config_and_data` ходит через тот же getter.

Сначала warning: в лог пишется caller, расчёт ещё идёт по старому пути, чтобы
увидеть скрипты и забытый `bound()`. Когда горячие пути молчат — тот же вызов
падает до чтения ширины и метаданных. `get_exact_width` и
`consume_plate_metadata` отдельно не патрулируем.

**Один воркер (A2).** Лимит входа и лимит OCR — словари в памяти процесса.
Второй процесс — второй словарь, эффективный лимит примерно умножается на число
процессов; SQLite получает второго писателя. Расширяем
`enforce_single_instance_workers` в `app/security/login_rate_limit.py`:

- объявлено больше одного воркера, общего хранилища нет — процесс не стартует
  ни в одном окружении;
- в production переменная не задана (`UVICORN_WORKERS` / `WEB_CONCURRENCY` /
  `APP_WORKERS`) — процесс не стартует;
- ровно один воркер — старт как сейчас.

`RATE_LIMIT_SHARED_STORE=redis` остаётся `NotImplementedError`.

## Key Assumptions to Validate

- [ ] Завод остаётся на одном компьютере, пока второго хоста нет датой в календаре — иначе эта идея не закрывает масштаб
- [ ] Горячий HTTP-путь уже входит в `bound()` / middleware, и страж в режиме raise на нём не стреляет — прогон существующих тестов коммерции и производства
- [ ] Режим warning сначала находит живых callers вне веба (скрипты, тесты, CLI), и их список короткий
- [ ] `bot_archived` нигде не запущен — мигрировать его не нужно
- [ ] В проде `UVICORN_WORKERS=1` уже стоит в env — иначе undeclared-fail уронит рабочий старт

## MVP Scope

Входит:

- Страж в getter: флаг warning, затем raise, если ContextVar не привязан
- Тест: два параллельных запроса с middleware не видят плиты друг друга; вызов без `bound()` в режиме raise падает
- Отказ старта при `workers > 1` без shared store во всех окружениях
- Отказ старта в production, если число воркеров не объявлено
- Поправить `ai_docs/develop/deploy-contract.md` и тесты `test_rate_limit_deployment`

Не входит в эту поставку — см. Not Doing.

## Not Doing (and Why)

- **Полная миграция «заказ только аргументом» и удаление прокси** — правильный конец, широкий дифф на денежном пути раскладки; время после того, как страж помолчит
- **Заморозка `LayoutRuntimeSnapshot` на входе в расчёт** — гонка двух потоков на одном объекте на веб-пути не показана: запрос ждёт свой поток, у запроса свой объект
- **Redis и смена SQLite** — лечат второй компьютер, которого нет
- **Очередь на раскладку и LibreOffice** — лечит подвисание сайта во время расчёта, это не названная боль
- **Отдельный процесс на каждый расчёт** — изоляция ценой старта Python на каждое КП
- **Счётчики лимита в SQLite** — нет сценария «несколько воркеров на одном хосте»

## Open Questions

- Сколько дней warning, прежде чем включить raise: критерий «ноль срабатываний на горячем пути»
- Кто смотрит `/health` и заметит `workers_undeclared`, пока отказ старта ещё не включён
- Одноразовые скрипты в `scripts/`, которые читают runtime без `bound()`: поправить обёрткой или удалить
