# КП на сваи

> Ideation session: 2026-07-30  
> Контекст: появился прайс цельных свай (`core/pile_price_db.py`, таблица `pile_prices` в `pb.db`); мастер создания КП сейчас работает только с плитами.  
> Связанные модули: `CommercialOfferWizard`, `CommercialWizardStepService`, `core/plate_line_parser.py`, `core/commercial_offer*.py`, `core/pile_price_db.py`.

## Problem Statement

**Как дать менеджеру возможность создать отдельное коммерческое предложение на сваи с тем же UX, что у плит — быстрый ввод (текст + фото), точная цена из `pile_prices` по классу бетона каждой позиции и выдача PDF/XLSX в архив?**

## Recommended Direction

### Выбор: «Шаг 0: тип продукта» + общий каркас мастера

Перед текущим wizard — выбор **«Плиты»** или **«Сваи»**. Дальше общая оболочка (`client → result → save`), но шаг 1, парсер, API и генерация файлов — отдельные для свай.

```
[Создать КП] → Плиты | Сваи
                    ↓
         Шаг 1: ввод (текст / фото / ИИ)
                    ↓
         Таблица: Марка | Класс бетона | Кол-во | Цена
                    ↓
         Шаг 2: Клиент (без изменений)
                    ↓
         Шаг 3: Результат → PDF/XLSX → Архив
```

**Почему так, а не смешанное КП или отдельный wizard:**
- Менеджер явно выбирает тип — нет конфликта с логикой wide-plates, OCR плит и производства.
- Переиспользуем client/result/save/archive — меньше дублирования, чем два независимых мастера.
- `product_type: "plates" | "piles"` в metadata черновика — единая точка ветвления на фронте и бэкенде.

### Ключевые продуктовые решения

| Решение | Выбор |
|---------|-------|
| Тип КП | Только отдельное: либо плиты, либо сваи |
| Ввод | Текст + фото + ИИ (как у плит) |
| Класс бетона | Парсится из текста заявки, если указан; иначе — быстрая простановка в таблице (dropdown + «применить ко всем») |
| Цена | `get_pile_price(mark, concrete_grade)` из `pile_prices` |
| Неизвестная марка | Блокировать расчёт, пока все позиции не найдены в прайсе |
| Выходные файлы | Тот же макет PDF/XLSX, что у плит; колонки: марка, класс, кол-во, цена |
| После сохранения | Архив + файлы; **без** производства и СГП |
| Нумерация КП | **Единая сквозная** (`kp_id`): плиты №2 → сваи №3; интеграция с 1С — позже |

### Технический контур (черновик)

**Backend:**
- `product_type` в metadata черновика КП
- `core/pile_line_parser.py` — разбор строк вида `С120.35-12 B25 5` (марка, grade, qty)
- OCR/ИИ-промпт под марки свай (аналог `core/plate_format_prompt.py`)
- API: `POST/PATCH .../piles` (по аналогии с `.../plates`)
- Расчёт: позиции с `concrete_grade` → lookup в `pile_prices`
- Валидация: все марки должны иметь цену для выбранного класса

**Frontend:**
- Экран выбора типа при «Создать КП»
- `PileInputStep` — клон UX `PlateInputStep` (текст, фото, paste, ИИ)
- `KpPilePreviewPanel` — таблица с dropdown класса (B15, B20, B22_5, B25, B30_granite), live-цена, массовое применение класса
- Wizard: условный первый шаг по `product_type`
- Архив: бейдж «Сваи» (фильтр — nice-to-have)

**Генерация файлов:**
- PDF/XLSX на базе существующих генераторов с колонками под сваи
- Без производственных артефактов (схема раскладки, breakdown плит)

## Key Assumptions to Validate

- [ ] **Марки свай однозначно парсятся** из текста и OCR (форматы вида `С120.35-12`, `С120.35-13и`) — тест на 5–10 реальных заявках менеджеров
- [ ] **Класс бетона** часто есть в заявке; когда нет — dropdown в таблице достаточно быстр — опрос 2–3 менеджеров
- [ ] **Шаблон PDF/XLSX** для свай совместим с текущим макетом плит (другие колонки, та же структура) — сверка с реальным Excel КП на сваи
- [ ] **Strict match марок** к `pile_prices` приемлем (без fuzzy) — если в заявке опечатка, менеджер правит вручную до расчёта
- [ ] **Шаги client/result** не требуют pile-специфичных полей (условия, менеджер, сроки — те же)

## MVP Scope

**In:**
- Выбор «Плиты / Сваи» при создании КП
- Ввод текста + фото + ИИ для свай
- Таблица позиций: марка, класс бетона (per-line), кол-во, цена из прайса
- Парсинг класса из текста; fallback — UI в таблице
- Блокировка расчёта при неизвестных марках
- Расчёт итога, генерация PDF/XLSX, сохранение в архив
- `product_type` в metadata; отображение типа в архиве

**Out (следующие этапы):**
- OCR/фото — если отдельно решат урезать scope (сейчас in)
- Fuzzy-match марок
- Смешанное КП (плиты + сваи в одном документе)
- Производство, планирование, СГП для свай
- Составные / шнековые сваи (только цельные из текущего прайса)
- Отдельная нумерация / интеграция с 1С
- Excel-импорт как основной канал ввода

## Not Doing (and Why)

- **Смешанное КП** — явный выбор «отдельно плиты или сваи»; упрощает парсер, wizard и архив
- **Производство / СГП** — вне scope MVP; сваи не идут в производственный цикл плит
- **Fuzzy-match марок** — блокировка при неизвестной марке; меньше риска неверной цены
- **Автоподбор класса из марки** — класс задаёт менеджер или приходит в тексте; прайс многоклассовый
- **Отдельный wizard целиком** — дублирование client/result без выигрыша
- **Отдельный счётчик для свай** — одна серия `kp_id` для всех КП

## Open Questions

- 2–3 **реальных примера** строк заявок на сваи — для тестов парсера и OCR (можно на этапе разработки)
- Есть ли **готовый Excel КП на сваи**, отличающийся от плитного по структуре — сверить при генерации
- Нужен ли **фильтр по типу** в архиве в MVP или достаточно бейджа «Сваи»

## Success Criteria

1. Менеджер делает КП на сваи **быстрее**, чем в Excel
2. **100% цены** из `pile_prices` — без ручного поиска в прайсе
3. **Тот же UX**, что у плит — минимум обучения (текст, фото, 3 шага, архив)
