# КП: доставка для ФБС / ступеней / маршей по известной массе

> Идеация 2026-09-10 (idea-refine). Спека: [`ai_docs/specs/kp-delivery-fbs-steps-marches.md`](../specs/kp-delivery-fbs-steps-marches.md)

## Problem Statement

Как менеджеру при создании КП получать корректную доставку для любого изделия с известной массой (ФБС, ЛС, ЛМ — не только плиты и сваи), без ручных досчётов, чтобы документы сходились у бухгалтерии.

## Recommended Direction

Третий весовой котёл в `calculate_total_cost`: сумма масс строк `fbs` + `steps` + `marches` → рейсы = `ceil(кг / 20 000)` × стоимость рейса (формула подтверждена пользователем 2026-09-10). Плиты (18 600 кг) и сваи (норма шт/20т из `pile_catalog`) не трогаем.

Источник веса — новый справочник по маркам, импорт из 1С-выгрузок (`банк знаний/Новая папка/*.xlsx`: Наименование | Вес | Объём | Код 1С) с валидатором: обязательные колонки, плотность 1500–3500 кг/м³, дубли. ЛС: точное совпадение марки → fallback на семейство (ЛС-N, веса внутри семейства однородны). Задел под `shipment_packing` (там уже лимит по весу) — тот же справочник.

## Key Assumptions to Validate

- [ ] Тариф рейса общий для всех типов (одно поле «Стоимость рейса») → подтвердить у логистики
- [ ] 20 000 кг — подтверждённая грузоподъёмность для этих изделий → логистика
- [ ] Объём не «кончается» раньше веса (ступени 133–245 кг, но габаритные) → проверить на 1–2 реальных КП
- [ ] Веса из 1С — нетто изделия, без палет/упаковки → сверить с производством
- [ ] 15 марок ЛС без точного веса (`ЛС11`, `ЛС11-2`, `ЛС11-Б`, `ЛС14-Б`, `ЛС15-Б`, `ЛС22`, `ЛС22-2` + ЛЕВ) — семейный fallback приемлем → менеджер
- [ ] Расхождение весов свай (11 марок, каталог vs 1С, до −6,3%) — отдельная data-задача сверки, не блокер

## MVP Scope

- Таблица справочника весов (марка, тип, вес, объём, источник) + импортер с валидацией
- Resolver веса строки КП для fbs/step/march (точный → семейный ЛС → pending)
- Котёл в `calculate_total_cost` + breakdown в totals (рейсы, pending-марки, ready)
- Строка доставки в PDF/XLSX по существующей конвенции котлов
- Поле «Стоимость рейса» в визарде показывается и для mono ФБС/ЛС/ЛМ драфтов
- pytest на математику котла, resolver и импорт; регрессия плит/свай

## Not Doing (and Why)

- **Сваи и `pile_catalog`** — расчёт работает; расхождения весов — отдельная data-задача
- **Новые типы продукции в визард** (перемычки, прогоны, тротуарные плиты, ЛП, кросс-блоки) — нет прайсов в pb.db и product types в визарде; веса лежат в файлах на будущее
- **Совмещение плит+ФБС в одну фуру** — редкий случай, ручная правка менеджером
- **Отдельные тарифы по типам** — запроса нет, одно поле рейса
- **Правка НДС обычного КП** (налог с доставки) — отдельная история, вопрос бухгалтерии
- **Ручной ввод числа рейсов** для этих типов — противоречит критерию «без ручных досчётов» (оставлен как pending-fallback через существующий механизм свай не требуется — pending просто показывается)

## Вопросы к бухгалтерии / логистике (вынести до релиза)

1. Тариф рейса — уже с НДС? В обычном КП НДС с доставки не выделяется (vat = изделия × 22%) — корректно ли для счёта-фактуры заказчика?
2. Новые строки доставки («Доставка ФБС/ЛС/ЛМ») — бухгалтерия заказчика примет услугу или нужен «вшитый» вариант?
3. Скидка на доставку не распространяется — общее правило для всех типов?
4. 20 000 кг — подтверждённая грузоподъёмность? С палетами или без?
5. Какой источник весов эталонный при расхождениях (1С-выгрузка vs `pile_catalog`)?
6. Смешанный рейс (плиты+ФБС одной фурой) — как делить в документах, если случится?
7. Самовывоз (доставка 0 ₽) — как оформляется в первичке?
