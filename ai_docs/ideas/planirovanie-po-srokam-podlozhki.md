# Планирование от ёмкости: срочные плиты + подложки из поздних КП

Дата: 2026-08-10. Статус: направление зафиксировано, MVP не начат.
Связь: соседняя идея `grafik-postavki-partii.md` — график поставки является
приоритетным источником дедлайнов для этой фичи.

## Problem Statement

Как менеджеру, заранее задав мощность (дорожки) на дни, получать предложение
состава плана, которое закрывает сроки и не теряет эффективность реза — за
счёт подкладывания поздних плит, которые оптимизатор фактически режет из
остатков срочных?

Сейчас менеджер вручную решает, что тянуть в план (`list_kp_candidates`
отдаёт КП «в работе» без дедлайнов), а ёмкость дня — константа
`MAX_TRACKS_PER_DAY` (`plan_calendar.py`, по-дневного редактирования нет).
О резах-доборах из поздних заказов система не знает ничего: остаток формы
уходит в отход, хотя его могла бы закрыть плита более позднего КП.

## Recommended Direction

1. **Ёмкость заранее.** По-дневное переопределение количества дорожек
   (сейчас `max = MAX_TRACKS_PER_DAY`, константа) + fallback на константу.
2. **Выбор дней → pull срочных.** Система собирает позиции с дедлайном ≤
   последний день выборки. Дедлайн: `produce_by` партий графика поставки
   приоритетно; fallback — `execution_terms` (парсер `core/execution_terms.py`,
   дефолт 14 дней). Гранулярность — позиция/партия, не КП целиком: у КП с
   графиком часть позиций срочные, часть — поздние.
3. **Аналитический прогон (кнопка «Найти подложки»).**
   `optimize_with_cascading_longitudinal_cuts(orders_2d = все плиты «в
   производстве»)`. Ёмкость игнорируется — прогон ради мэтчей, не ради плана.
4. **Рекомендации из фактических резов.** Вторичные резы в результате несут
   `kp_id`, `plate_name` и связь с родительским primary (slot-ledger в
   `optimize_2d/finalize.py`). Поздняя плита, порезанная из остатка срочной →
   рекомендация «подложить ПБ 57-4,8 ×3 (КП-127, срок 05.09) под ПБ 57-7,2
   (КП-115)». Второй ярус — поздние плиты, сматчившиеся с чем угодно, для
   догрузки остатка дорожек. Подложка предлагается в количестве, реально
   режущемся из остатков, а не всей позицией.
5. **Одобрение → существующий путь.** Отмеченный галочками список (срочные +
   подложки) уходит в `build_plan_from_filters` → оптимизатор → дорожки →
   визуализация. Жёстких связок нет: рекомендация — умный преселектор,
   финальный прогон свободен; конкретная пара из подсказки может дрейфовать
   на перепрогоне подмножества — это норма, эффективность не теряется.
6. **Дефицит ёмкости.** Срочные не влезают в дорожки выбранных дней →
   показать «+N дорожек до <дата>» (логика `delivery_schedule_check.py`),
   молча не обрезать.

## Key Assumptions to Validate

- [ ] A1. Мэтчи существуют: на реальном бэклоге заметная доля срочных плит
  имеет вторичный рез в поздние КП. Проверка: скрипт на `plita.db` — полный
  прогон + подсчёт мэтчей. Мэтчей нет → фича мертва, не строим.
- [ ] A2. Время полного прогона на всём бэклоге — секунды/десятки секунд
  (интерактивная кнопка с ожиданием, не автомат). Замер тем же скриптом.
- [ ] A3. `execution_terms` парсится у большинства КП «в работе» (прогнать
  парсер по БД, доля непарсящихся).
- [ ] A4. Менеджер принимает/редактирует предложенное, а не игнорирует
  (пост-запуск: доля принятых подложек).

Проверка A1–A3 — первый шаг реализации, до всякого UI: один скрипт на
реальной базе отвечает, живая ли фича.

## MVP Scope

Входит:
- По-дневная ёмкость: хранение переопределений + правка в календаре
  производства (fallback на `MAX_TRACKS_PER_DAY`).
- Сервис «срочные по сроку»: сбор позиций с дедлайном ≤ последний день
  (график поставки → `execution_terms`).
- Кнопка «Найти подложки»: аналитический прогон всего бэклога + извлечение
  мэтчей из secondary cuts.
- UI в wizard создания плана: блок «Срочные по срокам» (автопредложение) +
  блок «Подложки из поздних КП» (галочки, контекст: кого под кого, экономия
  метров).
- Дефицит ёмкости «+N дорожек» по мотивам светофора.

Не входит:
- Итеративные раунды перепрогона (один аналитический прогон, без цикла).
- Автозапуск анализа (только по кнопке, пока не измерено A2).
- Сводный блок красных партий (фаза 1.5 графика поставки — отдельно).

## Not Doing (and Why)

- **Фоновый прогон оптимизации при сохранении КП + таблица пар** — пары
  рождаются из микса в момент планирования; per-KP прогон видит только
  внутри-КП пары и протухает при каждой правке состава. Аналитический прогон
  даёт те же «пары с kp_id» без инвалидации.
- **Пары по формуле 12 − W (`dobor_split.py`)** — не знают длин и фактических
  остатков; в живом 2D-пути мэтчинг идёт по (длина × остаток × класс
  нагрузки), ветка 1D — только обратная совместимость.
- **Жёсткие связки «плита только с парой»** — убивают свободу оптимизатора;
  рекомендация ≠ ограничение.
- **Автоплан** (система сама собирает план, менеджер утверждает) — пока нет
  доверия, заработанного MVP.
- **Резервирование дорожек под график поставки** — осознанное «нет» из спеки
  `docs/specs/delivery-schedule.md`, не пересматриваем.

  финализатор (маленький diff).
- Источник «все плиты в производстве» для анализа: дефолт — фильтр как у
  `list_kp_candidates` (`in_plan_pct < 100`); уточнить про частично
  запланированные.
- Единый UI: расширяем существующий выбор дней/fill targets правкой max на
  день или отдельный режим редактирования ёмкости.
