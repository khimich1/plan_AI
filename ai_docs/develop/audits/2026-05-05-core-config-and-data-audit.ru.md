## Критические проблемы (исправить немедленно)

### [A1] Глобали как поверхность интеграции: заказ → ILP → визуализация
**Категория**: Архитектура  
**Место**: дизайн уровня модуля; паттерн состояния PlateOrder  
**Влияние**: 
- Конфликты конкуренции: одновременная обработка заказов портит глобальное состояние (например, сбои вроде `test_layout_secondary_unmatched_parent_user_list` из-за перекрёстного загрязнения)
- Интеграция ILP-решателя затруднена: нужны изолированные копии состояния, а не общие изменяемые глобали
- Визуализация «картины по заказу» небезопасна: несколько потоков/запросов конкурируют за `kp_db`, состояние `prays_by_plate`
- Непредсказуемые каскадные сбои при прохождении нескольких заказов через конвейер оптимизации

**Исправление**:
1. Вынести контекст заказа в изолированный неизменяемый dataclass `OrderContext` (не глобали)
2. Прокидывать контекст через слой ILP и визуализацию как зависимость
3. Возвращать результаты без побочных эффектов; вызывающий объединяет с персистентным хранилищем
4. Пример: `def optimize_order(context: OrderContext) -> OptimizationResult` вместо `apply_to_globals()`

---

### [A2] `PlateOrder.apply_to_globals()`: legacy-мост и риск «двух истин»
**Категория**: Архитектура  
**Место**: метод `PlateOrder.apply_to_globals()` (ориентировочно строки 400–500)  
**Влияние**:
- Два источника истины: состояние объекта (`self.plates`, `self.totals`) и глобали (`kp_db`, `prays_by_plate`, `plate_totals_cache`)
- Обновления могут молча не доходить; вызывающий не знает о несогласованности глобалей
- Частичное применение оставляет модуль в сломанном состоянии при исключении посередине обновления
- Legacy-стиль PlateOrder конфликтует с современным неизменяемым/функциональным потоком данных заказа

**Исправление**:
1. Заменить `apply_to_globals()` на чистую функцию: `def apply_plate_order(order: PlateOrder, state: GlobalState) -> GlobalState` (новое состояние, без побочных эффектов)
2. Убрать split brain: решить — PlateOrder это ORM-подобный объект или неизменяемый DTO?
   - Если ORM: SQLAlchemy или явная сессия/commit
   - Если DTO: сериализация в/из хранилища, не промежуточные глобали
3. Явная транзакционная семантика: всё или ничего, либо откат при частичном сбое
4. Тесты при конкурентных запросах; убедиться в отсутствии утечек состояния между заказами

## Высокий приоритет (исправить вскоре)

### Архитектура

**[A3] Нарушение SRP: мегамодуль**  
**Место**: весь `core/config_and_data.py`  
**Суть**: PlateOrder, разбор заказов, инициализация глобалей, хелперы ILP, подготовка данных «картины», генерация имён, отладочный I/O, кеши — в одном файле.  
**Влияние**: нельзя изолированно тестировать и переиспользовать; высокая когнитивная нагрузка; изменения бьют по неожиданным подсистемам.  
**Исправление**: разнести по модулям:
- `plate_order.py` — класс PlateOrder и сериализация  
- `order_context.py` — неизменяемый контекст и хелперы  
- `ipl_adapter.py` — интеграция с ILP  
- `visualization_adapter.py` — подготовка данных «картины по заказу»  
- `config_globals.py` — инициализация общего состояния (временно, для миграции)

**[A4] ILP жёстко привязан к глобалям `cfg`, а не к абстрактному контексту заказа**  
**Место**: код интеграции ILP (поиск вызовов солвера, построение матрицы)  
**Суть**: солвер читает `kp_db`, `prays_by_plate` напрямую вместо изолированного параметра контекста заказа.  
**Влияние**: нельзя параллелить несколько задач оптимизации; тесты требуют поднятия глобального состояния; перенос солвера в другой проект — копирование глобалей.  
**Исправление**:
1. Вход ILP (матрица, границы, целевая функция) в неизменяемую структуру `ILPInput`
2. Солвер принимает `ILPInput`, возвращает `ILPSolution` (без мутации глобалей)
3. Обязанность вызывающего: контекст заказа → `ILPInput` → применение решения

**[A5] Тройное дублирование логики итогов**  
**Место**: расчёты разбросаны (PlateOrder, проверка кеша, функции импорта)  
**Суть**: `sum()`, `compute_totals()`, логика `plate_totals_cache` написаны независимо.  
**Влияние**: баги рассогласования (устаревший кеш, неверные итоги в объекте); три места правки при смене формулы.  
**Исправление**: единый источник истины: `def compute_plate_totals(plates: List[Plate]) -> Totals` — использовать везде.

### Безопасность

**[S1] Глобали между сессиями / смешивание данных**  
**Место**: глобали уровня модуля `kp_db`, `prays_by_plate`, `plate_totals_cache`  
**Суть**: глобали переживают запросы/пользователей в веб-контексте; нет изоляции сессии.  
**Влияние**: расчёты заказа одного пользователя просачиваются к другому. Высокий риск приватности; потенциально GDPR, PCI.  
**Исправление**:
1. Область всех данных заказа — локально для запроса или для заказа
2. В FastAPI: `Depends()` с контекстом на запрос
3. Ноль персистентных глобалей для данных заказа (только неизменяемый конфиг)

**[S2] Проглатывание ошибок `fill_plate_nomenclature_cache()` после частичного обновления глобалей**  
**Место**: вызывающий `apply_to_globals()` или обработчик исключений  
**Суть**: при сбое `fill_plate_nomenclature_cache()` выполнение продолжается как при валидном кеше; исключение тихо логируется/игнорируется.  
**Влияние**: оптимизатор опирается на устаревшую или неполную номенклатуру; неверные подписи плит, стоимости; пользователь не видит ошибку.  
**Исправление**:
1. Пробрасывать исключение, не глотать
2. Явная транзакция: все обновления успешны или откат
3. Лог с контекстом: заказ, пользователь, шаги восстановления

### Качество кода

**[Q1] Хрупкость `from_dict` / `_parse_load_key`**  
**Место**: `from_dict()` и `_parse_load_key()`  
**Суть**: `KeyError` при отличной схеме; коэрция float/int неявна; нет лимитов глубины/размера.  
**Влияние**: падения на вариативном вводе; риск DoS на больших payload.  
**Исправление**: Pydantic v2, явные типы, лимиты, понятные сообщения об ошибках.

**[Q2] Острые края `KeyError` в `from_orders_2d`**  
**Место**: метод `from_orders_2d()`  
**Суть**: предполагается структура 2D-массива без проверки границ.  
**Исправление**: валидация формы; индексы строк/колонок в ошибке; режим skip-and-log; тесты на пустые строки и лишние колонки.

## Интеграция с «картиной по заказу» и ILP

**Блокер**: A1 и A2 (глобальная архитектура) должны быть сняты до расширения визуализации или оптимизации.

**После рефакторинга**:
1. Неизменяемый `OrderContext` проходит через ILP  
2. Солвер возвращает `ILPSolution` (назначения, стоимости, выполнимость)  
3. Визуализация потребляет `OrderContext` + `ILPSolution` → рендер «картины»  
4. Нет мутаций глобального состояния; результаты только append-only или версионируются
