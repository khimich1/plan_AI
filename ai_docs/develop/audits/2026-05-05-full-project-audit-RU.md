## Критические находки

### 🚨 Архитектура — A1: маршруты Offers API не подключены

**Где:** `app/api/v1/endpoints/offers.py`, `app/api/v1/router.py`

**Проблема:**  
Модуль эндпоинтов offers существует, но **не включён** в роутер API v1. При вызовах клиентами `/api/v1/offers/*` запросы завершаются ошибкой или 404 «молча», при этом приложение может считать маршруты активными.

**Последствия:**  
- Функциональность offers недоступна для API-клиентов
- Фронтенд/бот, вызывающие `/api/v1/offers`, получают ошибки без ясной диагностики
- Путаница при деплое: код есть, но не работает

**Исправление:**  
1. Импортировать роутер `offers` в `app/api/v1/router.py`
2. Подключить через APIRouter: `router.include_router(offers.router, prefix="/offers", tags=["offers"])`
3. Убедиться, что все эндпоинты видны в документации OpenAPI
4. Добавить интеграционные тесты против регрессии

**Статус:** ⏳ требует немедленного исправления

---

### 🚨 Безопасность — S1: значение по умолчанию для APP_SECRET_KEY (заглушка)

**Где:** `app/core/settings.py`, подпись сессий в `app/security/session.py`

**Проблема:**  
`APP_SECRET_KEY` по умолчанию равен заглушке (например, `"your-secret-key-change-in-production"`). Cookie сессий подписываются этим секретом. Если в окружении его не переопределить, **злоумышленник может подделать валидные cookie сессии** и выдать себя за любого пользователя.

**Последствия:**  
- Перехват сессии и impersonation
- Повышение привилегий до учёток администратора
- Полный обход аутентификации в продакшене

**Исправление:**  
1. **Безопасное поведение по умолчанию:** при отсутствии ключа генерировать криптостойкий случайный ключ при старте или завершать запуск с понятной ошибкой
2. **Переменная окружения:** `APP_SECRET_KEY` должен быть явно задан в `.env` (или при старте выбрасывать `ValueError`)
3. **Проверка:** при старте в `main.py` убедиться, что длина ключа ≥ 32 байта и это не заглушка
4. **Документация:** явные инструкции в README и гайде по деплою
5. **Ротация:** план ротации секрета для развёрнутых инстансов

**Статус:** ⏳ **БЛОКЕР** — исправить до любого публичного деплоя

---

### 🚨 Качество кода — Q1: голый `except:` проглатывает ошибки расчёта количества резов

**Где:** `core/optimization.py`, строки ~2301–2330

**Проблема:**  
Обработчик использует голый `except:`, который ловит **все исключения** (включая `KeyboardInterrupt`, `SystemExit`) и молча продолжает выполнение. Контекст ошибки теряется — невозможно понять, почему падают операции с количеством резов.

**Последствия:**  
- Ошибки оптимизации в проде проходят незамеченными
- Расчёты себестоимости/плана могут быть неверными без сигнала
- Отладка блокируется: нет логов, нет трассировок
- Сложно отличить намеренный пропуск от реального сбоя

**Исправление:**  
1. **Заменить голый `except:`** на конкретные исключения: `except (ValueError, KeyError, IndexError) as e:`
2. **Логировать:** `logger.error(f"Failed to process cut quantity: {e}", exc_info=True)`
3. **Проброс или явная обработка:** либо пробрасывать исключение дальше, либо давать fallback с предупреждением
4. **Юнит-тесты** на то, что ошибка корректно логируется/пробрасывается

**Статус:** ⏳ высокий риск в продакшене

---

### 🚨 Качество кода — Q2: молчаливое подавление исключений в пайплайне агента/планирования

**Где:** `production_planning_service.py` и связанные файлы, паттерн debug-ebb546 в `core/`, `bot/`, `app/`

**Проблема:**  
Повсеместные блоки `except Exception: pass` молча гасят ошибки при выполнении агента и оптимизации. Отладочное логирование неполное. Сбои в цикле планирования или оптимизации не оставляют следов.

**Последствия:**  
- Задачи планирования в проде падают без видимости для пользователя
- Нет механизма восстановления после ошибки
- Невозможно диагностировать, почему пользователь видит «план недоступен»
- Каскадные сбои в сценариях бота и API

**Исправление:**  
1. **Глобальный проход:** найти все `except Exception: pass` и заменить на узкую обработку
2. **Структурированное логирование:** `logger.exception(f"Plan generation failed: {context}")` с контекстом
3. **Ответы пользователю:** явные ошибки (500 с диагностическим ID) вместо молчаливых сбоев
4. **Тесты:** покрыть ошибочные ветки, чтобы они логировались и были заметны

**Статус:** ⏳ требует немедленного рефакторинга

## Находки высокого приоритета

### Архитектура

**A2: инвертированная зависимость — `core/db_config.py` → `app.core.settings`**  
Слой конфигурации БД зависит от настроек приложения; направление зависимостей нужно развернуть.  
**Исправление:** вынести настройки из слоя app; сделать core независимым.

**A3: `get_current_user` загружает всех пользователей на каждый запрос**  
`app/dependencies/auth.py` подтягивает полный список пользователей для проверки текущего; O(n) на запрос.  
**Исправление:** прямой lookup по `user_id`; кэш; при необходимости оптимизация async-запросов.

**A4: «Божественный» модуль — `app/web/router.py` (~1000 строк)**  
Один файл совмещает маршрутизацию, бизнес-логику, обработку ошибок; изолированно не протестировать.  
**Исправление:** разбить на группы маршрутов (auth, orders, offers); логику — в сервисы.

**A5: двойная доменная модель — `PlateOrder` в app и в `core.config_and_data`**  
Модель заказа дублируется между слоями; риск расхождений.  
**Исправление:** один источник истины; явное отображение или общая схема.

### Безопасность

**S2: флаг безопасности cookie сессии**  
`secure=False` в API auth и веб-логине; cookie могут передаваться по HTTP.  
**Исправление:** `secure=True` (только HTTPS); `SameSite=Lax` или `Strict`.

**S3: нет rate limiting на эндпоинтах входа**  
Не блокируются brute-force; нет блокировки учётки.  
**Исправление:** лимитер (например, slowapi); счётчик неудачных попыток; блок после N неудач за окно времени.

**S4: рычаг DoS — полный список пользователей на каждый аутентифицированный запрос** (то же, что A3)  
**Исправление:** см. A3 выше.

**S5: у менеджеров нет ограничения данных «своими» записями**  
Горизонтальное повышение привилегий: менеджер видит данные других менеджеров.  
**Исправление:** фильтрация в запросах; проверка `user_id` в допустимом множестве для текущего пользователя.

**S6: загруженные изображения читаются без лимита размера**  
`commercial.py`, веб-роутер загружают изображения целиком в память; риск DoS.  
**Исправление:** `MAX_IMAGE_SIZE`; потоковая обработка; валидация до полной загрузки.

### Качество кода

**Q3–Q4: `build_plan` и `_run_optimization_and_split` — огромные методы и глубокая вложенность**  
Высокая цикломатическая сложность; трудно следить за логикой.  
**Исправление:** вынести подфункции; глубина вложенности ≤ 3.

**Q5: дублирование `format_phone`**  
В `core/commercial_offer.py` и `commercial_offer_xlsx.py`; риск расхождения логики.  
**Исправление:** общий модуль, например `app/utils/phone.py`; один источник.

**Q6: в обработчиках бота повсеместно голый `except:`**  
Telegram-обработчики молчат при ошибке; пользователь не получает обратной связи.  
**Исправление:** логирование; сообщение пользователю (например, «Попробуйте позже»).

**Q7: `day_documents_service` импортирует приватные хелперы из `day_view_service`**  
Жёсткая связность; нарушение инкапсуляции.  
**Исправление:** общий утилитарный модуль; только публичные API.

**Q8: нет тестов для `offers_service`, `day_documents_service`; поверхностное покрытие**  
Покрытие критичных сервисов низкое.  
**Исправление:** юнит- и интеграционные тесты; целевое покрытие по договорённости (например, ~80%).

**Q9: вызовы `print` в `core/optimization.py`**  
Отладочный вывод засоряет потоки логов; нужен структурированный logging.  
**Исправление:** заменить на `logger.debug(...)`.

### Архитектура

**A6: «Божественный» модуль `core/config_and_data.py`**  
1000+ строк; смешаны конфиг, модели данных, хелперы.  
**Исправление:** разнести на `models/`, `config/`, `helpers/`.

**A7: раздутый `production_planning_service.py`**  
Сервис совмещает планирование, оптимизацию, форматирование; нарушение единственной ответственности.  
**Исправление:** вынести оптимизацию; отдельный сервис.

**A8: жёсткая связь Bot → App**  
Слой бота напрямую использует модели и сервисы app.  
**Исправление:** доменно-агностичные DTO; слабая связь через шину сообщений или события.

**A9: смешанные паттерны доступа к данным**  
Запросы через sqlite3 рядом со слоем репозиториев; непоследовательность.  
**Исправление:** весь доступ к БД через репозитории; аудит прямых вызовов sqlite3.

### Безопасность

**S7: CORS `allow_headers="*"` вместе с credentials**  
Слишком широко; лучше ограничить список заголовков.  
**Исправление:** например `allow_headers=["Content-Type", "Authorization"]`; задокументировать политику CORS.

**S8: утечка деталей через `detail=str(exc)`**  
Сообщения исключений уходят клиенту; возможна утечка деталей реализации.  
**Исправление:** логировать на сервере; клиенту — обобщённая ошибка.

**S9: нет security-заголовков для HTML**  
Нет CSP, X-Frame-Options, X-Content-Type-Options.  
**Исправление:** middleware с заголовками; ориентир — OWASP.

**S10: путаница с интеграцией роутера offers**  
Несколько путей кода ссылаются на `/api/v1/offers`; неочевиден канонический путь.  
**Исправление:** исправить A1; аудит всех ссылок; тесты.

### Качество кода

**Q10: «Суп» из `dict[str, Any]`**  
Много нетипизированных словарей; теряется типобезопасность.  
**Исправление:** Pydantic-модели; для структурированных dict — TypedDict.

**Q11: «Божественные» модули в `core/`, `bot/`**  
Несколько файлов по 500–1000 строк со смешанными обязанностями.  
**Исправление:** модульный рефакторинг; вынос сервисов, хелперов, моделей.

**Q12: глобальное состояние оптимизации**  
Изменяемое глобальное состояние в пайплайне оптимизации; риск при конкурентности.  
**Исправление:** dependency injection; передача состояния аргументами функций.

**Q13: запах O(n²) в агрегации**  
Вложенные циклы в агрегирующих функциях; при росте данных производительность падает.  
**Исправление:** профилирование; groupby/reduce; тесты на производительность.

**Q14: смесь legacy- и современной типизации**  
Где-то `typing.Dict`/`List`, где-то PEP 604 `| None`.  
**Исправление:** унифицировать на PEP 604 (Python 3.10+).

**Q15: заглушки TODO в экспорте бота**  
Неполные блоки кода.  
**Исправление:** реализовать или явно задокументировать временность.

**Q16: в `tests/` смешаны эксперименты**  
Экспериментальный код рядом с боевыми тестами.  
**Исправление:** вынести в `tests/experimental/`; описать назначение.

## Методология аудита

- **Архитектура:** структура модулей, зависимости, границы сервисов, согласованность доменной модели
- **Безопасность:** аутентификация, авторизация, валидация входа, обработка ошибок, чувствительные данные
- **Качество кода:** сложность, покрытие тестами, исключения, типизация, поддерживаемость
- **Данные:** исходники, тесты, устойчивые паттерны в коде

**Оговорки:**
- Динамическое поведение (рантайм-конфиг, переменные окружения) оценено не полностью
- Безопасность фронтенда/UI не в фокусе данного отчёта
- Бенчмарки производительности не включены (используйте профилирование или APM)

## Заключение

В аудите зафиксированы **42 отдельные находки** по архитектуре, безопасности и качеству кода. **4 критические проблемы необходимо устранить** до продакшена или расширения пользовательской базы.

Для системного рефакторинга архитектуры:  
**[`/refactor`]** — оркестрация рефакторинга, разбиение крупных модулей, улучшение паттернов проектирования  
**[`/implement`]** — исправления багов, подключение маршрутов, усиление безопасности, рост покрытия тестами
