## Executive Summary

Аудит охватывает слой оптимизации резки, монолитный модуль конфигурации/данных и пакет построения последовательности раскладки. Доминируют архитектурные риски: «god»-модули, тесная связь оптимизации с `cfg` вместо узких портов, дублирование правил кода нагрузки. В безопасности критических находок в scope нет; высокий риск связан с неконтролируемыми путями ФС и широким чтением/записью при недоверенном вызывающем коде. Качество кода страдает от побочных эффектов в горячих путях, слабой типизации оркестратора и рассеянной семантики нормализации load code.

## Critical

### Architecture

- **[A1]** `core/optimization/geometry.py` (~2.8k строк) — god module: таблицы конфигурации, генерация опций 1D/2D, фильтрация, вспомогательные функции в одном узле; нарушены SRP, тестируемость и локальность регрессий.

  - **Impact:** любое изменение затрагивает несвязанные сценарии; высокая стоимость ревью и регрессионного тестирования; ошибки сложно локализовать.

  - **Fix hints:** декомпозиция по поддоменам (конфиг/таблицы vs генерация vs фильтры); выделение чистых функций и портов для данных; покрытие контрактными/параметризованными тестами по слоям.

## High

### Architecture

- **[A2]** `viz_modules/layout_sequence/builder.py` (~4.2k), `from_plan.py` (~3.4k) — god modules: оркестрация, ветвления, логика усиления/сепараторов, NDJSON-трейсинг в чрезмерно крупных файлах.

  - **Impact:** сложность сопровождения; высокий риск регрессий при точечных правках; затруднён параллельный рефакторинг.

  - **Fix hints:** выделение подмодулей (трасса, усиление, построение шагов); явные границы API между этапами; сокращение смешения I/O и доменной логики.

- **[A3]** `core/config_and_data.py` — SRP/слои: реэкспорты, изменяемый runtime заказа (`__getattr__` → thread-local), связывание парсера, доменные хелперы, буферы метаданных — отсутствует узкая граница модуля.

  - **Impact:** непредсказуемые точки расширения; сложно подменять зависимости в тестах; рост связности всего приложения с одним файлом.

  - **Fix hints:** разнести конфиг, runtime-состояние заказа, парсинг и доменные утилиты по пакетам с явными публичными поверхностями.

- **[A4]** `core/optimization/*` импортирует полный `cfg` из `config_and_data` (`geometry.py`, `ilp_model.py`, `legacy_width_plan.py`, `optimize_2d/extract_cuts.py`, `finalize.py`) — тесная связь вместо `PlateOrderDataPort`; страдают DIP и юнит-тестирование.

  - **Impact:** тесты тянут монолит конфигурации; сложно подставить фейки; изменения в `cfg` ломают оптимизацию широким фронтом.

  - **Fix hints:** ввести порты/DTO для цен, нагрузок, метаданных плит; инъекция зависимостей с узкими интерфейсами.

- **[A5]** Дублированная логика `get_load_code_for_plate`: `layout_runtime_snapshot` vs `config_and_data` — риск расхождения поведения.

  - **Impact:** тихий дрейф бизнес-правил; расхождение продакшена и снапшотов/визуализации.

  - **Fix hints:** единый источник истины + общий хелпер или контрактный тест на паритет.

### Security

- **[S1]** `LayoutSequenceDeps` / `build_layout_sequence` принимают произвольные пути ФС; SQLite/усиление + `append_json_line` могут широко читать/писать — при недоверенном вызывающем коде возможны path traversal и произвольная запись.

  - **Impact:** компрометация данных на диске, запись вне ожидаемых каталогов, чтение чужих БД при ошибочной или злонамеренной конфигурации.

  - **Fix hints:** валидация и канонизация путей (базовый каталог, `resolve`, запрет `..`); allowlist корней; разделение доверенной конфигурации и пользовательского ввода; аудит вызовов API.

### Code Quality

- **[Q1]** `ilp_model`: `primary_options` мутирует dict `opt` на месте (`load_code`) — риск побочных эффектов ниже по стеку.

  - **Impact:** неявное изменение конфигурации; трудноуловимые баги при повторном использовании структур.

  - **Fix hints:** копирование перед мутацией, явный возврат нового dict, неизменяемые снимки на границах.

- **[Q2]** `layout_runtime_snapshot` дублирует алгоритм `get_load_code_for_plate` — нужен общий хелпер или контрактный тест.

  - **Impact:** дублирование согласовано с [A5]; регрессии при правках в одном месте.

  - **Fix hints:** консолидация реализации; snapshot как тонкая обёртка над каноническим API.

## Medium

### Architecture

- **[A6]** `ilp_model` → `core.price_db.get_price` — оптимизация связана с I/O БД.

  - **Impact:** сложность изоляции в тестах; нежелательные побочные эффекты и латентность в горячем пути.

  - **Fix hints:** абстракция ценообразования (порт + кэш/предзагрузка для batch).

- **[A7]** Оркестратор использует `print` вместо логгера.

  - **Impact:** нет уровней/корреляции; шум в stdout в проде; сложнее операционная наблюдаемость.

  - **Fix hints:** структурированное логирование с контекстом запроса/плана.

- **[A8]** `optimization/__init__.py` подменяет класс в `sys.modules` для `OPT_*` — нетипичная глобальная «магия».

  - **Impact:** неочевидный контракт для читателей и инструментов; риск ошибок при альтернативных точках входа.

  - **Fix hints:** явный объект контекста или фасад без подмены модуля.

- **[A9]** `_implementation/__all__` реэкспортирует много символов с подчёркиванием — «протекающий» публичный контракт.

  - **Impact:** пользователи завязываются на внутренности; сложнее семантическое версионирование.

  - **Fix hints:** сузить публичный API; префикс `_` оставить только для приватного слоя.

- **[A10]** В `layout_sequence`: `append_json_line` + `try/except: pass` на путях — конкуренция за ФС; вопросы масштабируемости.

  - **Impact:** потеря диагностических сигналов; деградация под нагрузкой при множественной записи.

  - **Fix hints:** очередь/единый writer, backoff, явная политика ошибок, опциональность трассы.

- **[A11]** `make_plate_name`: синхронные отладочные записи на горячем пути.

  - **Impact:** латентность и блокировки I/O в критическом потоке.

  - **Fix hints:** флаг отладки, асинхронный буфер или вынос за пределы hot path.

### Security

- **[S2]** Часть путей `optimize_2d` пишет NDJSON без ворот `OPT_DEBUG_LOG`; телеметрия «всегда включена»; `_DEBUG_LOG_7E420E` под `core/`.

  - **Impact:** рост артефактов на диске; нежелательное логирование в проде.

  - **Fix hints:** единый флаг/политика; согласовать пути с `debug_logs`; документировать включение.

- **[S3]** `config_and_data.make_plate_name`: безусловный NDJSON на некоторых ветках.

  - **Impact:** утечка операционных данных и шум I/O.

  - **Fix hints:** gated logging; уровни; редокция полей.

- **[S4]** `OPT_DEBUG_LOG` / `order_dispatch` логирует `kp_id`/`plate_name` в файлы — требуется классификация/редокция/ACL.

  - **Impact:** чувствительные атрибуты заказа на диске и в бэкапах.

  - **Fix hints:** политика данных, маскирование, ограничение доступа к каталогам логов.

### Code Quality

- **[Q3]** Публичный `__all__` в `_implementation` включает много `_*` символов (согласуется с [A9]).

  - **Impact:** размытие границ публичного API.

  - **Fix hints:** явный список поддерживаемых экспортов.

- **[Q4]** Оркестратор типизирован широкими `dict`/`Any` — слабая граница типов.

  - **Impact:** ошибки обнаруживаются поздно; хуже поддержка IDE.

  - **Fix hints:** Pydantic/dataclass для конфигурации и промежуточных структур.

- **[Q5]** `prep_solve`: значение `load_code` по умолчанию `800`, связано с «магией» `normalize_load_code` — скрытый контракт.

  - **Impact:** неочевидное поведение для новых разработчиков; риск несогласованности с доменом.

  - **Fix hints:** именованные константы; документированный default; явная валидация.

- **[Q6]** Нормализация load code размазана (`helpers.canonical_load_code`, домен, `config_and_data`) — риск несогласованной семантики.

  - **Impact:** разное поведение в разных слоях; трудно отлаживать.

  - **Fix hints:** единая каноническая функция и таблица допустимых значений.

- **[Q7]** `from_plan`: `_build_sequence_from_plan_impl` слишком монолитен — сложно инкрементально тестировать.

  - **Impact:** высокая стоимость изменений; фрагментарное покрытие тестами.

  - **Fix hints:** разбиение на этапы с чистыми входами/выходами; golden-тесты на подэтапы.

## Следующие шаги (без remediation в этом цикле)

1. **Архитектура:** запланировать декомпозицию `geometry.py` и файлов `layout_sequence` (builder/from_plan) с сохранением поведения; начать вынос портов из прямого `cfg` в оптимизации.

4. **Операционка:** заменить `print` на логгер в оркестраторе; согласовать отладочный I/O (`append_json_line`, hot path в `make_plate_name`) с политикой производительности.
