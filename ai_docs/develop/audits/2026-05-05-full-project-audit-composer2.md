## Critical Issues (fix immediately)

### [A1] Инвертированная зависимость `app/` → `bot.handlers.plan_manager`

**Категория**: Architecture  
**Локация**: слой `app/` (зависимость от Telegram-бота); затрагивают контуры вокруг планов: `plan_repository`, `production_planning_service`, `day_documents` и связанные вызовы.

**Impact**: нарушается направление зависимостей (веб/API не должен тянуть обработчики бота). Усложняются тестирование, деплой по слоям и замена канала (бот vs API). Риск скрытых побочных эффектов при изменении бота.

**Fix**: вынести общую доменную логику планов в нейтральный модуль (`core` или `app/domain` + сервисы), а `bot.handlers` оставить тонким адаптером. `app` должен зависеть только от абстракций репозитория/сервиса, а не от `bot.handlers`.

---

### [A2] `PlanRepository` как тонкая обёртка над состоянием бота — «фейковая» граница данных

**Категория**: Architecture  
**Локация**: репозиторий планов, связанный с JSON/FS и метаданными в `bot/data` (см. обсуждение в аудите архитектуры).

**Impact**: граница персистентности выглядит как репозиторий, фактически привязана к артефактам бота. Растёт связность, нет ясного контракта БД/API, сложнее масштабирование и консистентность при нескольких воркерах.

**Fix**: явно определить порт хранения планов (интерфейс), реализацию для файлов/БД отделить от бота; документировать источник истины и миграцию данных.

---

### [S1] Дефолтный `APP_SECRET_KEY` — риск подделки сессии

**Категория**: Security  
**Локация**: `app/core/settings.py` (секрет приложения по умолчанию).

**Impact**: при незаданном или известном секрете злоумышленник может подписать сессионные cookie/токены (в зависимости от использования), что ведёт к **полной компрометации сессий** в типичной схеме.

**Fix**: в production **запретить** старт без явного секрета (fail-fast), генерировать криптостойкий ключ в деплое, ротировать секреты; убедиться, что дефолт не попадает в прод-конфиги.

## High Priority Issues (fix soon)

### [A3] Загрузка всех пользователей на каждый запрос

**Категория**: Architecture / Performance  
**Локация**: `app/dependencies/auth.py`

**Impact**: линейный рост задержки и памяти с числом пользователей; потенциальный узел нагрузки и удобная цель для злоупотреблений при большом каталоге.

**Fix**: кэш с инвалидацией, выборка по идентификатору, индексированное хранилище; для JWT — верификация без полного сканирования списка.

---

### [A4] Глобальное / thread-local состояние оптимизации

**Категория**: Architecture / Concurrency  
**Локация**: контур `core/optimization`, сервисы планирования/оптимизации

**Impact**: при параллельных запросах в одном процессе возможны гонки и «протечки» контекста между вызовами; непредсказуемость в multi-worker окружении.

**Fix**: явная передача контекста (`Context` объект), изоляция на вызов, отказ от неявного глобального состояния для запрос-зависимых данных.

---

### [A5] Мутация `sys.modules` в `core/optimization/__init__.py`

**Категория**: Architecture  
**Локация**: `core/optimization/__init__.py`

**Impact**: неочевидное поведение для импорта, сложная отладка, риск конфликтов с тестами и ленивой загрузкой.

**Fix**: нормальный пакетный layout без подмены модулей в runtime; при необходимости совместимости — явный facade и deprecation путь.

---

### [S2] Cookie `secure=False`

**Категория**: Security  
**Локация**: настройки сессий / cookie (веб-слой)

**Impact**: cookie могут уходить по незашифрованному HTTP — риск перехвата в сети.

**Fix**: в production `Secure=True`, HTTPS-only, корректные флаги `HttpOnly`/`SameSite` по модели угроз.

---

### [S3] Нет rate limiting на логин

**Категория**: Security  
**Локация**: эндпоинты аутентификации

**Impact**: перебор паролей и DoS по учётным записям без дополнительных затрат.

**Fix**: лимиты по IP/аккаунту, задержки, CAPTCHA при пороге, мониторинг неудачных попыток.

---

### [S4] Поверхность CSRF (legacy-формы)

**Категория**: Security  
**Локация**: legacy HTML-формы vs SPA

**Impact**: классические CSRF-атаки на state-changing запросы без токена/SameSite.

**Fix**: CSRF-токены для cookie-сессий, строгий SameSite, поэтапный отказ от небезопасных форм.

---

### [S5] In-memory OCR upload limiter небезопасен при нескольких воркерах

**Категория**: Security / Availability  
**Локация**: загрузка/OCR

**Impact**: каждый воркер держит свой счётчик — лимит обходится и нагрузка непредсказуема.

**Fix**: Redis/общий store, лимиты на reverse-proxy, квоты по пользователю.

---

### [Q1] Дублирование `commercial_offer` vs `commercial_offer_xlsx` (VAT, `format_phone`)

**Категория**: Code Quality / DRY  
**Локация**: `core/commercial_offer.py`, `core/commercial_offer_xlsx.py`

**Impact**: расхождение бизнес-правил между каналами, ошибки при правке только одного места.

**Fix**: единый модуль форматирования/налоговой логики, общие чистые функции, тесты на оба пути.
