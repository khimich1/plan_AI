## Executive Summary

Модуль несёт слишком много ролей (константы, преобразования, `PlateOrder`, runtime, парсинг текста, хелперы имён/цен, метаданные), что усложняет сопровождение и тестирование. Выявлены скрытая связность с инфраструктурой (кэш номенклатуры при глобальных обновлениях), нетипичный приём подмены класса модуля и побочные эффекты I/O в путях, ожидаемых как «чистые» вычисления. На стороне безопасности **критических** и **высоких** рисков по итогам этапа Security не зафиксировано; основные риски — отсутствие лимитов на объём входных структур/текста и потенциальная утечка деталей через логи/отладочные записи. Качество кода страдает от высокой цикломатической сложности ключевых функций, дублирования правил и «тихих» деградаций при ошибках парсинга.

**Критические (Critical) находки по всем трём направлениям: не обнаружены.**

## Находки по уровням (с рекомендациями)

### Critical

**Не выявлено** (Architecture, Security, Code Quality).

### High

**Архитектура**

- **God-модуль, нарушение SRP:** в одном месте смешаны константы, преобразования, `PlateOrder`, runtime, парсинг текста, хелперы имён/цен, метаданные.  
  **Рекомендация:** разнести по слоям: `domain/plate_order.py`, `parsing/plate_lists.py`, `config/constants.py`, `runtime/binding.py`; оставить в «тонком» модуле только сборку/реэкспорт при необходимости.

- **Скрытая связность:** вызовы `fill_plate_nomenclature_cache` внутри `apply_to_globals` и `set_plate_lists_from_text`.  
  **Рекомендация:** явная инъекция зависимости (callback/сервис) или событие «после обновления списков»; юнит-тесты без глобального кэша.

- **Нетипичный API модуля:** `sys.modules[__name__].__class__ = _ConfigDataModule`.  
  **Рекомендация:** заменить на обычный объект настроек/`dataclass` + фабрика; избегать магии импорта для упрощаемости статического анализа.

- **Побочный file I/O в `make_plate_name`.**  
  **Рекомендация:** вынести отладку в опциональный логгер/trace; в продакшен-пути отключать запись в файл по умолчанию.

**Качество кода**

- **`set_plate_lists_from_text` + `add_items`:** очень высокая сложность и ветвистость.  
  **Рекомендация:** декомпозиция на шаги (нормализация строк, разбор блоков, применение правил ширин), таблица стратегий или конвейер с явными DTO.

- **Дублирование правил ширин** в двух местах (в т.ч. пересекается с архитектурной находкой).  
  **Рекомендация:** единая функция/класс политики ширин с тестами на матрицу случаев.

- **`make_plate_name`:** смешение вычисления и побочных эффектов.  
  **Рекомендация:** чистая функция имени + отдельный адаптер для диагностики.

- **`apply_to_globals`:** подавление деталей исключений широким `except`.  
  **Рекомендация:** узкие типы исключений, цепочка `raise ... from e`, структурированное логирование без потери причины.

### Medium

**Архитектура**

- **Размытый контракт `canonical_plate_key` vs другие ключи `round(..., 3)`.**  
  **Рекомендация:** задокументировать единый контракт ключа; обернуть округление в одну функцию; тесты на граничные float.

- **Высокая сложность `set_plate_lists_from_text`.**  
  **Рекомендация:** см. High — целенаправленный рефакторинг с сохранением поведения по золотым примерам.

- **Дублирование правил ширин `add_items` vs `PlateOrder.from_orders_2d`.**  
  **Рекомендация:** DRY через общий модуль правил.

- **Смешение доменных правил и политики отображения/ценообразования.**  
  **Рекомендация:** разделить «что есть заказ» и «как считаем/показываем цену»; зависимость домена на абстракции прайсинга.

**Безопасность**

- **`make_plate_name` пишет в debug-файл при вызовах:** риск роста логов, утечек содержимого, нагрузки на диск.  
  **Рекомендация:** лимиты размера/ротация, уровни логирования, запрет по умолчанию вне debug.

- **Нет лимита на размер `user_text`/число строк в `set_plate_lists_from_text` (DoS-риск).**  
  **Рекомендация:** константы `MAX_TEXT_LEN` / `MAX_LINES`, ранний отказ с понятной ошибкой.

- **`from_dict` без лимитов размера структур (DoS-риск).**  
  **Рекомендация:** ограничение глубины/числа элементов или валидация на входе схемой (Pydantic) с лимитами.

- **Логирование текста исключений может раскрыть детали окружения.**  
  **Рекомендация:** пользовательские сообщения обезличить; в лог — короткий код + `exc_info` только на доверенном уровне.

**Качество кода**

- **Ручное копирование полей** в `to_dict`/`from_dict`/`get_current_plate_order`/`apply_to_globals`.  
  **Рекомендация:** `dataclasses`/`model_copy`, общий маппер или генерация списка полей.

- **Нестрогая типизация (`Optional`/`tuple`/`set` без уточнений).**  
  **Рекомендация:** `TypedDict`/явные `NewType` для ключей, `Sequence`/`frozenset` где уместно.

- **Тихие возвраты `0.0` при ошибках парсинга.**  
  **Рекомендация:** `Result`/исключение парсинга или явный маркер ошибки, чтобы не маскировать баги.

- **Лишняя ветка `parsed`/`continue`.**  
  **Рекомендация:** упростить поток, покрыть тестом ветвления.

- **Потенциально недостижимая ветка `n is None`.**  
  **Рекомендация:** удалить или доказать достижимость тестом; статический анализ.

  **Рекомендация:** централизовать политику округления (см. Medium про ключи).

## Практичные направления: рефакторинг и hardening

1. **Разрезать модуль** по ответственности и убрать «магию» `sys.modules`, сохранив обратную совместимость через тонкий фасад и постепенный deprecation.
2. **Ввести лимиты входа** для текстового парсинга и `from_dict`; единая валидация (размер, глубина, число элементов).
3. **Убрать неявные побочные эффекты** из вычислительных функций; кэш номенклатуры вызывать через явный контракт после успешного обновления состояния.
4. **Один источник правды** для ширин и округлений + регрессионные тесты на парсер и сериализацию.
5. **Политика логов:** не писать сырой пользовательский ввод и полные тексты исключений в пользовательские каналы; ротация/лимиты для любых debug-файлов.
6. **Обработка ошибок:** отказ от широких `except` на границах публичного API; сохранение cause chain для диагностики.
