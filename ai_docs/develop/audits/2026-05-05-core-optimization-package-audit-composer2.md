## Критические замечания (устранять в первую очередь)

### [A1] Star-import, замена `sys.modules` и `_OptimizationModule` для перехвата `OPT_*`
**Категория:** Архитектура  
**Где:** `core/optimization/__init__.py`  
**Почему это важно:** непрозрачный публичный контракт пакета, тяжёлые побочные эффекты при импорте, сложность отладки и тестирования, риск неожиданного поведения при обновлении Python/инструментов.  
**Направление исправления:** явный публичный API без подмены модуля; конфигурация через объекты/контекст вместо перехвата атрибутов модуля.

## Высокий приоритет (исправить в ближайшем цикле)

### Архитектура

- **[A2]** `_implementation.py` — «god module» порядка ~1700 строк, нарушение SRP, высокая связность изменений.  
- **[A3]** Циклическая зависимость `orchestrator` ↔ `implementation` через ленивый импорт — хрупкая инициализация и риск порядка импорта.  
- **[A4]** `_optimize_2d_with_lengths` — чрезмерно большая одна функция; сложность сопровождения и тестирования.  
- **[A5]** `ilp_model.py` зависит от `core/price_db` — смешение доменной логики оптимизации с инфраструктурой цен.  
- **[A6]** Ветка 1D с захардкоженными `plate_price` / `long_cut_cost` при том, что 2D опирается на цены из БД — расхождение модели стоимости и риск неконсистентных результатов.

### Безопасность

- **[S1]** В `validation.py` нет верхней границы на `qty` / суммарный спрос — риск DoS через построение чрезмерно больших ILP-моделей.  
- **[S2]** Сообщения `ValueError` при валидации могут утекать клиенту как ответ **500**, если не сопоставлены с контролируемыми HTTP-ошибками — информационная утечка и плохой UX.

### Качество кода

- **[Q1]** В `_implementation.py` при извлечении результатов 1D — голый `except:` (проглатывание ошибок).  
- **[Q2]** `print` вместо `logging` в `orchestrator`.  
- **[Q3]** Монолитная сложность (согласовано с [A2]/[A4]).  
- **[Q4]** Несоответствие описания в docstring валидации фактическому поведению с `opt_error` в контракте результата.

## Средний приоритет (запланировать на спринт)

### Безопасность

- **[S3]** Отладочные логи могут содержать `kp_id`, `plate_name` (потенциально PII).  
- **[S4]** Ad-hoc запись в `core/debug-7e420e.log`.  
- **[S5]** Логирование в `price_db` на каждый `get_price` — шум и возможная утечка контекста в логах.  
- **[S6]** Вывод в stdout (`print`).  
- **[S7]** PuLP CBC как подпроцесс + тяжёлые модели (усиливает [S1]).

### Качество кода

- **[Q5]** Дублирующиеся участки agent log regions.  
- **[Q6]** Сложность `order_dispatch`; тестовое покрытие скудное.  
- **[Q7]** У `ilp_model` нет прямых модульных тестов.  
- **[Q8]** Слабая типизация.  
- **[Q9]** `_canonical_length` возвращает `0.0` молча.  
- **[Q10]** `optimize_tracks` возможно не используется.  
- **[Q11]** Неиспользуемый импорт `optimize_tracks`.  
- **[Q12]** `__import__` в отладочных блоках.
