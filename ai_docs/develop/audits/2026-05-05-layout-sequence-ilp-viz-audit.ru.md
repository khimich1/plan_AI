## Критические проблемы (требуют действий)

### [A1] Данные запроса в глобалях процесса

**Серьёзность:** Критическая  
**Категория:** Архитектура  
**Место:** `core/config_and_data.py`, `viz_modules/layout_sequence.py`  

**Влияние:**  
Глобальные переменные (`OPT_CASCADING_PLAN`, `OPT_PLAN`, `OPT_ORDERS` и т.д.) хранят состояние на запрос без изоляции. В сценариях нескольких воркеров или параллельных тестов данные одного запроса портят другой. Не потокобезопасно; нет семантики greenlet. Нарушает контракт области запроса.

**Текущий шаблон кода:**
```python
# Глобали модуля (опасно при конкуренции)
OPT_CASCADING_PLAN = None
OPT_PLAN = None
OPT_ORDERS = None

def build_layout_sequence():
    global OPT_PLAN
    # неявно: вызывающий должен заранее выставить OPT_PLAN, OPT_CASCADING_PLAN, OPT_ORDERS
```

**Исправление:**
1. Внедрять состояние конвейера через параметры функций или менеджер контекста.
2. Использовать thread-local или область запроса (FastAPI `Depends`, context vars, доменные контекст-объекты).
3. Убрать изменения на уровне модуля.
4. Добавить тесты конкурентного доступа.

**Трудозатраты:** Высокие  
**Приоритет:** P0

### [S1] Изоляция мультитенантности/воркеров нарушена через изменяемые глобали модуля

**Серьёзность:** Критическая  
**Категория:** Безопасность  
**Место:** `core/config_and_data.py`, `viz_modules/layout_sequence.py`  

**Влияние:**  
Если система обслуживает несколько арендаторов, клиентов или параллельные запросы в одном процессе, изменяемые глобали напрямую допускают утечку данных: план раскладки, заказы или результаты оптимизации одного арендатора становятся видимы другому. Вектор эксфильтрации в общей инфраструктуре.

**Сценарий:**
```python
# Воркер A выставляет глобальное состояние
OPT_PLAN = {"customer_id": 123, "sensitive_layout": ...}

# Переключение контекста: стартует воркер B
# Воркер B видит данные воркера A через глобали
```

**Исправление:**  
То же, что для A1 — внедрение зависимостей в области запроса. Провести аудит обработчиков на мутации глобального состояния.

**Трудозатраты:** Высокие  
**Приоритет:** P0 (безопасность)

### [A3] Фиктивная оптимизация портит состояние OPT_PLAN

**Серьёзность:** Высокая  
**Категория:** Архитектура  
**Место:** `core/visualization.py`, `visualize_plan()`  

**Влияние:**  
`visualize_plan()` вызывает `optimize_cuts_pulp()` с фиктивным заказом (`order_key="dummy"`), что очищает и снова заполняет `OPT_PLAN` как побочный эффект. Последующий код видит испорченное состояние. Нарушает прозрачность ссылок; скрывает неявную мутацию состояния.

**Текущий шаблон:**
```python
def visualize_plan():
    optimize_cuts_pulp("dummy")  # побочный эффект: мутирует OPT_PLAN глобально
    # OPT_PLAN теперь содержит игрушечную оптимизацию, а не реальные данные
```

**Исправление:**  
1. Сделать оптимизацию явной через возвращаемое значение, а не побочный эффект.
2. Добавить проверки на порчу состояния.
3. Рассмотреть отдельный `VisualizationContext`, не мутируемый оптимизацией.

**Трудозатраты:** Средние  
**Приоритет:** P1
