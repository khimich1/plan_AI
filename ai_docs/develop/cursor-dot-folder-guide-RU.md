# Папка `.cursor` в Cursor: назначение и практическое использование

Этот документ объясняет, зачем в проекте (и в Cursor вообще) используется каталог **`.cursor`**, какие в нём бывают сущности и **в каких случаях** их подключать. Описание ориентировано на ваш репозиторий `plan_wed_web`, но большая часть совпадает с общими правилами Cursor.

---

## 1. Зачем нужна `.cursor`

**`.cursor`** — это **локальная конфигурация проекта для ИИ и автоматизации в Cursor**: правила поведения ассистента, описание подагентов, пользовательские команды (slash-команды), навыки (skills), хуки и служебное рабочее пространство оркестрации.

| Цель | Что даёт |
|------|-----------|
| Единый стиль кода и процессов | Rules фиксируют стандарты без повторения их в каждом чате |
| Повторяемые сценарии | Commands + Skills описывают пошаговые workflow (аудит, рефакторинг, ревью) |
| Специализированные роли | Agents задают роль подагента (планировщик, ревьюер, worker и т.д.) |
| Интеграция с файловой системой | Hooks могут реагировать на события (редактирование, завершение подагента) |

Файлы из `.cursor` обычно **коммитят в git**, чтобы вся команда и CI/agents видели одинаковые правила.

---

## 2. Карта каталога в этом проекте

У вас в `.cursor` типичная «рабочая» раскладка:

| Путь | Назначение |
|------|------------|
| `.cursor/rules/` | Правила для модели (глобальные для проекта или подключаемые через `@`) |
| `.cursor/agents/` | Описания подагентов (роль, ограничения, когда вызывать) |
| `.cursor/commands/` | Slash-команды чата (`/audit`, `/review`, …) — короткий триггер + указание прочитать skill |
| `.cursor/skills/` | Подробные сценарии workflow (оркестрация, аудит, простая реализация и т.д.) |
| `.cursor/config.json` | Пути для планов/отчётов/аудитов под `ai_docs/` и настройки workspace |
| `.cursor/hooks.json` | Хуки Cursor (события после правок, остановки подагента и др.) |
| `.cursor/workspace/` | Рабочие файлы оркестрации (планы, прогресс); см. `.gitignore` внутри |

## 3. Rules (правила)

**Файлы:** `.cursor/rules/*.md`, `.cursor/rules/*.mdc`

### Зачем

- Закрепить **стандарты**: безопасность, тестирование, коммиты, документация, исследование кодовой базы.
- Ограничить или направить поведение модели **на уровне проекта**.

### Типичные режимы

- **Всегда применяются** — в frontmatter у `.mdc` может быть `alwaysApply: true` (если вы так настроите). Тогда контекст правила подмешивается без явного упоминания.
- **По запросу через `@`** — `alwaysApply: false`: правило **не болтается в каждом сообщении**, но вы явно подключаете его в чате через `@имя_файла_правила`, когда задача про эту область (например, только security или только исследование кода).

### Когда использовать какие правила

| Ситуация | Что подключать |
|----------|----------------|
| Любая задача с кодом в этом монорепо | Общие правила качества / архитектуры (если есть в `rules/`) |
| Нужно **описать код как есть**, без советов | `@codebase-researcher` (у вас это именно такой профиль) |
| Работа с секретами, auth, API | `@security` |
| Тесты, CI | `@testing` |
| Формат коммитов / PR | `@commit-messages`, `@git-workflow` |

**Практика:** не включайте «всё сразу» в `alwaysApply`, если контекстное окно забивается; держите узкие правила для `@`.

---

## 4. Agents (подагенты)

**Файлы:** `.cursor/agents/*.md`

### Зачем

Описание **роли исполнителя**, которого основной агент может вызвать через инструмент задач (например, `Task` с типом вроде `planner`, `reviewer`, `worker`). В файле задаются:

- имя и описание;
- поведение (например, planner **обязан** сохранять план в пути из `config.json`);
- ограничения (readonly, фоновый режим и т.д., если поддерживается вашей версией Cursor).

### Когда использовать

| Задача | Типичный агент |
|--------|----------------|
| Разбить большую фичу на шаги и сохранить план | `planner` |
| Написать или изменить код | `worker` |
| Проверить качество перед коммитом | `reviewer` / `senior-reviewer` |
| Разобрать падение тестов | `test-runner` |
| Дописать тесты | `test-writer` |
| Починить по отчёту | `debugger` |
| Аудит безопасности точечно | `security-auditor` |
| Обновить документацию по факту изменений | `documenter` |

Агенты **не заменяют** правила: правила задают *стандарты*, агенты — *кто и как действует* в многошаговом сценарии.

## 5. Commands (slash-команды)

**Файлы:** `.cursor/commands/*.md`

### Общая идея

Ввод **`/имя_команды`** в чате Cursor подгружает markdown из `.cursor/commands/<имя>.md`. Там обычно задано:

1. **Роль основного ассистента — только координатор**: сам он не анализирует код, не правит файлы и не гоняет тесты; каждый шаг выполняется **подагентом** через инструмент задач (`Task` и явный `subagent_type`).
2. **Обязательное чтение skill**: перед стартом координатор должен прочитать соответствующий `.cursor/skills/.../SKILL.md` и выполнить его шаги **без сокращений**.

Это нужно, чтобы процесс был **воспроизводимым**: один и тот же сценарий аудита или рефакторинга не зависел от «настроения» модели в конкретном чате.

### Сводная таблица команд проекта

| Команда | Skill | Суть цикла |
|---------|--------|------------|
| `/audit` | `audit-workflow` | Область → архитектура → безопасность → качество → сводный отчёт → (опционально) исправления по согласию |
| `/refactor` | `refactor-workflow` | Анализ (senior-reviewer) → рефакторинг → тесты/линтер → документация |
| `/review` | `review-workflow` | Ревью → при необходимости фиксы → проверка тестами |
| `/implement` | `simple-workflow` | Код → тесты → прогон → документация **без** плана и без полного цикла оркестрации |
| `/orchestrate` | `orchestration` | План (planner) → цикл по задачам: worker → test-writer → test-runner → reviewer → … → итоговые доки |

Ниже — подробности и **когда что запускать**.

---

### `/audit` — аудит здоровья проекта

- **Файл команды:** `.cursor/commands/audit.md`
- **Skill:** `.cursor/skills/audit-workflow/SKILL.md`

**Что делает процесс (упрощённо):**

1. Определяется **область** аудита (весь проект, каталог, файл или изменения относительно git).
2. Последовательно вызываются подагенты (каждый получает контекст предыдущего шага):
   - **senior-reviewer** — архитектура, слои, связность, масштабируемость;
   - **security-auditor** — auth, валидация, секреты, типичные веб-риски;
   - **reviewer** — качество кода, читаемость, ошибки;
   - **documenter** — **единый консолидированный отчёт** (часто с приоритетами Critical / High / …).
3. Фазы анализа по задумке skill — **только чтение и отчёт**; массовые правки кода — только если пользователь согласился на этап **remediation** и координатор маршрутизирует работу (например, через refactor или planner+worker).

**Примеры области (из skill):**

- `/audit` — типично основной каталог исходников проекта;
- `/audit путь/к/модулю/` — узкий модуль;
- `/audit путь/к/file.py` — один файл, глубже;
- `/audit --since main` или `--since HEAD~10` — только затронутые файлы из diff.

**Когда использовать:**

- Перед релизом или перед крупным рефакторингом.
- Онбординг в незнакомый репозиторий (картина рисков и долга).
- Периодический «снимок» качества (раз в спринт / квартал).
- После смены архитектуры — сравнить «до/после» новым аудитом в `ai_docs/develop/audits/` (пути заданы в `.cursor/config.json`).

**Когда не заменяет другие команды:** аудит не обязан править код; для точечного прекоммитного просмотра часто удобнее `/review`.

---

### `/refactor` — безопасный цикл рефакторинга

- **Файл команды:** `.cursor/commands/refactor.md`
- **Skill:** `.cursor/skills/refactor-workflow/SKILL.md`

**Что делает процесс:**

1. Задаётся **scope**: файл, каталог, формулировка цели или «что изменилось в git».
2. **Обязательная проверка:** для области желательны **существующие тесты**; если их нет, skill предписывает предупредить пользователя и спросить, продолжать ли (риск регрессий).
3. **senior-reviewer** — только анализ: запахи, приоритеты, конкретные типы рефакторинга (extract function, уменьшение связности и т.д.).
4. **refactor** (подагент-рефактор) — применяет изменения по списку целей, без новых фич и без смены поведения по возможности.
5. **test-runner** — линтер и тесты; при падениях — **debugger** с ограниченным числом повторов.
6. **documenter** — краткое резюме изменений для документации в структуре проекта.

**Примеры scope:**

- `/refactor app/services/foo.py`
- `/refactor frontend/src/features/bar/`
- `/refactor` без аргумента — ориентир на недавние изменения в git (уточняется в skill).

**Когда использовать:**

- После `/audit` или ревью, когда явно видны структурные проблемы.
- Когда новая фича упирается в «локально понятный» технический долг в одном модуле.
- После того как на модуль написали тесты и можно безопасно менять форму кода.

**Когда лучше не использовать:** нужна новая функциональность с нуля и декомпозиция — тогда `/orchestrate`; нужна только оценка диффа перед коммитом — `/review`.

---

### `/review` — код-ревью (часто перед коммитом или PR)

- **Файл команды:** `.cursor/commands/review.md`
- **Skill:** `.cursor/skills/review-workflow/SKILL.md`

**Что делает процесс:**

1. Определяется **область**: по умолчанию часто **staged** изменения, иначе diff к `HEAD`, иначе пользователь указывает файл/папку.
2. **reviewer** классифицирует замечания: Critical / Quality / Suggestion.
3. Если критичные проблемы или пользователь согласился чинить Quality — **debugger** вносит правки в рамках замечаний (не «рефакторинг ради красоты»).
4. После правок — **test-runner**; при падениях — снова **debugger**, с лимитом повторов.

**Примеры (из skill):**

- `/review` — staged;
- `/review --staged`, `/review --last-commit`;
- `/review путь/к/файлу или каталогу`.

**Когда использовать:**

- Перед локальным коммитом или перед созданием PR.
- Быстрая sanity-проверка конкретного файла после сложного merge.
- Когда вы хотите **отчёт + опционально автофиксы**, но не полный аудит всего проекта.

---

### `/implement` — простая реализация «под ключ»

- **Файл команды:** `.cursor/commands/implement.md`
- **Skill:** `.cursor/skills/simple-workflow/SKILL.md`

**Последовательность подагентов:** **worker** → **test-writer** → **test-runner** → **documenter**. Планирование и цикл по многим задачам из плана **нет** — это один проход по одной задаче.

**Когда использовать:**

- Один компонент, одна функция, один endpoint, один небольшой патч с понятным ТЗ.
- Нужно быстро получить код **и** тесты **и** проверку **и** занесение в документацию по правилам проекта.

**Когда не использовать (явно из skill):**

- Несколько подзадач и зависимостей — **`/orchestrate`**;
- Нужна только проверка уже написанного — **`/review`**;
- Уже есть код и нужна только перестройка структуры — **`/refactor`**.

---

### `/orchestrate` — полный цикл для сложной фичи

- **Файл команды:** `.cursor/commands/orchestrate.md`
- **Skill:** `.cursor/skills/orchestration/SKILL.md`

**Фазы:**

1. **planner** создаёт план и оркестрационное рабочее пространство под `.cursor/workspace/` (конкретные пути и ссылки на файлы планов — из `.cursor/config.json` и skill).
2. Для **каждой** задачи из плана (со статусами в `tasks.json` и т.д.): **worker** → **test-writer** → **test-runner** (при сбоях — **debugger**, с повторами) → **reviewer** (при замечаниях — **debugger** + снова reviewer).
3. После выполнения всех задач — **documenter** оформляет итоговую документацию.

**Когда использовать:**

- Крупная фича на несколько файлов/модулей.
- Нужна явная декомпозиция, трекинг прогресса и повторяемый цикл «реализовал → протестировали → отревьюили» по каждому куску.
- Задачи, где важны регрессии и качество на каждом шаге, а не один раз в конце.

**Отличие от `/implement`:** есть план, состояние оркестрации на диске, обход задач и встроенный ревью-цикл на каждую подзадачу.

---

### Как формулировать запрос к команде

- Указывайте **область** (файл, каталог, флаг git), если команда это поддерживает (`/audit`, `/review`, `/refactor`).
- Для `/implement` и `/orchestrate` приложите **критерии готовности**, ограничения (не трогать X), стек/слой (backend vs frontend), если это не очевидно из контекста.
- В одном чате координатор может держать длинную цепочку подагентов — избегайте параллельных конфликтующих правок в том же branch без необходимости.

## 6. Skills (навыки / workflow)

**Файлы:** `.cursor/skills/<имя>/SKILL.md`

### Зачем нужны skills и чем они отличаются от команд

**Skill** — это **полная инструкция для агента**: последовательность шагов, какие подагенты вызывать, как передавать контекст между этапами, форматы отчётов, лимиты повторов, правила по области (scope) и по сохранению артефактов на диск.

| Команда (`/…`) | Обычно одна страница | Часто только: «прочитай skill и будь координатором» |
|----------------|----------------------|-----------------------------------------------------|
| Skill | Длинный сценарий | Реальное «тело» процесса |

Команды **не дублируют** skill — они **входная точка**; без skill координатор не знает точной последовательности.

### Два типа skills в проекте

1. **Workflow-skills** — пошаговые оркестрации (аудит, рефакторинг, реализация, полный цикл). Их триггерят slash-команды или явная отсылка в промпте.
2. **Опорные skills** — стандарты и справочники (качество кода, архитектура, безопасность, git, структура доков, трекинг задач). Их **читают другие агенты** по указанию workflow или senior/reviewer/worker.

### Workflow-skills (сценарии с подагентами)

#### `audit-workflow`

- **Файл:** `.cursor/skills/audit-workflow/SKILL.md`
- **Триггер:** `/audit` (координатор обязан прочитать skill до любых действий).

**Идея:** последовательный аудит с наращиванием контекста — каждый следующий этап получает вывод предыдущего, чтобы не дублировать и углублять находки.

**Типичная цепочка:**

1. Согласовать **область**: весь проект, каталог, файл, или список файлов из `git diff` (`--since main`, `--since HEAD~N` и т.д.).
2. **senior-reviewer** — архитектура (слои, связность, масштабируемость, перегруженные модули).
3. **security-auditor** — угрозы (auth, валидация, секреты, API, утечки в ошибках); на вход подмешивают краткое резюме архитектурных рисков.
4. **reviewer** — качество кода, ошибки, поддерживаемость.
5. **documenter** — **единый сводный отчёт** с агрегацией серьёзности (Critical / High / …).
6. Этап **remediation** (исправления) — только после явного согласия пользователя; маршрутизация по типу проблемы (структурное → refactor; безопасность/фичи → planner + worker и т.п.), затем верификация и обновление отчёта.

**Когда опираться на skill вручную (без `/audit`):** нужно провести аудит по тем же правилам, но из другого чата или скрипта координатора — достаточно приказать: выполнить шаги из этого файла.

---

#### `refactor-workflow`

- **Файл:** `.cursor/skills/refactor-workflow/SKILL.md`
- **Триггер:** `/refactor`.

**Этапы:**

1. **Scope** — файл, каталог, намерение текстом или опора на недавний git diff.
2. **Предусловие:** для целевого кода желательны тесты; при отсутствии — предупреждение и вопрос пользователю (продолжать рискованно или сначала добавить тесты).
3. **senior-reviewer** — только анализ (запахи, приоритеты, рекомендуемые виды рефакторинга), без правок.
4. Подагент **refactor** — применяет изменения по списку; без новых фич и без смены поведения, насколько возможно; опирается на **code-quality-standards**.
5. **test-runner** — линтер и тесты; при падениях — **debugger**, с ограничением числа попыток per skill.
6. **documenter** — фиксирует итог для документации проекта.

**Сценарии:** долг после ревью/аудита; подготовка модуля к фиче; безопасное упрощение кода при наличии тестов.

---

#### `review-workflow`

- **Файл:** `.cursor/skills/review-workflow/SKILL.md`
- **Триггер:** `/review`.

**Этапы:**

1. **Scope:** по умолчанию часто staged; иначе diff к `HEAD`; можно `--staged`, `--last-commit`, путь к файлу/каталогу.
2. **reviewer** — находки Critical / Quality / Suggestion с путями и смыслом.
3. Если только предложения — спросить, чинить ли; критичное — идти к фиксам (с оговоркой для больших объёмов).
4. **debugger** — правки строго под замечания, без лишнего рефакторинга.
5. **test-runner** — проверка после правок; при ошибках снова debugger, с лимитом повторов.

**Сценарии:** прекоммит, перед PR, точечная проверка после merge.

---

#### `simple-workflow`

- **Файл:** `.cursor/skills/simple-workflow/SKILL.md`
- **Триггер:** `/implement`.

**Цепочка:** **worker** → **test-writer** → **test-runner** → **documenter**. В skill описана последовательность без параллели: каждый шаг после завершения предыдущего; контекст передаётся дальше явным текстом промпта.

**Дополнительно:** упоминается фоновый **hook** автоформатирования (eslint/prettier и аналоги) — зависит от настройки проекта и Cursor hooks.

**Когда использовать skill напрямую:** формулировка «реализуй X по simple-workflow» без ввода `/implement`.

**Когда не подходит:** несколько связанных подзадач — **orchestration**; нужен только просмотр — **review-workflow**; нужна только перестройка — **refactor-workflow**.

---

#### `orchestration`

- **Файл:** `.cursor/skills/orchestration/SKILL.md`
- **Триггер:** `/orchestrate`.

**Фазы:**

1. **planner** — план, оркестрация ID, файлы в `.cursor/workspace/active/orch-…/` (`progress.json`, `tasks.json`, `links.json`), ссылка на файл плана в зоне документации из **config.json** (см. **task-management** и **docs**).
2. **Цикл по каждой задаче из плана:** worker → test-writer → test-runner (при сбоях debugger с повторами) → reviewer (при замечаниях debugger + повтор reviewer с лимитом).
3. Обновление статусов задач в `tasks.json` и отметок в плане (в skill заданы идеи формата статусов).
4. После всех задач — **documenter** для итоговой документации.

**Сценарии:** крупные фичи, много файлов, нужен учёт прогресса и качество на каждом шаге.

---

### Опорные skills (стандарты и инфраструктура планов)

#### `task-management`

- **Файл:** `.cursor/skills/task-management/SKILL.md`
- **Кто использует:** прежде всего **planner**, координатор **orchestration**, **documenter**, любой агент, который должен логировать некритичные issues.

**Содержание:**

- **Двухуровневая модель:** временное состояние в **`.cursor/workspace/`** (активные/завершённые оркестрации, метаданные, статусы задач, ссылки на файлы планов) и **постоянные** артефакты по путям из `.cursor/config.json` (планы, отчёты, issues, архитектура и др.).
- Форматы **`progress.json`**, **`tasks.json`**, **`links.json`** и соглашения по именованию оркестраций.
- Правила обновления статусов задач при старте/завершении шага (чтобы `/orchestrate` можно было продолжать предсказуемо).

**Когда читать вручную:** настраиваете оркестрацию, меняете `config.json`, отлаживаете «потерянный» план или хотите вручную возобновить сессию по файлам в `workspace/`.

---

#### `docs`

- **Файл:** `.cursor/skills/docs/SKILL.md`
- **Кто использует:** **documenter**, **planner**, координаторы workflow при сохранении отчётов.

**Ключевые правила:**

- **Не хардкодить** `ai_docs/` — всегда брать корень и подпути из **`documentation.paths`** в `.cursor/config.json`.
- Описание назначения каталогов: `plans/`, `reports/`, `issues/`, `features/`, `api/`, `components/`, `architecture/`, `design/`, `changelog/`, **`audits/`** (в вашем `config.json` аудиты включены отдельным ключом).
- Когда обновлять документацию (после фичи, по запросу пользователя и т.д.).
- Именование файлов (kebab-case для фич и т.п.), перекрёстные ссылки, даты в правках.

**Сценарии:** «куда положить отчёт аудита», как подключить доку в контекст через `@`, если часть путей в `.cursorignore`.

---

#### `code-quality-standards`

- **Файл:** `.cursor/skills/code-quality-standards/SKILL.md`
- **Кто использует:** подагент **refactor**, **reviewer**, **worker**, **debugger** (по описанию skill).

**Содержание:** принципы читаемости, DRY, KISS, модульность, обработка ошибок, типичные рефакторинги и антипримеры. Это **не** пошаговый сценарий чата, а **эталон качества** для правок и проверок.

**Когда явно подключать:** просите ревью или рефакторинг «строго по code-quality-standards» или добавляете `@` на файл skill в контекст.

---

#### `security-guidelines`

- **Файл:** `.cursor/skills/security-guidelines/SKILL.md`
- **Кто использует:** **security-auditor**, **worker** при auth/API/данных, **debugger** при фиксе уязвимостей, **reviewer** при проверке соответствия.

**Содержание:** пароли и хеширование, сессии/JWT, валидация и санитизация входа, SQL-инъекции, CORS, rate limiting, секреты в коде, загрузка файлов, типичные запреты (`eval` пользовательского ввода и т.д.).

**Сценарии:** любая задача с авторизацией, публичными эндпоинтами, персональными данными; подготовка к `/audit`.

---

#### `architecture-principles`

- **Файл:** `.cursor/skills/architecture-principles/SKILL.md`
- **Кто использует:** **senior-reviewer**, **planner**, **worker**, **reviewer** при проверке согласованности архитектуры.

**Содержание:** SOLID, разделение слоёв, направление зависимостей, каталог паттернов (Repository, Factory, Strategy и др. — в spirit skill), критерии хорошей декомпозиции модулей.

**Сценарии:** планирование крупной фичи, архитектурное ревью, разбор «куда положить новый сервис».

---

#### `git-helper`

- **Файл:** `.cursor/skills/git-helper/SKILL.md`
- **Назначение:** единый справочник по **git** для агентов и пользователя в этом репозитории.

**Содержание:** Conventional Commits и генерация сообщений по `git diff --cached`, работа с ветками, разрешение конфликтов, откаты (`reset`, `restore`, `revert`), **bisect**, полезные команды истории.

**Сценарии:** «предложи сообщение коммита», «как безопасно обновить ветку от main», «как откатить последний коммит с сохранением изменений» — координатор или вы можете потребовать следовать этому skill.

### Как не путать skills между собой

| Нужно | Skill |
|-------|--------|
| Полный аудит репозитория или ветки | `audit-workflow` |
| Переписать структуру кода без фичи | `refactor-workflow` |
| Проверить diff перед коммитом | `review-workflow` |
| Одна маленькая задача с тестами и доками | `simple-workflow` |
| Много подзадач и трекинг | `orchestration` + `task-management` |
| Куда сохранить план/отчёт | `docs` + `config.json` |
| Стандарты при написании/рефакторинге | `code-quality-standards` |
| Чеклист безопасности | `security-guidelines` |
| Архитектурные критерии | `architecture-principles` |
| Коммиты и ветки | `git-helper` |

## 7. `config.json`

**Файл:** `.cursor/config.json`

У вас он связывает оркестрацию с деревом **`ai_docs/`**: планы, отчёты, аудиты, архитектура и т.д. Планировщик и другие агенты **читают эти пути**, чтобы сохранять результаты в нужные подпапки.

**Когда менять:** переезд документации, отключение типа артефактов (`enabled: false`), другие сроки очистки `.cursor/workspace`.

---

## 8. `hooks.json`

**Файл:** `.cursor/hooks.json`

Хуки Cursor — реакции на события (например, после сохранения файла или при остановке подагента). У вас массивы пустые — это **заготовка**.

**Когда наполнять:** нужны локальные скрипты (форматирование, проверка, уведомления). Документацию по актуальному формату хуков смотрите в справке Cursor для вашей версии — поля могут эволюционировать.

---

## 9. `.cursor/workspace`

Служебная зона для **текущих** планов оркестрации, прогресса и временных файлов. В репозитории часто добавляют `.gitignore`, чтобы не коммитить машинно-генерируемое; при этом **пути итоговых отчётов** у вас завязаны на `ai_docs/` через `config.json`.

---

## 10. Как связать всё вместе (типовые сценарии)

1. **Быстрая правка в одном файле**  
   Достаточно системных/user rules; можно не трогать agents/commands.

2. **Новая фича на несколько дней**  
   `/orchestrate` или явный вызов planner → worker → test-runner → reviewer; опираться на `orchestration` / `task-management` skills и `config.json`.

3. **Разобраться, как устроен модуль**  
   `@codebase-researcher` + узкий вопрос по пути в коде.

4. **Релиз / безопасность**  
   `/audit` или `@security` + при необходимости agents `security-auditor`, `reviewer`.

5. **Привести код к стандартам**  
   `/refactor` + skill `refactor-workflow`; правила качества подключены через rules.

---

## 11. `@` в чате Cursor (кратко)

- **`@файл`** — прикрепить файл в контекст.
- **`@папка`** — прикрепить дерево (осторожно с размером).
- **`@правило`** из `.cursor/rules/` — явно применить выбранный профиль (особенно если `alwaysApply: false`).
- Упоминания вида **`@.cursor/...`** в инструкциях агентов означают: «прочитай этот путь из проекта» — то же самое можно сделать вручную в чате через `@` на файл.

---

## 12. Частые ошибки

- **Слишком много `alwaysApply`** — деградация ответов из‑за переполнения контекста и конфликтующих инструкций.
- **Дублирование** одного и того же в rules и в skills без разделения ролей: rules = стандарты, skills = процесс.
- **Коммит всего `workspace/`** — засорение истории; лучше игнорировать генерируемое и хранить итоги в `ai_docs/`.

---

## 13. Где ещё может быть конфигурация Cursor

Помимо **проектной** `.cursor/`, у вас могут быть **пользовательские** навыки и правила в домашнем каталоге (например, глобальные skills в `~/.cursor/...` — зависит от установки). Проектная `.cursor` имеет приоритет контекста «этот репозиторий» и удобна для команды.
