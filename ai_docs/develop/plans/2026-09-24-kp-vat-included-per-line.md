# Implementation Plan: НДС в КП «в том числе 22%», по строкам

**Created:** 2026-09-24  
**Status:** PLAN, к коду не переходили  
**Spec:** [`ai_docs/specs/kp-vat-included-per-line.md`](../../specs/kp-vat-included-per-line.md)

## Overview

Новый `kp_id` выделяет НДС так же, как 1С: по каждой напечатанной сумме строки `round(сумма × 22/122, 2)` с округлением половины вверх, затем сумма. Итог к оплате не меняется. Карточка, PDF и обычный Excel показывают одно число. Excel «доставка в цене» считает той же функцией, но по суммам, куда доставка уже вошла, поэтому может отличаться на копейки.

Уже выданные номера, включая КП № 26, остаются на `× 0,22` и прежней базе. Порог — константа, равная `max(kp_id) + 1` на момент реализации.

## Architecture Decisions

- **A1. Одна чистая функция.** `vat_included_from_line_sums` в `core/commercial_pricing.py`. На вход — суммы строк в рублях. Внутри `Decimal` и `ROUND_HALF_UP`. Дробь `22/122`. Банковское `round` Python не использовать.
- **A2. База — копейка строки, которая попадёт в документ.** Сначала квант суммы строки до `0.01`, потом налог. Для обычного документа в список входят изделия и строки доставки. Для файла «доставка в цене» — только строки изделий после `embed_delivery_in_unit_prices`, их `line_sum`.
- **A3. Порог по id, без колонки и без миграции.** `VAT_PER_LINE_FROM_KP_ID`. `kp_id` меньше порога: прежняя формула (плиты после скидки × 0,22; доставка в обычном НДС не входит; во вшитом Excel вся сумма строк × 0,22). `kp_id` больше или равен порогу, и расчёт ещё без id (визард до сохранения): новая формула. Пересохранение старого id порог не перескакивает.
- **A4. Карточка число не считает.** Она уже показывает `vat_amount` из API. Верное значение обязано записаться в `KP_offers.vat_amount` через текущие `calculate_total_cost` → `offers_write` / `kp_persistence_service`.
- **A5. Excel нового КП пишет число, не формулу `SUM × 0,22`.** Иначе лист округлит иначе, чем PDF. Старый `kp_id` формулу `× 0,22` сохраняет.
- **A6. Итог к оплате не трогать.** `total_with_vat = плиты после скидки + доставка`. Меняются `vat_amount` и `subtotal = total_with_vat − vat_amount`.
- **A7. Вне плана.** Цены, скидка, рейсы, раскладка доставки по штукам, экран сверки, подпись без суммы, пачка `UPDATE` по архиву. Ветка `ImportError` в `kp_persistence_service` (налог сверху и итог `subtotal + vat`) недостижима и не меняется.

```
vat_included_from_line_sums
        │
        └── calculate_total_cost(kp_id)
                │
                ├── сохранение → KP_offers.vat_amount → карточка
                ├── PDF (те же totals)
                └── XLSX: число из функции
                        │
                        └── режим «доставка в цене»: те же правила,
                            вход — line_sum после вшивания
```

## Implementation order

1. Функция и эталон счёта 680, без вызовов из документов.
2. Ветка порога в `calculate_total_cost`: старый id считает как сейчас, новый — по строкам, включая доставку. Итог к оплате тот же.
3. Все вызовы `calculate_total_cost` для уже сохранённого КП передают его `kp_id`. Визард до номера порог не передаёт.
4. PDF и оба Excel берут это число. У вшитого файла свой список строк. Старый id в Excel остаётся на формуле `× 0,22`.
5. Прогон тестов, которые зашивали `× 0,22`, только там, где сценарий стал новым id.

## Tasks

- [ ] Task: функция и эталон
  - Acceptance: 21 сумма счёта 680 даёт `447107.82`. Одно умножение итога `2479416.00 × 22/122` = `447107.80` функция не возвращает. Пустой список и `0` дают `0.00`.
  - Verify: `pytest tests/test_vat_included.py -q`
  - Files: `core/commercial_pricing.py`, `tests/test_vat_included.py`

- [ ] Task: порог и расчёт итогов
  - Acceptance: при `kp_id < VAT_PER_LINE_FROM_KP_ID` `vat_amount` равен прежнему `round(плиты × 0.22, 2)`, доставка в базу не входит. При новом id налог — сумма по строкам изделий и доставки, `total_with_vat` прежний. Константа выставлена в `max(kp_id)+1` на момент правки (сейчас живой максимум — 26, порог не ниже 27, если к тому времени номер не вырастет).
  - Verify: тесты в `tests/test_vat_included.py` на оба режима; `total_with_vat` до и после совпадает.
  - Files: `core/commercial_pricing.py`, `tests/test_vat_included.py`

- [ ] Task: сохранение передаёт id
  - Acceptance: обновление и создание КП пишут `vat_amount` из `calculate_total_cost`. Повторное сохранение КП № 26 не меняет записанные `513112.80`. Новый номер пишет построчный налог.
  - Verify: точечный тест записи или существующий тест offers/persistence с подставным id по обе стороны порога.
  - Files: `core/kp/offers_write.py`, `core/kp_persistence_service.py`, связанный тест

- [ ] Task: PDF и Excel
  - Acceptance: у нового id карточка, PDF и обычный XLSX показывают один `vat_amount`. Ячейка НДС в новом Excel — число, подпись «в том числе НДС (22%)». Вшитый XLSX вызывает ту же функцию от `line_sum` и может отличаться на копейки. У id ниже порога оба Excel остаются на `× 0,22` и прежней базе.
  - Verify: `pytest tests/test_vat_included.py tests/test_commercial_offer_xlsx.py tests/test_archive_endpoints.py -q`
  - Files: `core/commercial_offer.py`, `core/commercial_offer_xlsx.py`, тесты этих генераторов

## Risks

- Не передать `kp_id` из какого-то вызова `calculate_total_cost` — старое КП при выгрузке получит новый налог. Перед правкой вызовов сверить все вхождения.
- Сумма строки в float, а в файле уже копейка — налог разъедется с 1С. Квантовать строку до вызова функции.
- Порог, зафиксированный раньше нового заказа, переведёт ещё не выданный, но уже сохранённый номер на новую формулу. Константу ставить в той же правке, когда включается расчёт, по фактическому `max(kp_id)`.
