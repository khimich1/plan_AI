# План: Дельта КП в 1С

**Дата:** 2026-10-01
**Статус:** выполнен
**Идея:** `ai_docs/ideas/kp-1c-delta.md`
**Спека:** `ai_docs/specs/kp-1c-delta.md`

## Overview

Сборщик перестаёт писать «Счёт на оплату» и кладёт в файл тело, которое 1С уже приняла по КП 31: «КоммерческоеПредложение» со строками, суммами и НДС. Первая отправка называется `new_{kp_id}_{время}.json` и не содержит идентификаторов заказа. Исправление называется `delta_{kp_id}_{время}.json`: те же строки целиком, а первыми ключами идут `УИД_ЗК`, `Номер_ЗК`, `УИД_КП`. Номер хранится в `order_number_1c`, УИД — в двух новых колонках. Для КП 31 пустые колонки один раз заполняются из уже присланного ответа, шапка показывает «Счёт 469». Разбор следующих ответов 1С в план не входит.

## Architecture Decisions

- **Сборщик по-прежнему не пишет файл.** `build_invoice_document` возвращает словарь и хеш. Файл пишет `ArchiveService` после ворот контрагента, договора и GUID.
- **`action` остаётся аргументом функции, не ключом JSON.** `create` выбирает отсутствие трёх идентификаторов и префикс `new_`. `update` требует номер и оба УИД и выбирает префикс `delta_`.
- **Ключи `event`, `action`, `НомерЗаказа` из файла уходят.** Штамп `attach_contract_number` уже принимает «КоммерческоеПредложение».
- **Суммы строк считает сборщик.** `СуммаСНДС` = цена до скидки × количество × коэффициент скидки, плюс `СуммаДоставки`. НДС строки = эта сумма × 22/122. Шапка — сумма строк, не сырые `vat_amount` и `total_amount` карточки.
- **Склад и доставка не переоткрываются.** `Склад`, `Самовывоз` и доли `СуммаДоставки` остаются как есть.
- **УИД не попадают в API карточки.** `get_kp_by_id` читает `SELECT *`, новые колонки видны сервису. Схема ответа карточки их не добавляет. Кнопка по-прежнему смотрит на `order_number_1c` и `correction_pending`.
- **Запись идентификаторов одна функция.** Пустые поля заполняются. Совпадение с уже лежащими значениями — пустая операция. Отличие хотя бы в одном поле — отказ, строка не меняется. Миграция КП 31 вызывает её и при отказе не роняет старт приложения.
- **Уже лежащие файлы обмена не трогаем.**

## Dependency graph

```
сборщик тела «КоммерческоеПредложение»
    │
    ├── колонки uid_order_1c, uid_kp_1c
    │       │
    │       └── запись трёх полей КП 31
    │               │
    │               └── POST invoice-export → new_
    │                       │
    │                       └── POST invoice-correction → delta_
    │                               │
    │                               └── шапка «Счёт 469» (колонка номера, без нового UI)
    │
    └── штамп НомерДоговора (уже принимает это имя документа)
```

Разбор входящего `otvet` в граф не входит.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Тесты ждут «Счёт на оплату», `event` и `invoice_create_` | Среднее | Их утверждения меняются в D1C-001 и D1C-003 вместе со сборщиком, а не отдельным проходом |
| Шапка `СуммаСкидки` сегодня может брать число карточки, а не сумму строк | Среднее | D1C-001 считает её по строкам. Для КП 31 скидка 0, расхождения нет |
| `ensure_schema` уже отметила базу в текущем процессе | Низкое | Новые колонки видны после перезапуска приложения. План сам сервер не перезапускает |
| В кнопке номер есть, а УИД в базе нет | Низкое | Сервис отказывает и не пишет файл. Запись КП 31 кладёт все три значения вместе |
| 1С допишет строки `delta_` к заказу вместо замены | Высокое для боя | В файл всё равно уходит весь состав, как договорились. Боевой `delta_` по КП 31 кладётся после приёмки плана и проверки файла, не из этого плана автоматически |

## Out of scope

- Разбор следующего файла ответа и сторож каталога
- HTTP в 1С
- Поле ввода номера, показ JSON и УИД
- Удаление или переписывание `kp_offer_31_20260929.json` и `invoice_create_*`
- Смена склада, формулы доставки, оплаты и перехода в производство
