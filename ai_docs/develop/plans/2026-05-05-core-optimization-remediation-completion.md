## Оставшийся разрыв

Сейчас `core/optimization/__init__.py` **выполняет** (`exec`) содержимое соседнего файла `core/optimization.py`, подменяя `__file__` на путь монолита. Публичный API пакета фактически «живёт» в этом файле.

**Что остаётся в монолите** (по поверхностной инвентаризации):

- **`verify_coverage`** — сверка покрытия спроса.
- **`_optimize_2d_with_lengths`** — крупный блок: пост-ILP пайплайн, интеграция с уже вынесенными модулями.
- **`_optimize_1d_widths_only`** — режим только по ширине.
- **Legacy 1D PuLP:** `apply_width_optimization`, `optimize_cuts_pulp`, вспомогательные `_group_plate_lengths`, `_append_actions` и др.
- **Отладочные/служебные** хелперы (`_debug_runtime_write_648532`, группировки действий и т.д.).

Оценка размера файла: **порядка 1,5–1,6k строк** — основной долг техдолга по SRP не в новых leaf-модулях, а в этом файле и в способе его подключения.

**Технический долг загрузки:** `exec` усложняет статический анализ, отладку трассировок и порядок инициализации; `orchestrator.py` вынужден делать ленивый `import core.optimization as pkg` и вызывать символы с пакета.

## OPT-008 — убрать `exec`, нормальный пакет (**PHASE-A**)

**Задача в `tasks.json`:** `OPT-008` — «Create package `__init__.py` and retire old file».

**Цель:** перестать выполнять монолит как строку; сохранить поведение и `_OptimizationModule`.

### Атомарные подшаги (выполнять по порядку)

| ID | Шаг |
|----|-----|
| **OPT-008-S01** | **Импорт-граф (baseline до правок):** зафиксировать, кто импортирует `core.optimization`, `core.optimization.orchestrator`, подмодули пакета; нарисовать/записать ориентир: `__init__.py` → `_implementation` → подмодули; `orchestrator` ↔ пакет (ленивые импорты). |
| **OPT-008-S02** | **Запрет циклов `orchestrator` ↔ `_implementation`:** `_implementation` (бывший монолит) не импортирует `orchestrator` на уровне модуля; тяжёлые связи только через локальные `import` внутри функций или через уже существующий паттерн «вызов в пакет после загрузки». |
| **OPT-008-S03** | **Переименовать/перенести** `core/optimization.py` → `core/optimization/_implementation.py` (или согласованное имя); обновить внутренние относительные ожидания `__file__` только если тесты/логи завязаны на путь. |
| **OPT-008-S04** | **`core/optimization/__init__.py`:** обычные `import`/`from ._implementation import ...`; явный **`__all__`** и реэкспорт всех публичных символов, которые реально используют потребители (grep из `OPT-009` может уточнить список); **убрать** `exec`/`compile`. |
| **OPT-008-S05** | **`sys.modules` / `importlib` проверки:** после импорта `import core.optimization` убедиться, что `sys.modules['core.optimization']` — пакет с ожидаемым `__path__`; нет дубликата ключа под старым путём к однофайловому модулю; при необходимости однократно прогнать `python -c` / минимальный скрипт с `importlib.reload` в dev-only сценарии. |
| **OPT-008-S06** | **Удалить** соседний файл **`core/optimization.py`**, чтобы не было конфликта «файл vs каталог» с пакетом `core/optimization/`. |
| **OPT-008-S07** | **TLS / `_OptimizationModule`:** сохранить `sys.modules[__name__].__class__ = _OptimizationModule` (или эквивалент) для пакета; регрессия: присваивание `core.optimization.OPT_*` уходит в TLS как сейчас. |

**Критерии приёмки (OPT-008):**

1. `python -c "import core.optimization"` и импорт ключевых символов без ошибок.
2. Нет вызова `exec`/`compile` для загрузки реализации в `__init__.py`.
3. Присваивания вида `core.optimization.OPT_PLAN = ...` (или перечисленные в `_TLS_PUBLIC`) уходят в TLS, как сейчас.
4. Импорт-граф без новых циклов на старте пакета; при необходимости — только локальные импорты внутри функций.

## Риски и откат

| Риск | Митигация | Откат |
|------|-----------|--------|
| Цикл импортов `orchestrator` ↔ пакет после удаления `exec` | Ленивые импорты внутри функций; `_implementation` не импортирует `orchestrator` на модульном уровне | Временный реэкспорт через промежуточный shim-файл |
| Потеря поведения `OPT_*` через `_OptimizationModule` | Регрессионный тест на присваивание и чтение из TLS | Вернуть класс-обёртку без изменения семантики |
| Внешний код импортировал подмодули из старого пути файла | `OPT-009` до merge | Тонкий `optimization.py` только с предупреждением/реэкспортом (нежелательно долгосрочно) |
| Рост времени импорта при «толстом» `_implementation` | Поэтапный вынос в Фазу 2 (`OPT-P2-004`) | — |

### Удаление `core/optimization.py` — процедура отката (нумерованно)

1. **До удаления:** создать ветку; убедиться, что содержимое перенесено в `core/optimization/_implementation.py` и все публичные имена доступны через пакет.
2. **Проверка:** `OPT-009-S01` grep и smoke-импорт приложения / бота / CI.
3. **После удаления при сбое:** `git revert` коммита удаления **или** временно восстановить файл из истории как thin-reexport с `DeprecationWarning`, затем снова пройти `OPT-008-S04`..`S07`.
4. **Контроль `sys.modules`:** при откате очистить из кэша проблемный модуль вручную только в debug-сценариях; в production полагаться на новый процесс после деплоя.
