# Политика доступа к коммерческим предложениям (КП)

**Status:** accepted  
**Date:** 2026-08-28  
**Related:** [`app/security/offer_access.py`](../../../app/security/offer_access.py), [`core/kp/offers_read.py`](../../../core/kp/offers_read.py)  
**Audit:** S1 / A15 (2026-08-28, `ai_docs/develop/audits/2026-08-28-full-project-audit.md`)

## Context

В системе действуют роли `admin` и `manager`. Коммерческий архив (все КП, все разделы) является **общим рабочим пространством** коммерческого отдела: менеджеры совместно ведут сделки, подхватывают КП коллег и работают с архивом без разграничения «свой/чужой».

Проверки доступа сосредоточены в `app/security/offer_access.py`:

- `can_read_offer(user, offer)` / `can_write_offer(user, offer)` возвращают `is_admin_or_manager(user)`;
- `assert_offer_read_access` / `assert_offer_write_access` поднимают `403` для остальных ролей;
- `list_filters_for_user` не накладывает фильтров для admin/manager и возвращает `{"deny_all": True}` для прочих.

При этом модель данных уже поддерживает владельца: `core/kp/offers_read.py` читает `owner_user_id` из `kp_meta` и умеет фильтровать выборки по `owner_user_id` (параметр `_offer_access_sql_filters`). В действующей policy этот параметр **не используется**.

Аудит 2026-08-28 зафиксировал это расхождение как находки:

| Находка | Суть |
|---------|------|
| [S1] | «IDOR: любой менеджер видит и изменяет чужие КП» — трактовка как уязвимости |
| [A15] | «Модель авторизации КП не использует `owner_user_id`» — расхождение модели данных и policy |

## Decision

Общий доступ к коммерческому архиву — **осознанная бизнес-политика** (решение владельца продукта от 2026-08-28), а не уязвимость IDOR:

- Менеджеры и администраторы **разделяют полный доступ на чтение и изменение всех КП во всех разделах**.
- Разграничение по владельцу (`owner_user_id`) осознанно **НЕ применяется**.
- Поле `owner_user_id` в модели данных и поддержка фильтрации в `core/kp/offers_read.py` **зарезервированы** для возможной будущей политики (например, «личные черновики» или разграничение по командам). Их наличие не является дефектом.

| Аспект | Политика |
|--------|----------|
| Чтение КП | admin + manager — все КП, все разделы |
| Изменение КП | admin + manager — все КП, все разделы |
| Остальные роли / аноним | `403`, списки — `deny_all` |
| Фильтр по `owner_user_id` | Не применяется (зарезервирован) |

## Consequences

- Поведение зафиксировано тестами `tests/test_archive_authorization.py` и `tests/test_offers_production_authorization.py`; они являются исполняемой спецификацией этой политики.
- Находка [S1] аудита 2026-08-28 закрывается как «won't fix — by design»; [A15] закрывается этим документом.
- При смене политики (например, введении разграничения по владельцу) порядок изменений строго такой: **сначала обновить этот ADR**, затем код (`app/security/offer_access.py`, при необходимости `core/kp/offers_read.py`) и тесты.
- До смены политики любые PR, добавляющие owner-check в `offer_access.py`, считаются нарушением зафиксированного поведения.

## Non-goals

- Реализация owner-based разграничения доступа в этом change set.
- Удаление или переработка `owner_user_id` из модели данных — поле сохраняется как резерв.
- Изменение поведения `list_filters_for_user` для ролей вне admin/manager.
