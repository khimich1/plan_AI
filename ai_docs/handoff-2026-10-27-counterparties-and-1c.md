## Зачем

Менеджеру нужен раздел карточек договоров в архиве: поиск, создание, правка, файл карточки, удаление. КП с контрагентом, у которого уже есть договор, должно уходить в 1С без повторного ввода номера, ИНН и кода. Имена карточек должны совпадать со справочником 1С, если ИНН однозначный.

## Где что лежит в базе

Файл: `plita.db`.

| Таблица | Что хранит |
|---|---|
| `counterparties` | Справочник 1С: `code_1c` (обязателен и уникален), `guid_1c`, имя, ИНН, КПП, `is_client`, `is_active`. На 21.10.2026 — 4413 строки. `guid_1c` пустой у всех. |
| `supply_contract` | Карточка договора. Имя списка — `imported_name`. Номер, ИНН, статус, реквизиты бланка, `counterparty_id`. На 21.10.2026 — 186 строк. |
| `KP_offers` | Снимок на КП: `counterparty_id`, `customer_name`, `customer_inn`, `customer_kpp`. Номер счёта из 1С — `order_number_1c`, плюс `uid_order_1c`, `uid_kp_1c`. Номер договора на КП не хранится. |
| `supply_contract_event` | Журнал смен полей договора. |

Код 1С в форму «Новая карточка» не вводится. Он уже лежит в `counterparties.code_1c`. В JSON счёта уходит как `Контрагент.Код`. `Контрагент.GUID` берётся из `guid_1c` и сейчас пустой. Пустой GUID отправку не останавливает.

## Что уже сделано в коде

Раздел архива **Контрагенты** (`?section=counterparties`). Список КП на этой вкладке не запрашивается.

- Поиск по имени, ИНН и номеру. Пустой запрос показывает все карточки под формой «Новая карточка».
- Новая карточка: имя, необязательные ИНН и номер. Без номера программа ставит следующий `NNNN/MM/YY` (`next_contract_seq`).
- Перетаскивание Word, Excel, PDF, JPEG, PNG на форму «Новая карточка» и внутри открытой карточки. Разбор до создания строки: `POST /contract-cards/parse`. Реквизиты бланка пишутся только по «Сохранить реквизиты».
- Если ИНН целиком или отображаемое имя целиком совпадает с уже занесённой карточкой, форма не создаёт дубль молча. Диалог: «Редактировать» открывает найденную, «Всё равно создать» пишет новую. Прямой `POST /contract-cards` вторую карточку всё ещё может создать.
- Удаление карточки: кнопка под «Сохранить реквизиты». Нужно ввести слово `УДАЛИТЬ` заглавными. `DELETE /contract-cards/{id}`. Справочник не трогается, номер освобождается.
- Флаг «не полные»: серверное поле `requisites_complete`. Пустой бланк помечается в списке и на карточке. Печать Word/PDF бланка запрещена, отправка в 1С — нет.
- Имена 180 карточек переписаны в `imported_name` из `counterparties.name` при однозначном ИНН. Пропущены: ООО «Прогресс» (ИНН `6700015814` нет в справочнике), «Банк Точка» (ИНН `7743298799` — два разных имени), `0001/10/26` оставлен с полным именем бланка «Общество с ограниченной ответственностью «КАПИТАЛСТРОЙ»».
- Мастер КП ищет клиента только по карточкам договоров. Имя и ИНН на КП — с карточки, не из другого имени справочника. Код и `counterparty_id` подставляются, только если связь живая. Архив «Занести контрагента» по-прежнему ищет весь справочник 1С.
- Отправка в 1С связывает договор со справочником, если ИНН указывает ровно на одного активного клиента. Берётся самый поздний по `contract_date`, при равенстве — больший `id`. Связь пишется в момент отправки и перевода в производство. Подсказка кнопки только читает. Живой проход 21.10.2026: `created=172`, `skipped=13`. У `0882/09/25` (Караван) `counterparty_id` стал `1362`. У Секлюцкого связан только `0933/03/26`.
- Архив КП сортируется по `kp_id DESC` (`core/kp/offers_read.py`, `get_all_kp_list`).
- В `app/schemas/notifications.py` добавлено `KIND_INVOICE_NUMBER_RECEIVED = "invoice_number_received"`. Без неё приём `otvet_*.json` не импортировался.

## Отправка в 1С

Кнопка «Отправить в 1С» пишет UTF-8 JSON в `data/exchange_export/` (настройка `EXCHANGE_EXPORT_DIR`, по умолчанию `data/exchange_export`). Живого HTTP в 1С нет. Имя файла: `new_{kp_id}_{timestamp}.json`. Пример уже отправленного: `data/exchange_export/new_16_20261021T144518069148.json`. После записи КП переходит в «на согласовании».

Договор ищется так: сначала `supply_contract.counterparty_id` равен клиенту КП. Если нет — однозначный ИНН и правило «самый поздний договор». Иначе текст «Нет действующего договора поставки». Без клиента на КП — «Сначала занесите контрагента».

КП №16 (Ярославский речной порт) ушло с номером договора `0797/02/25`, кодом `00-00002153`, ИНН `7607001209`, КПП `760701001`, GUID контрагента `null`. Три плиты с GUID номенклатуры. НДС в файле `162805.23`, на карточке КП показывалось `176622.38`. Итог `902829` совпал.

## Ответ 1С

Файл `otvet_*.json`. Обязательные поля:

| Поле | Куда |
|---|---|
| `Номер_КП` | `kp_id` нашего КП |
| `Номер_ЗК` | `KP_offers.order_number_1c` — номер счёта |
| `УИД_ЗК` | `uid_order_1c` |
| `УИД_КП` | `uid_kp_1c` |

`Описание` не читается. Если на КП уже другой номер или УИД, новый ответ не перезаписывает строку.

Номер счёта подставляется при следующем скачивании спецификации (и XLSX, и PDF) в заголовок: «Спецификация по счету № …». Номер договора поставки не меняется: «к Договору поставки № …» остаётся из `supply_contract`.

Фиктивный прогон КП №17 делался только во временной базе `/tmp/kp17-reply-sim`, каталог удалён. Живой КП №17 не трогали: клиент «КАПИТАЛСТРОЙ», ИНН `7612045875`, `counterparty_id` 1359, договор `0001/10/26` связан, `0998/07/26` без связи, `order_number_1c` пустой.
