## Assumptions I'm Making

1. Договор вешается на `counterparties.id`, уже привязанный к КП. Без `counterparty_id` кнопка недоступна.
2. Один действующий договор на контрагента. КП номер не хранит: сборщик JSON читает его через контрагента.
3. Статус подписи не блокирует будущую отправку в 1С. Блокирует только отсутствие действующего договора.
4. Номер вида `{seq}/{mm}/{yy}`. `seq` — сквозной, не меньше 4 цифр (`1028`). `mm` и `yy` берутся из даты договора в момент выдачи. После выдачи дату можно сменить, номер не пересчитывается.
5. Стартовый `seq` не зашит. Перед включением лист юриста за 2026 год загружается заново. На 25.09.2026 последняя строка была `1027/09/26`.
6. Имя поля в JSON — `НомерДоговора` в шапке документа `КоммерческоеПредложение`. Если 1С назовёт иначе, меняется только ключ.
7. Роль новая не нужна. Пишет тот же круг, что архив: `admin` и `manager`.
8. Реквизиты покупателя не пишутся в `counterparties`. Справочник по-прежнему затирается выгрузкой 1С (имя, код, GUID, ИНН, КПП).
9. Физлицо и КФХ получают свою преамбулу, не текст ООО.
10. Распознавание карточки уточнено спекой [`supply-contract-card-recognition.md`](supply-contract-card-recognition.md): Word, Excel и PDF с текстом читаются локально; зрение — только фото и скан без текста, через `create_ocr_provider()`. Неверная цифра в поле не кладётся. Экран после разбора — спека [`supply-contract-card-review.md`](supply-contract-card-review.md): предупреждение только по непрошедшим цифрам, масштаб фото как у снимков КП.

→ Если что-то из этого неверно — править spec до плана.

## Objective

Менеджер в архиве заводит договор поставки покупателю, получает номер и docx, видит реестр вместо Excel юриста. Тот же номер попадает в шапку JSON, по которому 1С создаёт КП и заказ клиента.

Успех: у контрагента не больше одного действующего договора; КП без договора не из чего подставить номер; повторное КП того же контрагента не создаёт новый бланк.

### Пользователь

Менеджер по продажам (роли `admin` / `manager`), карточка КП в архиве. Контрагент 1С уже привязан.

### Сценарии

1. **Договора нет.** Кнопка открывает выбор: загрузить карточку или пустая форма. Слева источник (картинка, скан или текст файла), справа поля. Менеджер правит подсвеченное и подтверждает. Появляются номер, статус «нет», docx, строка реестра.
2. **Договор есть.** Кнопка показывает номер, дату и статус. Новый бланк не создаётся. Docx можно скачать снова из сохранённых полей.
3. **Реестр.** Список: номер, дата, контрагент, менеджер, статус оригинала/ЭДО, отметка скана. Менеджер меняет статус и прикладывает скан. Смена пишется в историю (кто, когда, какое значение).
4. **Отмена.** Статус «отмена не будем работать» не создаёт новый договор. Отдельное действие «Новый договор» снова открывает сценарий 1. Старая строка остаётся.
5. **Повторное КП.** Тот же `counterparty_id`, действующий договор есть — сценарий 2, даже если это другое КП.
6. **Импорт листа.** Строки 2026 года попадают в реестр. Совпавший контрагент связывается только человеком. Похожие названия программа может показать, сама не связывает.

## Поля бланка

Блок поставщика в форму не входит. Это константа печати: ООО «ЖБК СТАРТ», Шишов А. В. по уставу, ИНН/КПП/ОГРН, адреса Костромы и Ярославля, счёт ПСБ, почты, оператор ЭДО «Тензор», город Кострома. Штрафы, ГОСТ, раздел ЭПД и пустое приложение №1 (форма М-2) печатаются как в шаблоне.

Менеджер заполняет покупателя.

| Поле | Обязательность | Куда в бланке |
|---|---|---|
| Вид: ООО, АО, ИП, КФХ, физлицо | да | преамбула |
| Полное наименование | да | преамбула и блок «ПОКУПАТЕЛЬ» |
| Краткое наименование | да | блок «ПОКУПАТЕЛЬ» |
| Должность и ФИО подписанта | да для ООО и АО; для ИП, КФХ и физлица — ФИО | «в лице» |
| «действующего» / «действующей» | да, выбор, по умолчанию «действующего» | преамбула. Из имени не угадываем |
| Основание: устав или доверенность | да. У доверенности номер и дата | преамбула, п. 7.8 |
| ИНН | да | реквизиты |
| КПП | да для ООО и АО, пусто для остальных | реквизиты |
| ОГРН / ОГРНИП | да | реквизиты |
| Юридический адрес | да | реквизиты |
| Почтовый адрес | нет | реквизиты, если отличается |
| Телефон | нет | реквизиты |
| E-mail | да | п. 10.3(б) и реквизиты |
| Банк, расчётный счёт, корсчёт, БИК | да | реквизиты |
| Оператор ЭДО и идентификатор | нет | реквизиты, если заполнены |

Из архива в пустую форму подставляются краткое имя, ИНН и КПП контрагента. Менеджер КП пишется в реестр, не в текст договора.

Преамбула ООО и АО собирается из вида, имени, подписанта, рода и основания. ИП, КФХ и физлицо не получают фразу «Общество с ограниченной ответственностью … на основании Устава».

В договор не входят марки, цены, доставка, срок, ИГК, казначейский счёт и доверенность на водителя.

## Реестр

| Колонка | Значения |
|---|---|
| Номер | `1028/09/26`, выдаётся программой, вручную не редактируется |
| Дата | дата договора, по умолчанию день подтверждения |
| Контрагент | связанный `counterparty_id` либо, для импорта, текст имени до связки |
| Менеджер | менеджер КП в момент создания |
| Оригинал (либо ЭДО) | `нет` (старт), `подписан по ЭДО`, `оригинал в бухгалтерии`, `подписан с синей печатью оригинал`, `отмена не будем работать` |
| Наличие скана | пусто, `получен скан`, `внесены правки`; к строке можно приложить файл |

Действующий договор — любой статус, кроме «отмена не будем работать».

## Распознавание карточки

Экран один: источник слева, форма справа, подтверждение внизу. Правила чтения, контроля цифр и списка счетов — в [`supply-contract-card-recognition.md`](supply-contract-card-recognition.md).

- Неподтверждённый разбор номер не получает и в печать не идёт.
- Повторный запуск и правка полей на том же экране. Отдельная текстовая инструкция модели не входит в первую версию.

Парсер марок, суффиксы нагрузки и многостраничный состав КП не используются.

## Номер и импорт

Выдача номера — одна транзакция: `seq = max(первый сегмент по всем договорам, включая отменённые) + 1`, месяц и год из даты. Дыры не заполняются.

Импорт листа — разовый сценарий администратора, файл в репозиторий не кладётся. Строка без уверенной связи остаётся с текстовым именем и без `counterparty_id`. Такой номер действующим договором клиента не считается, пока менеджер не свяжет строку. Пока лист ещё ведут снаружи, новые номера в программе не включают.

## Шов с 1С

Живого клиента обмена в коде нет. Контур договора обязан отдать номер так:

```json
{
  "Документ": "КоммерческоеПредложение",
  "НомерДоговора": "1028/09/26",
  "Контрагент": {}
}
```

Поле в шапке, не в строках товаров. Нет действующего договора — пакет не собирается.

Ответ 1С, когда обмен появится, пишет на КП номер заказа и статус заказа. Номер счёта в 1С равен номеру заказа. Этот контур хранение этих двух полей предусматривает, сам обмен не реализует.

Организацию в тестовом JSON (`ООО «Комбинат ЖБК»`) эта спека не меняет.

## Code Style

Номер и «действующий договор» считаются в одном месте.

```python
def format_contract_number(seq: int, on: date) -> str:
    return f"{seq:04d}/{on.month:02d}/{on.year % 100:02d}"


def active_status(status: str) -> bool:
    return status != "отмена не будем работать"
```

Ошибки менеджеру по-русски, в тоне архива: «Сначала занесите контрагента из 1С», «У контрагента уже есть договор 1028/09/26».

## API

Все маршруты под `require_roles("admin", "manager")`, КП только «в архиве», запись — автор КП или admin, как у остальных правок архива.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/commercial/archive/{kp_id}/supply-contract` | Действующий договор контрагента или пусто |
| POST | `/commercial/archive/{kp_id}/supply-contract/parse` | Файл карточки → поля и подсветка, без номера |
| POST | `/commercial/archive/{kp_id}/supply-contract` | Подтверждённые поля → номер, строка, docx |
| GET | `/commercial/archive/{kp_id}/supply-contract/document` | Скачать docx |
| PATCH | `/commercial/archive/supply-contracts/{id}` | Статус, отметка скана, файл скана |
| POST | `/commercial/archive/supply-contracts/{id}/replace` | После отмены: новый договор того же контрагента |
| GET | `/commercial/archive/supply-contracts` | Реестр |
| POST | `/commercial/archive/supply-contracts/import` | Разовый разбор листа, только admin |

POST создания при уже действующем договоре отвечает существующим номером и новый не выдаёт.

## Boundaries

- **Always:** номер только после подтверждения формы; один действующий на контрагента; отменённый seq не переиспользовать; реквизиты не писать в `counterparties`; тесты на номер, повтор и преамбулу ИП; ошибки по-русски.
- **Ask first:** другое имя поля JSON; обязательность телефона или ЭДО; смена статуса не менеджером, а отдельной ролью; хранить скан в БД, а не файлом; править текст бланка.
- **Never:** живой вызов 1С из этой кнопки; автосвязка импорта по похожему имени; суффикс `-КП`; заполнять приложение М-2; подставлять в договор строки КП; коммитить лист юриста, карточки клиентов и сканы.

## Success Criteria

- [ ] КП в архиве с контрагентом и без договора: подтверждённая форма даёт один номер, статус «нет», docx и строку реестра
- [ ] Второе КП того же контрагента показывает тот же номер и не увеличивает seq
- [ ] КП без `counterparty_id`: кнопка недоступна, POST отвечает отказом
- [ ] «Отмена» оставляет номер занятым. «Новый договор» выдаёт следующий seq
- [ ] ООО без КПП не подтверждается. ИП без КПП подтверждается, в преамбуле нет формулы ООО
- [ ] Картинка остаётся на экране сверки рядом с полями. Неподтверждённый разбор номер не создаёт
- [ ] Смена статуса пишет событие с пользователем и временем
- [ ] В собранном JSON шапка содержит `НомерДоговора` действующего договора. Без договора пакет не собирается
- [ ] Импорт не связывает строку с контрагентом без явного выбора менеджера

## Open Questions

Блокирующих нет. На включении: перечитать лист юриста и, если у одного контрагента две неотменённые строки, выбрать одну вручную до запуска выдачи номеров.
