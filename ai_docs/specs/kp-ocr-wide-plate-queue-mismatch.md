## Assumptions I'm Making

Подтверждено в этом чате 2026-10-24, если не сказано иное.

1. **Подтверждено.** Менеджер сделал верный жест: на сверке фото выбрал «Заменить» и нажал «Применить решения». Сообщение «Число списков не совпадает с числом фото. Список у снимков не изменён.» — баг, не ошибка менеджера.
2. **Подтверждено.** Бейдж «7 позиций требуют внимания» — это `wideLines.length` в карточке «Нестандартная ширина» (`WidePlatesInlineSection`). Семь широких строк вроде `ПБ 76-15-8 13`, не семь фото. Число строк замены (2 или 4) к отказу не относится.
3. **Подтверждено по коду.** Обычный путь «несколько фото распознаны в этой сессии, затем Применить решения» доходит до отказа так: `hydrate-draft` кладёт в store текст последней партии, фокус остаётся на первом готовом снимке, flush из‑за этого не равен `input_text`, `update` с `mode: "replace"` оставляет одну партию, zip видит `1 !== N`. Разбор — в Objective.
4. **Подтверждено по коду.** Обычная сверка одного фото (одна страница `ready`, одна партия этой сессии, менеджер список не трогал) до этого сообщения не доходит. Последняя партия и есть этот снимок, длины совпадают. Страницы `pending` / `error` и чужие старые партии тот же текст дают только когда они реально есть в очереди или в черновике; на этом пути их нет. См. Objective.
5. **Подтверждено.** Суффикс нагрузки «п» в списке у фото до apply не добавляем и не снимаем. `_align_text_batch_normalized` для `image` по-прежнему выходит сразу.
6. **Подтверждено.** `buildAutoSplitSuggestion` остаётся подсказкой из двух строк. Две и четыре строки, которые менеджер оставил в поле «Заменяющие позиции», обе применяются. Потолка в две строки нет.
7. **Подтверждено.** Заводской рез и позиции без цены в эту спеку не входят. Verify OCR не выключается. Продукт только `plates`.
8. **Подтверждено.** Нового endpoint нет. Ответ `POST .../wide-plates/resolve` уже несёт текст по партиям в `metadata.plate_batches`, если перед ним партии не схлопнули в одну.
9. **Подтверждено.** Если длины всё же расходятся по настоящей неоднозначности (в очереди осталась страница без партии, либо в черновике есть партии не из этой сессии фото), пары не угадываем: чужой список не кладём на чужое фото.
10. Коммит агент не делает без явной просьбы.

→ Если пункт неверен — править spec до плана.

## Objective

**Проблема.** «Применить решения» на сверке фото уже может успешно пройти `POST .../wide-plates/resolve`, но список рядом со снимком остаётся старым OCR. На карточке текст «Число списков не совпадает с числом фото. Список у снимков не изменён.». Широкая марка `ПБ 76-15-8 13` на месте, радио стоит на «Подтвердить».

**Проверенная причина.** Отказ пишет `syncWidePlateQueuePages`: при `plate_batches.length !== pages.length` функция не придумывает текст страниц и возвращает эту строку. На обычной сессии из нескольких фото длины расходятся не из‑за бейджа и не из‑за числа строк замены. Цепочка такая.

1. Свежая сессия: первое фото — `create` (одна партия), следующие — `append`. Успешное фото `i` пишет свой OCR в `PageSource.batchReviewText` и в `plate_batches[i]`. `input_text` — склейка этих текстов через `\n`.
2. Пока сверка не подтверждена, `confirmedBatchCount` остаётся 0, `needsBatchReview` истинно. `hydrate-draft` всё равно подставляет в `state.batchReviewText` текст последней партии (`getCurrentBatchReviewText`), даже если вызов просил `refreshBatchText: false`. Так делает и refetch черновика после каждого распознанного кадра.
3. Фокус не перескакивает на следующий кадр, если текущая страница уже `ready` (`shouldFocus` в `useMultiPageRecognize`). Экран показывает список первого фото (`activePage.batchReviewText`). Store к этому моменту — текст последнего.
4. `handleApplyWidePlates` собирает flush через `buildMergedFlushText` и в слот активного фото кладёт `state.batchReviewText`, не текст страницы на экране. Для двух фото это `последний\nпоследний`, а `input_text` — `первый\nпоследний`. Строки не равны.
5. `flushThenResolveWidePlates` при неравенстве вызывает `updateInput` с `mode: "replace"` и `image: null`. В `ProductDraftHandler.update` ветка не-append (`merged_cycle_text` ложно) ставит `batches = [source_text["batch"]]`. Для такого текстового flush `_align_text_batch_normalized` ещё и переписывает эту одну партию каноном всего текста.
6. Resolve переписывает уже одну партию и возвращает `plate_batches.length === 1`. Страниц в очереди по-прежнему N. Zip отказывает.
7. `sync-after-wide-plates` к этому моменту уже очистил `widePlateActions`. Ветка отказа возвращает в store старый `batchReviewText` активной страницы и не возвращает выбор. Карточка читает `decisions[id] ?? { action: "confirm" }`, overlay снова видит широкую марку в старом OCR и открывает карточку. Радио — «Подтвердить».

Та же склейка в одну партию случается, если менеджер поправил список у фото до кнопки или перераспознал кадр: flush честно отличается от `input_text`, `replace` всё равно оставляет одну партию, при N > 1 zip падает. Поле «Заменяющие позиции» само по себе flush не меняет: две или четыре строки там ни при чём.

**Что код не делает на обычной сверке одного фото.** Одна страница `ready` и одна партия: отравленный store совпадает с этим снимком, flush равен `input_text`, `update` не вызывается, длины 1 и 1, zip проходит. Страница `pending` или `error` даёт тот же текст ошибки только если она лежит в `multiPage.pages`: zip считает все страницы, пустой текст из flush выкидывается, партии у такого кадра нет. Мастер зовёт `multiPage.start({ productType })` без `existingDraftId`, первый кадр идёт через `create`, старые партии к сессии не примешиваются. Хук умеет `existingDraftId`, текущий мастер его не передаёт.

**Цель.** «Применить решения» на сверке одного или нескольких фото этой сессии записывает применённый список на ту же страницу очереди, где лежит снимок. Сообщение про несовпадение числа списков и фото на этом пути не появляется. Переключение снимка показывает список этого снимка. «Список верен» не возвращает уже заменённую марку.

**Пользователь:** менеджер на шаге «Плиты», экран сверки с фото.

**Успех:** после кнопки у фото с `ПБ 76-15-8 13` в списке лежат строки из поля замены (и две, и четыре), этой марки нет, карточка по ней не открывается снова. Соседний снимок сохраняет свой список.

### Сценарии

1. **Два фото, фокус на первом, список не правили.** Оба кадра `ready`. На первом в списке `ПБ 76-15-8 13` и другие широкие строки. «Заменить», в поле две или четыре строки. «Применить решения». Ошибки про число списков нет. У первого фото эти строки замены, `76-15-8` нет. У второго список тот же, что был до кнопки. Радио не падает в «Подтвердить» поверх старой марки.
2. **Одно фото.** Та же замена. Список у этого фото обновлён. Сообщения про несовпадение нет. Регрессия текущего успешного пути.
3. **Четыре строки замены.** Менеджер стёр подсказку из двух строк и вписал четыре марки. В списке этой страницы все четыре. Обрезки до двух строк нет.
4. **Правка списка у фото до кнопки.** Менеджер поправил OCR этой страницы и затем применил замену. Ошибки про число списков нет. На странице остаётся её текст с уже применённой заменой, не список другого кадра и не одна общая партия на все фото.
5. **Переключение и «Список верен».** После сценария 1 переход на второй снимок показывает его прежний список, возврат на первый — уже заменённый. «Список верен» по очереди не возвращает `ПБ 76-15-8 13`.
6. **Страница без партии.** В очереди есть `pending` или `error`, либо в черновике есть партии не из этих страниц. Zip по-прежнему отказывается и не назначает список наугад. Выбор менеджера на экране при этом не подменяется на «Подтвердить», пока список страницы не обновлён.
7. **Текст без фото.** Замена широкой плиты без очереди фото работает как сейчас. `mode: "replace"` этого пути не ломаем.

## Code Style

Сейчас flush подставляет store, а сервер на `replace` оставляет одну партию. Так делать нельзя: на экране список первого фото, в store — последнего.

```ts
const flushText = buildMergedFlushText({
  hasStarted: multiPage.hasStarted,
  pages: multiPage.pages,
  activePageId: multiPage.activeId,
  editorText: state.batchReviewText,
  singlePageText: state.batchReviewText,
});
```

```python
if merged_cycle_text:
    batches = list(metadata.get(spec.batches_key) or [])
    batches.append(source_text["batch"])
else:
    next_text = source_text["input_text"]
    batches = [source_text["batch"]]
```

Для очереди фото в слот активной страницы попадает её видимый текст. Если склейка страниц уже равна `input_text`, `update` с `mode: "replace"` не вызывается. Resolve получает те же N партий, что создали `create` и `append`, и переписывает строки внутри них. Страница `i` после успеха:

```ts
multiPage.updatePageText(page.id, batches[index].normalized_text);
```

`normalizeLineKey` и правило родителя «не откатывать `replace` в `confirm`» не ослабляем. `_align_text_batch_normalized` для `source_type != "text"` по-прежнему выходит сразу. `buildAutoSplitSuggestion` не режет поле замены.

## Boundaries

- **Always:** на сессии фото не вызывать `update` `mode: "replace"` перед wide resolve; писать применённый список на ту же страницу, что и снимок; 2 и 4 строки замены переносить целиком; при честной разной длине не угадывать пару; прогнать команды из раздела Commands.
- **Ask first:** новый endpoint, новое поле в `update` или `wide-plates/resolve`, смена смысла `mode: "replace"` для текста и для «Список верен», правка invalid width / unpriced, коммит.
- **Never:** дописывать или снимать «п» в списке у фото до apply; выключать verify OCR; ограничивать замену двумя строками; класть список одной страницы на другую, когда длины не сошлись; писать секреты; менять `tests/archived/`; удалять падающий тест без замены, которая ловит тот же разрыв.

| S1 | Несколько фото этой сессии, фокус не на последнем, список не правили, «Заменить» на 2 или 4 строки: ошибки про число списков нет, у активного фото эти строки и нет `76-15-8`, у другого фото его прежний список | vitest на flush и zip |
| S2 | Одно готовое фото этой сессии по-прежнему применяет замену и не показывает это сообщение | vitest |
| S3 | Четыре строки в поле замены попадают в список этой страницы целиком | vitest, pytest если трогали сервер |
| S4 | Правка OCR у страницы до кнопки не схлопывает партии в одну и не подменяет страницу чужим списком | vitest |
| S5 | `pending` / `error` или партии не из этой очереди: zip отказывается, список страницы не выдумывается, радио не становится «Подтвердить», пока страница не обновлена | существующий тест отказа + тест выбора |
| S6 | «Список верен» после успешного apply не возвращает заменённую марку. Текстовый ввод без фото не ломается | unit на текст страниц; регрессия flush без очереди |
| S7 | До кнопки список у фото остаётся текстом распознавания, суффикс «п» не добавляется и не снимается | `test_align_text_batch_normalized_uses_parser_text` |
| S8 | Команды из раздела Commands зелёные | локальный прогон |

Одной фразой: после «Применить решения» на сверке фото этой сессии применённый список лежит на той же странице, что и снимок, а сообщение «Число списков не совпадает с числом фото» на этом пути не появляется.
