## Objective

**Проблема.** Сохранённый план производства не совпадает с реальностью — три утечки
на пути «заказ → план → БД» (все подтверждены живыми данными):

- **A25 (Critical)** — сироты/призраки. Источник — **двойная атрибуция одной геометрии
  к разным КП**: assignment-side (slot-ledger, `finalize.py:203,261`) и track-side
  (`backfill_track_items_identity`, `_pick_best_order` max-remaining,
  `plate_attribution.py:70–86`) используют РАЗНЫЕ правила выбора и намеренно
  нешаренные consumed-счётчики (`plate_attribution.py:111–114`). Живой кейс
  `plan_20260904_124248`, «ПБ 20,6-7,2-8п»: заказано КП#4=3, КП#5=1, физически 4
  (итог сходится), атрибуция раздала 2/2. Дальше симптом-механика: pro-rated ветка
  (`plan_commit.py:614–641`) → сирота `id=197` с `day_number=NULL` (не попадает в пул —
  guard `:650`, не ловится orphan-rollback `:711–743`); у КП#5 pool=1 < items=2 →
  призрак (silent `continue`, `:703–708`). **Канал точного фикса:** и assignments
  (`finalize.py:224–226`), и track items (`from_plan.py:693–694,761–762,964–965`)
  несут один и тот же `unit_id` — матчинг по нему вместо геометрии устраняет
  кросс-КП полностью.
- **A24 (High)** — `concrete_grade=null` на всех root items трасс живого плана.
  Точка потери: `from_plan.py:_build_sequence_from_plan_impl` — три места сборки item
  (`:676`, `:747`, `:944`) копируют из cut `kp_id`/`plate_name`, но не `concrete_grade`
  (хотя `finalize.py:209` его ставит); skip-путь `plate_attribution.py` (`:319`)
  добивает grade только items без identity.
- **A26 (High, переформулировано)** — слепота детекции surplus: `coverage_verify.py:60`
  (`ok = not missing`), результат идёт только в лог (`finalize.py:157–180`),
  `is_optimization_success` на него не смотрит. ILP перепроизводить **не может**
  (доказано: `:261` точный `==`, все переменные `LpInteger`); живых surplus в планах
  не найдено (кейс КП#4/#5: физика = заказу, 4=4). Рассинхрон округления в
  `extract_cuts.py` (`:61–62`, `:119`, `:140`) — латентный дефект при `LpInteger`.
  Surplus с identity сегодня уже роняет коммит через `optimizer_extra`
  (`plan_commit.py:494–502`); молчаливый канал — rescue-leftovers (`:504–514`).

**Цель.** У каждой физической плиты на трассе есть хозяин (`kp_plate_id`), марка бетона
и ровно одна строка в БД — by construction. План с расхождением не коммитится молча.

**Пользователь:** мастер производства и завод (напрямую); менеджер (косвенно).

**Успех:** A24–A26 → `resolved` в FINDINGS.md; новый план: 100% items с маркой и хозяином;
surplus — fail-сигнал; id=197 отремонтирован.

## ASSUMPTIONS I'M MAKING

1. **Широкие плиты (>1.2 м) отсекаются на уровне КП** — подтверждено данными 2026-09-21
   (0 строк >1.21 м в `kp_plates`; 0 событий `no_sources` с 11.09). Вне скоупа;
   ERROR-лог «❌ НЕТ ИСТОЧНИКОВ» остаётся канарейкой.
2. **Марка доступна на входе пайплайна** — `enrich_orders_2d_concrete_grade` уже зовётся
   (`planning.py:120`); задача — propagation, не источник данных.
3. **Hash-сверка sequence воспроизводима** (прецедент Q3, hash `77c686bd…`); стоящего
   инструмента в репо нет — PR-1 включает мини-скрипт сверки.
4. **ILP-модель невиновна — доказано кодом**: спрос точный (`ilp_model.py:261`,
   `z_prim+z_sec+unmet == qty`), все переменные `LpInteger` (`:173–254`), `>=` в `:289`
   ограничен сверху тем же `==`. surplus может родиться только после солвера
   (post-correction, force-add). Модель не меняется.
5. **Группировка трасс по марке — отдельное решение завода** (смешение M400/M500 —
   политика, не баг атрибуции). До решения — только атрибуция и отображение.
6. **Коммиты — по просьбе.** `./run+logs.sh` не убивать.
7. **Гейт enforce — только после источника**: сначала reconciliation-pass (PR-3),
   затем неделя observe, критерий «0 новых расхождений».
8. **Ремонт id=197 — разовый скрипт с `--dry-run` и логом**: привязать id=197 к
   призрачному item (физически это плита КП#4); не общая миграция БД.
9. **Трасса = физическая правда.** При расхождении assignments ↔ track items
   коммит ориентируется на трассы; взаимозаменяемые плиты (одинаковые имя/размер
   в разных КП) реатрибутируются между КП с записью в audit-лог.

## User Stories

- Как **мастер**, открываю день производства — у каждой плиты на трассе видна марка
  бетона, а не пустота; лишних плит нет.
- Как **мастер**, вижу бейдж «план чист / N расхождений» до печати документов.
- Как **завод**, не получаю план с плитой «в плане», которая не стоит ни на одной трассе
  (и наоборот — плитой на трассе без строки в БД).
- Как **разработчик**, коммичу план с расхождением — в observe вижу отчёт в логе,
  в enforce получаю ошибку с перечнем расхождений по-русски.
- Как **аудитор**, следующим прогоном не нахожу A24/A25/A26.

### PR-3. Источник (unit_id) + коммит-гейт (A25)

**Источник (D-unit-id), первым:** track-side backfill матчит по `unit_id` —
предпочитает `kp_id`, который assignment-side уже выбрал для того же `unit_id`
(`finalize.py:224–226` ↔ `from_plan.py:693–694,761–762,964–965`); fallback на
геометрию — только при отсутствии unit_id. Тест-кейс КП#4/#5: заказ 3+1, после
фикса атрибуция 3→КП#4 и 1→КП#5 (не 2/2).

**Вторая линия:** reconciliation-pass перед mark — Σ items по КП против заказанного
для каждого `plate_name`; остаточная мисатрибуция реатрибутируется с audit-логом.
Известный непокрытый источник расхождений: `trim_assignments_to_tracks`
(rescue-треки отрезаются первыми, `kept_counts` не считает secondary_cuts —
`planning.py:286,420–433`) — гейт обязан его ловить.

**Сеть (D-gate-env/scope):** `_verify_plan_integrity()` — точка вставки **после**
`plan_commit.py:710` (там проставляется `kp_plate_id`), до финального return.
Enforce → **обязательный откат** пометок (паттерн `:734–739`) + `PlanCommitError`
по-русски с перечнем и remediation (что чинить). Legacy (`tracks_by_day=None`) →
skip + log (legacy-коммиты по построению маркируют без day_number, `:672–677`).
Направление pool→item уже детектится с откатом (`:711–743`) — не дублируем;
новое: item→pool, NULL-day, rescue-leftovers в отчёт.

**Ремонт id=197 — двусторонний:** item'у в plan JSON проставить `kp_id=4` +
`kp_plate_id=197` (сейчас `kp_id=5`, `kp_plate_id=None`); строке id=197 —
`day_number=2`. Пост-проверка: гейт observe по отремонтированному плану — чисто.
`--dry-run` по умолчанию [ask first на запуск].

Переход observe → enforce: неделя без новых расхождений ПОСЛЕ внедрения источника.

## Boundaries

- **Always:** observe-first для гейта; hash-сверка sequence на PR-1/PR-2; зелёный
  `pytest -q` перед merge; русские сообщения; минимальный diff; отдельный PR на шаг.
- **Ask first:** запуск ремонтного скрипта по БД (id=197); новые env сверх
  `PLAN_COMMIT_GATE`; включение enforce-режима; смена семантики `opt_ok`;
  группировка трасс по марке (решение завода).
- **Never:** изменять ILP-ограничения; миграции/изменения схемы БД; глушить ERROR
  «❌ НЕТ ИСТОЧНИКОВ»; коммит без просьбы; убивать `./run+logs.sh`; менять логику
  ПОСТРОЕНИЯ RESCUE/fallback-трасс (их атрибуция/покрытие гейтом — входит в скоуп).
