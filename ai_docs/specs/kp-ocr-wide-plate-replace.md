## Assumptions I'm Making

1. **Подтверждено.** Баг — карточка «Нестандартная ширина» для плит **шире 12 дм** (`WidePlatesInlineSection`, `POST .../wide-plates/resolve`). Заводской рез (`InvalidWidthsInlineSection`) и позиции без цены не входят в эту спеку.
2. «Работает при OCR» значит: менеджер на сверке фото выбрал «Заменить», оставил или поправил текст замен и нажал «Применить решения». Широкая марка исчезает из списка рядом с фото, на её месте строки из поля «Заменяющие позиции». То же для «Исключить» (строки нет) и «Подтвердить» (строка остаётся, карточка по ней закрывается).
3. **Подтверждено 2026-10-23.** Суффикс нагрузки оставляем как есть. До «Применить решения» список у фото — текст распознавания, без подстановки и без снятия `п`. `_align_text_batch_normalized` для `image` по-прежнему не переписывает партию.
4. Проверки OCR (`ocr_corrections`, второй проход verify) не выключаются и не переписываются.
5. Продукт только `plates`. Сваи, ступени, марши, ФБС не трогаем.
6. Текстовый ввод без фото уже применяет замену. Этот путь не должен сломаться.
7. **Подтверждено.** Исправление живёт в той же очереди, что и фото: у каждой страницы распознавания есть файл снимка и свой текст списка (`PageSource.batchReviewText`). «Применить решения» пишет новый список в текст **этой** страницы. Переключение снимка в галерее показывает список этой страницы. «Список верен» отправляет текст из очереди страниц и не возвращает уже заменённую марку. Ящик «исходные фото» после подтверждения по-прежнему хранит только снимки, без строк плит.
8. Коммит агент не делает без явной просьбы.

→ Если пункт неверен — править spec до плана.

## Decisions locked

| # | Тема | Решение |
|---|------|---------|
| D1 | Когда чинить | В момент «Применить решения», не в момент распознавания |
| D2 | Суффикс нагрузки | Как сейчас. До apply в редакторе у фото нет подстановки `п`. Совпадение замены терпит марку и с `п`, и без неё |
| D3 | Склейка решения | Выбор «Заменить» / «Исключить» / «Подтвердить» на строке OCR доходит до сервера как это же действие. Молчаливый откат в `confirm`, когда менеджер выбрал `replace`, — ошибка |
| D4 | Какая строка одна и та же | `ПБ 76-15-8 13`, `ПБ 76-15-8п 13`, `76-15-8 13`, лишние пробелы и «шт» — одна позиция. Ведущий номер строки в редакторе (`11.`) — номер UI, в текст марки не входит |
| D5 | Где лежит результат | В очереди страниц, в том же элементе, что и фото. Store только повторяет текст активной страницы. Карточка по решённой строке закрыта и не открывается от старого OCR этой страницы |
| D6 | После провала | Текст ошибки в карточке. Список не делает вид, что замена прошла |
| D7 | Подсказка 12 + остаток | `ПБ 76-15-8 13` → `ПБ 76-12-8 13` и `ПБ 76-3.0-8 13`. Количество — то, что осталось в поле. `3.0` — это 300 мм, гейт «шире 12 дм» её не открывает |
| D8 | Что не меняем | Verify OCR, гейты invalid width и unpriced, правило «Список верен» без решения по ширине, блокировка «Готово, далее», пока wide не решён |

## Objective

**Проблема.** На сверке фото карточка предлагает замену широкой плиты, но «Применить решения» не меняет список рядом со снимком. Тот же жест по набранному тексту список меняет.

Два разрыва, оба нужны для фикса:

1. **Решение не приклеивается к строке OCR.** `wide_plate_lines` собраны по канону парсера (`ПБ 76-15-8п 13`). Редактор и карточка смотрят на сырой OCR (`ПБ 76-15-8 13`). Для текста `_align_text_batch_normalized` делает эти строки одинаковыми. Для `image` функция выходит сразу, партия остаётся сырым OCR. Если ключи не совпали, `buildWidePlateResolveDecisions` подставляет `confirm`. Сервер отвечает успехом и плиту не заменяет.
2. **Успешный ответ не попадает в редактор у фото.** `sync-after-wide-plates` пишет новый текст только в store. Пока идёт сессия фото, редактор читает `multiPage` → `activePage.batchReviewText`. Эта строка после resolve не обновляется. Overlay снова видит ширину > 12 дм в старом тексте и открывает карточку заново. Для Apply AI это уже закрыто: новый текст пишется и в store, и в активную страницу (`planApplyAiSessionSync`).

**Цель.** «Заменить» на сверке фото делает то же, что при текстовом вводе: широкая марка заменяется строками из поля, список у фото это показывает, карточка по ней гаснет.

**Пользователь:** менеджер на шаге «Плиты», экран сверки с фото.

**Успех:** после «Применить решения» список рядом с фото содержит замены, исходной широкой марки в нём нет, карточка по ней не возвращается. Текстовый ввод ведёт себя как сейчас.

### Сценарии

1. **Одно фото, замена.** Распознано `ПБ 76-15-8 13` (ширина 15 дм). В карточке «Заменить», в поле две строки подсказки. «Применить решения». В списке у фото эти две строки, `76-15-8` нет. Карточки по этой позиции нет. «Готово, далее» не держится из‑за неё.
2. **Суффикс `п`.** Сервер хранит `ПБ 76-15-8п 13`, на экране `ПБ 76-15-8 13`. Действие всё равно `replace`, не `confirm`.
3. **Исключить.** Та же пара строк. «Исключить» убирает марку из списка у фото. Замены не появляются.
4. **Подтвердить.** Марка остаётся в списке. Карточка по ней закрыта и не открывается снова, пока менеджер сам не сделает строку шире 12 дм.
5. **Пустая или неразобранная замена.** Поле замены пустое или ни одна строка не читается как плита. Карточка показывает ошибку. Старая широкая марка на месте.
6. **Текст без фото.** `ПБ 68-15-8п 2` → замена на `ПБ 68-12-8п 2` и `ПБ 68-3.0-8п 2`. Список в редакторе обновляется, как сейчас.
7. **Два фото в очереди.** У каждого снимка свой текст. На втором кадре заменили широкую плиту: в элементе очереди второго снимка лежит новый список, у первого — его прежний. Переключение галереи показывает список выбранного снимка. «Список верен» по обоим кадрам не возвращает заменённую марку второго.
8. **Правка поля.** Менеджер стёр подсказку и вписал свои две марки с тем же количеством. В списке у фото именно они.

## Code Style

Имя действия и текст замены доезжают до resolve даже если id карточки — `live-wide-0`, а id на сервере — `wide-1`. Совпадение по нормализованной марке, не по равенству сырой строки.

```ts
const decision =
  decisionsById[flushed.id] ??
  (live ? decisionsById[live.id] : undefined);

return {
  lineId: flushed.id,
  sourceLine: flushed.line,
  action: decision?.action ?? "confirm",
  replacementText: decision?.replacementText ?? "",
};
```

`normalizeLineKey("ПБ 76-15-8 13")` и `normalizeLineKey("ПБ 76-15-8п 13")` дают один ключ. Если ключ не найден, действие не подменяется на `confirm` молча: запрос либо не шлёт эту строку как решённую, либо сервер отвечает уже существующей ошибкой «позиция не найдена в списке», и карточка её показывает.

После успеха новый текст пишется в элемент очереди активной страницы (`PageSource.batchReviewText`). Store получает ту же строку, потому что редактор при сессии фото читает очередь, а не отдельное поле. Переключение страницы читает текст той страницы, куда ушли.

```ts
dispatch({ type: "set-batch-review-text", text: nextText });
if (multiPage.hasStarted && multiPage.activeId) {
  multiPage.updatePageText(multiPage.activeId, nextText);
}
```

`_align_text_batch_normalized` для `source_type != "text"` по-прежнему выходит сразу. Тест `test_align_text_batch_normalized_uses_parser_text` остаётся зелёным.

## Boundaries

- **Always:** не откатывать `replace` в `confirm`; после успеха писать список в ту же страницу очереди, где лежит фото; показать ошибку, если строка не найдена или замена пустая; прогнать команды из раздела Commands.
- **Ask first:** новый endpoint, смена контракта `wide-plates/resolve`, подмена OCR каноном сразу при распознавании, правка invalid width / unpriced, коммит.
- **Never:** отключать verify OCR; писать секреты; менять `tests/archived/`; удалять падающий тест без замены, которая ловит тот же разрыв.
