# Spec: имена карточек на сервере, привязка КП и одна отправка в 1С

> **Статус:** SPECIFY. Код и серверная база по этой спеке ещё не менялись.  
> **Дата:** 2026-10-27  
> **База:** только сервер `himweb`, файл `/var/lib/docker/volumes/plan_zavod_web_split_data/_data/plita.db`.  
> **Не это:** дырка в сохранении КП и путь `EXCHANGE_EXPORT_DIR`. Их чиним следующим заходом, после того как один живой файл лежит в папке 1С.

## Assumptions I'm Making

1. «Образец имени 1С, как в старой базе» — это имя строки `counterparties.name`, тем же правилом, которым 21 октября на ноутбуке переписали `imported_name`. На сервер строки с ноутбука не копируются: там другой набор договоров. Договора `0001/10/26` на сервере нет.
2. Сейчас на сервере 185 карточек, связаны со справочником 3. У 184 заполнено `imported_name`, и это часто имя бланка, не имя справочника. Пример: карточка `ООО "ПСК "ГЕФЕСТ"`, в справочнике `ПСК ГЕФЕСТ ООО`.
3. Привязка КП — это запись `counterparty_id`, `customer_inn` и `customer_kpp` на КП и `counterparty_id` на одну карточку. Номер договора на КП по-прежнему не хранится.
4. В 1С уходит один файл одного КП. Остальные привязанные КП остаются в архиве и сами не отправляются.
5. Пустой `guid_1c` контрагента отправку не останавливает. Пустой GUID марки останавливает, и его не выдумывают.
6. Приложение уже запущено и базу держит открытой. Пишем в неё с сервера, контейнер не пересоздаём.

→ Если нужно отправить все привязанные КП, а не одно, или переписать ещё и `customer_name` в списке архива — это другое решение, в этой спеке его нет.

## Decisions locked

| # | Тема | Решение |
|---|------|---------|
| D1 | Где работать | Только серверная `plita.db`. Ноутбук, `pb.db` и справочник `counterparties` не пишутся |
| D2 | Имя карточки | `imported_name` становится `counterparties.name`, если по ИНН карточки в справочнике одно имя. Сравнение имён: регистр, `ё/е`, лишние пробелы. Несколько разных имён на один ИНН — карточку не трогать |
| D3 | Что не стирать | `full_name`, `short_name`, реквизиты бланка, номер, дата, статус. Связь карточки на шаге переименования не ставить |
| D4 | Какое КП | Статус `в архиве` и пустой `counterparty_id`. Уже отправленные («на согласовании», со счётом) не трогать |
| D5 | Какая карточка | Сначала ИНН КП, если он есть и у него ровно один активный клиент. Иначе точное имя КП после той же нормализации, если оно совпало ровно с одной карточкой, а ИНН этой карточки — ровно с одним активным клиентом. Несколько карточек одного ИНН: самая поздняя `contract_date`, при равенстве больший `id`. Остальные карточки этого ИНН без связи |
| D6 | Нет карточки | Имя есть в справочнике, карточки нет — КП не привязывать и карточку не создавать. Так остаются Атлантстройгрупп, Стройтех, Экострой, Геострой, Олимп |
| D7 | Имя на КП | `customer_name` не переписывать. В JSON имя берёт уже существующий код из справочника |
| D8 | Пробная отправка | Одно самое новое привязанное КП с `product_type = plates`. Склад `Склад Готовой Продукции`. Остальные не отправлять |
| D9 | Куда класть файл | Код пишет туда, куда умеет сейчас. Этот один файл затем копируется в `/opt/plan_zavod/data/exchange/to_1c`. Настройки контейнера и исходники не меняются |
| D10 | Ответ 1С | `order_number_1c` сами не пишем. Номер счёта появится только из настоящего `otvet_*.json` |

## Objective

Менеджер на сайте видит карточки договоров под теми же именами, что справочник 1С, а КП с однозначной карточкой можно отправить без повторного ввода кода. Один такой файл оказывается в папке, из которой 1С уже забирала счета до 9 октября.

Успех этой задачи — данные и один файл. Кнопка для следующих КП без карточки по-прежнему может сказать «Сначала занесите контрагента»: это дырка кода, её закрываем после.

### Сценарии

1. **Гефест.** Карточка `0808/03/25` получает имя `ПСК ГЕФЕСТ ООО`. КП, где имя или ИНН `7604304420` однозначны, получают клиента справочника этой карточки. В файл, если пробным выбран этот клиент, попадают имя справочника, его код, ИНН и номер `0808/03/25`.
2. **Два имени на один ИНН.** Карточка остаётся со старым `imported_name`. КП к ней не привязывается.
3. **Экострой, Геострой, Олимп.** В справочнике по два активных клиента с одним именем, карточки нет. КП №155, 156, 157, 159 остаются без `counterparty_id`.
4. **Атлантстройгрупп и Стройтех.** Клиент в справочнике один, карточки нет. КП №158, 160, 161 остаются без связи. Новая карточка в этой задаче не создаётся.
5. **Уже ушедшие счета.** КП №31, 46, 48, 52, 56, 59, 63, 67, 81 не меняются. Их номера счетов и три уже связанные карточки не переписываются заново, если имя уже совпало со справочником.

## Tech Stack

Живой сервер `himweb` (`5.129.200.30`), SQLite серверной `plita.db`, уже запущенный контейнер `plan_zavod-backend-1`. Одноразовый скрипт на сервере в `/tmp`, в образ и в репозиторий не входит. Новых библиотек нет. Код FastAPI и React в этой задаче не собирается и не выкладывается.

## Commands

Проверка до записи, с сервера, база только на чтение:

```bash
ssh -o BatchMode=yes himweb 'python3 - << "PY"
import sqlite3
path = "/var/lib/docker/volumes/plan_zavod_web_split_data/_data/plita.db"
conn = sqlite3.connect(f"file:{path}?mode=ro", uri=True)
print(conn.execute("SELECT COUNT(*) FROM counterparties").fetchone()[0])
print(conn.execute("SELECT COUNT(*), SUM(counterparty_id IS NOT NULL) FROM supply_contract").fetchone())
print(conn.execute("SELECT COUNT(*), SUM(counterparty_id IS NULL) FROM KP_offers").fetchone())
PY'
```

Копия базы до первой записи — `sqlite3 .backup` в файл рядом с томом, с меткой времени. Обычный `cp` живой базы не использовать. Контейнер не останавливать.

Отправка — уже существующий `POST` архива с телом `{"warehouse": "Склад Готовой Продукции"}`. Новый маршрут не добавлять.

После копии файла:

```bash
ssh -o BatchMode=yes himweb 'ls -l /opt/plan_zavod/data/exchange/to_1c /srv/exchange-1c/to_1c'
```

Оба пути — один каталог через bind. В списке должен быть один новый `new_<kp_id>_*.json`.

## Code Style

Одноразовая запись на сервере делает только то, что уже делает правило имени. Справочник и связь карточки в этом шаге не меняются:

```python
chosen = choose_directory_name(directory_names, inn)
if chosen is None or chosen == visible:
    return visible
conn.execute(
    "UPDATE supply_contract SET imported_name = ? WHERE id = ?",
    (chosen, card_id),
)
```

Привязка КП — отдельный следующий `UPDATE`. Имя клиента на КП в него не входит.

## Testing Strategy

Автотесты репозитория эту серверную базу не открывают. Проверка — запросы до и после и содержимое одного JSON.

До записи сохранить счётчики: число строк `counterparties`, число карточек, число КП, список `kp_id` у которых уже есть `counterparty_id`, список трёх уже связанных договоров.

После переименования: у карточки с однозначным именем `imported_name` равен этому имени; у неоднозначной ИНН строка та же; число строк справочника и каждый `code_1c` те же; `counterparty_id` карточек те же, что до этого шага.

После привязки: у подошедшего КП заполнены `counterparty_id`, `customer_inn`, `customer_kpp` выбранного активного клиента; у выбранной карточки тот же `counterparty_id`; у КП без карточки или с двумя клиентами на одно имя все четыре поля клиента как были; `customer_name` и `order_number_1c` ни у кого не изменились.

После отправки: статус пробного КП `на согласовании`; в JSON `Клиент` и `Контрагент.Наименование` равны имени справочника, `Контрагент.Код` и ИНН — этой строки, `НомерДоговора` — номер выбранной карточки; файл лежит в `/opt/plan_zavod/data/exchange/to_1c`; `order_number_1c` пустой.

Если существующая проверка GUID марки отказывает, файл не копировать, статус КП не подменять вручную, другое КП вместо него не отправлять. В отчёте остаются марки без GUID.

## Boundaries

- Always: копия базы через `.backup` до первой записи; сначала переименование, потом привязка, потом одна отправка; неоднозначные ИНН и КП без карточки оставить и перечислить; проверить, что bind-папка 1С и `/srv/exchange-1c/to_1c` показывают один и тот же файл.
- Ask first: отправить второе КП; создать недостающую карточку; переписать `customer_name` у уже сохранённых КП; остановить контейнер.
- Never: править код, compose, `.env` и образ; писать ноутбукную `plita.db`; менять строки `counterparties` или `pb.db`; ставить выдуманный `order_number_1c`; отправлять все привязанные КП; удалять карточки; связывать второй действующий договор тому клиенту, у которого связь уже есть.

## Success Criteria

- Серверная копия `plita.db` снята до изменений и лежит рядом с томом.
- Карточки с однозначным именем справочника показывают это имя в `imported_name`. Карточки с двумя разными именами на один ИНН не изменились.
- Каждое КП из D4, для которого D5 нашёл одну карточку и одного клиента, связано с этим клиентом, и эта карточка тоже.
- КП №155, 156, 157, 158, 159, 160 и 161 остаются без `counterparty_id`, потому что карточки нет или имя не одно.
- В `/opt/plan_zavod/data/exchange/to_1c` лежит один новый `new_<kp_id>_*.json` пробного КП. Внутри имя, код и ИНН справочника и номер выбранной карточки. Статус этого КП — `на согласовании`.
- Исходники репозитория и настройки контейнера не изменились.
