> **Источник идеи:** [`ai_docs/ideas/kp-1c-delta.md`](../ideas/kp-1c-delta.md)

> **Фаза SDD:** SPECIFY ✅ → PLAN
> **Статус:** договор с 1С зафиксирован живым файлом КП 31 и ответом `otvet`. Код не писать до приёмки плана.
> **Дата:** 2026-10-01
> **Заменяет в контракте обмена:** имя документа, ключи `event` / `action` / `НомерЗаказа` и имена `invoice_create_` / `invoice_update_` из [`archive-on-approval.md`](archive-on-approval.md). ## Assumptions I'm Making

1. Кнопку «Отправить исправление» нажимает менеджер КП. Роли те же, что у карточки архива.
2. Утверждённое тело — файл `kp_offer_31_20260929.json`: документ «КоммерческоеПредложение» и строки с суммами. Текущий файл `invoice_create_*.json` («Счёт на оплату», ключи `event` и `action`) 1С не подтверждал.
3. `delta_` содержит весь заказ после правки. 1С загружает его вместо текущего состава заказа. Отдельного списка изменений нет.
4. `Номер_ЗК` из ответа пишется в уже существующую `KP_offers.order_number_1c`. Шапка, спецификация и «В производство» продолжают читать эту колонку.
5. Два УИД — новые колонки `uid_order_1c` и `uid_kp_1c`. Целый JSON ответа в базе не хранится.
6. Для КП 31 колонки сейчас пустые. Три значения из присланного ответа записываются один раз. Повтор с теми же значениями ничего не меняет. Другие значения поверх уже записанных не пишутся.
7. Поле `Статус` в JSON — литерал «в архиве», как в принятом файле. Внутренний статус «на согласовании» в файл не попадает.
8. `Дата` в файле — `YYYY-MM-DD`. Если в базе дата хранится как `DD.MM.YYYY`, сборщик приводит её к ISO.
9. Разбор следующего ответа 1С в эту спеку не входит. Колонки названы так, чтобы поздний разбор только заполнял их.

→ Если что-то из этого неверно — править spec до кода.

## Decisions locked

| # | Тема | Решение |
|---|------|---------|
| D1 | Имя документа | `КоммерческоеПредложение` и в `new_`, и в `delta_` |
| D2 | Имена файлов | `new_{kp_id}_{время}.json` и `delta_{kp_id}_{время}.json`. Время — `YYYYMMDDTHHMMSSffffff`, как сейчас, чтобы второй файл не затирал первый. Маски 1С: `new_%.json`, `delta_%.json` |
| D3 | Чего нет в JSON | Ключей `event`, `action`, `НомерЗаказа`. `Номер_КП` и `Описание` из ответа в исходящий файл не входят |
| D4 | `new_` | Полное тело без `УИД_ЗК`, `Номер_ЗК`, `УИД_КП`. Этих ключей в файле нет, в том числе со значением null |
| D5 | `delta_` | То же тело. Первые три ключа — `УИД_ЗК`, `Номер_ЗК`, `УИД_КП`. Дальше документ как в `new_` |
| D6 | Состав дельты | Все текущие строки КП и итоги, пересчитанные по этим строкам |
| D7 | Хранение | `order_number_1c` = `Номер_ЗК`. `uid_order_1c` = `УИД_ЗК`. `uid_kp_1c` = `УИД_КП` |
| D8 | Запись идентификаторов | Пустые колонки можно заполнить. Если хотя бы одна уже заполнена и новое значение отличается — отказ, строка КП не меняется |
| D9 | Кнопка исправления | Пишет файл только при статусе «на согласовании», всех трёх заполненных полях и хеше состава, отличном от `invoice_snapshot_hash` |
| D10 | Шапка | Непустой `order_number_1c` показывается как сейчас: «Счёт {номер}». Поля ввода нет |
| D11 | КП 31 | Пока все три колонки пустые, записать номер `469`, УИД заказа `9cfb5882-bd7e-11f1-9e1d-d8bbc1d1be1f`, УИД КП `9cfb5881-bd7e-11f1-9e1d-d8bbc1d1be1f` |
| D12 | Уже ушедший файл | `kp_offer_31_20260929.json` и лежащие `invoice_create_*` эта спека не переписывает и не удаляет |

## Objective

Менеджер правит состав КП, которое 1С уже приняла, и кнопкой «Отправить исправление» кладёт в папку обмена один файл со всем новым заказом и идентификаторами того заказа клиента. Первая отправка нового КП кладёт файл той же формы, без идентификаторов, под именем `new_`.

Успех: файл попадает в маску 1С; дельта КП 31 содержит 24 строки, итог 1 859 443,20 и НДС 335 309,43; в файле есть УИД и номер 469; карточка показывает 469; без трёх идентификаторов файл исправления не пишется.

### Пользователь

Менеджер по продажам в карточке коммерческого архива.

### Сценарии

1. **Первая отправка.** Условия прежние: контрагент, действующий договор, GUID строк, выбранный склад. Файл `new_{kp_id}_{время}.json`. Статус становится «на согласовании». Снимок состава запоминается. Трёх идентификаторов в файле нет.
2. **На согласовании, идентификаторов нет.** Шапка: «Счёт · номер ещё не пришёл из 1С». «Отправить исправление» нет. «В производство» серое, пока нет номера.
3. **Идентификаторы записаны, состав не менялся.** Шапка: «Счёт 469» для КП 31. Тихая строка «В 1С ушло без правок». Файл не пишется.
4. **Идентификаторы записаны, состав изменён.** Фиолетовая «Отправить исправление». Файл `delta_{kp_id}_{время}.json` содержит три идентификатора и весь текущий состав. Статус не меняется. После успеха снимок обновляется, кнопка гаснет.
5. **Повтор той же дельты.** Состав совпал со снимком. Второй файл не пишется.
6. **Чужой УИД поверх записанного.** Запись отказывается. Уже лежащие номер и УИД остаются.
7. **КП 31 после этой спеки.** Колонки получают три значения из ответа. Шапка показывает 469. Состав из 24 строк отличается от снимка первой отправки, кнопка исправления доступна. `paid_at` пустой, «В производство» остаётся серым до оплаты.

## JSON

Кодировка UTF-8. Каталог — `exchange_export_dir`. Сборщик возвращает словарь. Файл пишет сервис архива после ворот GUID, контрагента и договора.

Порядок ключей шапки `new_`:

| Поле | Значение |
|---|---|
| `Документ` | `КоммерческоеПредложение` |
| `НомерВПриложении` | `kp_id` |
| `Дата` | `YYYY-MM-DD` |
| `Организация` | `ООО «Комбинат ЖБК»` |
| `Клиент` | наименование контрагента |
| `Контрагент` | наименование, код 1С, GUID или null, ИНН, КПП |
| `НомерДоговора` | действующий договор, сразу после `Контрагент` |
| `КонтактноеЛицо` | null |
| `Валюта` | `RUB` |
| `ХозяйственнаяОперация` | `РеализацияКлиенту` |
| `Налогообложение` | `ОблагаетсяНДС` |
| `ЦенаВключаетНДС` | true |
| `Статус` | `в архиве` |
| `Комментарий` | пустая строка |
| `Менеджер` | менеджер КП |
| `Автор` | тот же менеджер |
| `Склад` | сохранённое имя склада |
| `Самовывоз` | истина, когда доставка нулевая; иначе ложь |
| `ПроцентСкидки` | скидка заказа |
| `СуммаСкидки` | сумма скидок строк |
| `СуммаНДС` | сумма НДС строк |
| `СуммаДокумента` | сумма `СуммаСНДС` строк |
| `Товары` | массив строк |

В `delta_` перед `Документ` стоят `УИД_ЗК`, `Номер_ЗК`, `УИД_КП`. Остальной порядок тот же.

Строка `Товары`, в этом порядке:

| Поле | Значение |
|---|---|
| `Номенклатура` | имя строки |
| `GUID` | GUID 1С после `assert_invoice_guids` |
| `Характеристика` | null |
| `Количество` | количество |
| `ЕдиницаИзмерения` | `шт` |
| `ВидЦены` | `Продажная` |
| `Цена` | цена карточки до скидки, с НДС |
| `ПроцентСкидки` | скидка заказа |
| `СуммаСкидки` | скидка строки в рублях |
| `Сумма` | сумма без НДС |
| `СтавкаНДС` | `22%` |
| `СуммаНДС` | НДС строки |
| `СуммаСНДС` | к оплате по строке |
| `СуммаДоставки` | доля доставки после скидки, как в спеке склада; ноль при самовывозе |

Формулы, копейка, округление half up. `Цена` уже включает НДС.

- `СуммаСНДС` = округление(`Цена` × (1 − `ПроцентСкидки` / 100) × `Количество`, 2) + `СуммаДоставки`
- `СуммаНДС` = округление(`СуммаСНДС` × 22 / 122, 2)
- `Сумма` = `СуммаСНДС` − `СуммаНДС`
- `СуммаСкидки` = округление(`Цена` × `Количество` × `ПроцентСкидки` / 100, 2)

Шапка считается по строкам файла, не по сырым `vat_amount` / `total_amount` карточки, если те разошлись с построчным округлением. Для КП 31 скидка 0 и доставка 0: `СуммаДокумента` 1859443.20, `СуммаНДС` 335309.43, последняя строка — «Плиты ПБ 75-12-8п», количество 10, цена 29316.0, GUID `cf7fc182-ee4c-11e9-8f4e-04d9f5387845`.

`attach_contract_number` принимает «КоммерческоеПредложение». Имя «Счёт на оплату» не ломает старые вызовы штампа.

## Данные

На `KP_offers` уже есть `order_number_1c` и `invoice_snapshot_hash`. Эта спека добавляет:

```sql
ALTER TABLE KP_offers ADD COLUMN uid_order_1c TEXT;
ALTER TABLE KP_offers ADD COLUMN uid_kp_1c TEXT;
```

Пустая колонка — идентификатор ещё не пришёл. `order_status_1c` эта спека не заполняет.

Заполнение КП 31 выполняется только когда `kp_id = 31` и все три колонки пустые:

| Колонка | Значение |
|---|---|
| `order_number_1c` | `469` |
| `uid_order_1c` | `9cfb5882-bd7e-11f1-9e1d-d8bbc1d1be1f` |
| `uid_kp_1c` | `9cfb5881-bd7e-11f1-9e1d-d8bbc1d1be1f` |

Свежая тестовая база без КП 31 этой записью не заполняется.

Правило отказа при расхождении живёт в коде записи, не только в миграции: непустое поле и другое новое значение — ошибка по-русски, файл не пишется, колонки не меняются.

Хеш снимка остаётся прежним: строки, скидка заказа, доставка, итог. Кнопка сравнивает текущий состав с `invoice_snapshot_hash`.

## API

Новых маршрутов нет. Меняется тело уже существующих.

| Метод | Путь | Что меняется |
|---|---|---|
| POST | `/commercial/archive/{kp_id}/invoice-export` | пишет `new_{kp_id}_{время}.json` телом этой спеки |
| POST | `/commercial/archive/{kp_id}/invoice-correction` | пишет `delta_{kp_id}_{время}.json`, только когда заполнены `order_number_1c`, `uid_order_1c` и `uid_kp_1c` и снимок состава изменился |

Отказ — 422 с русским текстом. Неполный набор идентификаторов: исправление не отправляется, причина называет, что номер заказа из 1С ещё не записан.

Карточка отдаёт `order_number_1c` как сейчас. Два УИД на экран не выводятся.

## Code Style

Ошибки по-русски. Сборщик не пишет файл. Внутренний признак «первая отправка или исправление» выбирает имя файла и наличие трёх ключей. В словарь JSON английские `event` и `action` не кладутся.

```python
document = build_invoice_document(
    offer,
    action="update",
    order_number="469",
    uid_order="9cfb5882-bd7e-11f1-9e1d-d8bbc1d1be1f",
    uid_kp="9cfb5881-bd7e-11f1-9e1d-d8bbc1d1be1f",
)
assert document["Документ"] == "КоммерческоеПредложение"
assert list(document)[:3] == ["УИД_ЗК", "Номер_ЗК", "УИД_КП"]
assert "event" not in document
```

Кнопка на клиенте JSON не собирает.

## Testing Strategy

| Слой | Где | Что |
|---|---|---|
| Документ | `tests/test_archive_invoice_export.py` | `new`: «КоммерческоеПредложение», нет трёх идентификаторов, нет `event`/`action`/`НомерЗаказа`; строки содержат суммы, НДС, вид цены, единицу; шапка сходится со строками |
| Дельта | там же | три ключа в начале; значения равны переданным; состав — все строки |
| Отказ сборки | там же | исправление без номера или без любого УИД не собирается |
| Файл | там же | успешная первая отправка — `new_{id}_*.json`; исправление — `delta_{id}_*.json`; без трёх полей файла нет |
| Запись КП 31 | тест схемы или сервиса | пустые колонки получают три значения; повтор тех же значений не ошибка; другое значение не затирает уже записанное |
| Шапка | `OfferDetailsDrawer.test.tsx` | при `order_number_1c = 469` заголовок «Счёт 469»; пустая колонка — прежняя фраза про номер |
| Договор | `tests/test_supply_contract.py` | штамп принимает «КоммерческоеПредложение» |

Живая 1С и папка завода в тестах не используются. Каталог выгрузки — временный.

## Boundaries

- **Always:** файл в маске `new_` или `delta_`; дельта содержит весь состав и три идентификатора; `new_` этих ключей не содержит; суммы шапки равны суммам строк; исправление без любого из трёх полей не пишется; другой УИД не затирает записанный; ошибки по-русски; тесты на тело, имя файла и отказ.
- **Ask first:** другая маска или каталог входящего ответа; разбор `otvet`; другое имя ключей `УИД_ЗК` / `Номер_ЗК` / `УИД_КП`; смена литерала `Статус`; единица измерения кроме `шт`.
- **Never:** HTTP в 1С; поле ввода номера; показывать JSON и УИД менеджеру; хранить тело ответа в базе; слать дельту одной строкой; переписывать уже лежащий `kp_offer_31`; коммитить файлы из папки обмена.

## Success Criteria

- [ ] Первая отправка пишет `new_{kp_id}_{время}.json` с документом «КоммерческоеПредложение» и без `УИД_ЗК`, `Номер_ЗК`, `УИД_КП`
- [ ] В файле нет ключей `event`, `action`, `НомерЗаказа`
- [ ] Строка содержит номенклатуру, GUID, характеристику, количество, единицу, вид цены, цену, скидку, сумму, ставку НДС, суммы НДС и с НДС, сумму доставки
- [ ] `СуммаДокумента` и `СуммаНДС` равны сумме строк файла
- [ ] Исправление пишет `delta_{kp_id}_{время}.json`, первые ключи — три идентификатора, дальше весь текущий состав
- [ ] Без любого из трёх полей файл исправления не создаётся, статус не меняется
- [ ] Повторно нажатая кнопка при том же снимке второй файл не пишет
- [ ] КП 31 с пустыми колонками получает номер 469 и два УИД; шапка показывает «Счёт 469»
- [ ] Попытка записать другой УИД поверх уже лежащего не меняет колонки
- [ ] УИД на карточке не отображаются. Поля ввода номера нет
