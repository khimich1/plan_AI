# Spec: КП с существующим договором уходит в 1С

> **Статус:** IMPLEMENT ✅. Тесты зелёные: `.venv/bin/python -m pytest tests/test_kp_invoice_existing_contract.py tests/test_archive_invoice_export.py -q` — 53 passed.  
> **План:** [`ai_docs/develop/plans/2026-10-21-kp-invoice-existing-contract.md`](../develop/plans/2026-10-21-kp-invoice-existing-contract.md)  
> **Дата:** 2026-10-21  
> **База:** `plita.db`  
> **Рядом, не это:** импорт GUID из 1С, правка бланка договора, файл «спорные ИНН», ослабление гейта номенклатуры.

## Assumptions I'm Making

1. «Нужная информация уже в базе» — это номер договора, имя, ИНН и КПП организации и код 1С на строке справочника. GUID контрагента в базе нет: `guid_1c` пустой у всех 4413 строк. Отправка его не ждёт и не выдумывает.
2. Договор ищется для того контрагента, который уже стоит на КП (`KP_offers.counterparty_id`). Пример: КП №15 «КАРАВАН ООО» указывает на справочник id 1362, код `00-00003032`. Договор `0882/09/25` с тем же ИНН `3528341614` имеет пустой `counterparty_id`, поэтому кнопки «Отправить в 1С» пишет «Нет действующего договора поставки».
3. На 2026-10-21 из 186 договоров связан с справочником один (`0001/10/26`). Ещё 181 ИНН указывают ровно на одного активного клиента. Четыре таких ИНН имеют 2–3 договора (Секлюцкий — три). У трёх ИНН в справочнике больше одной строки. Одного ИНН в справочнике нет.
4. В 1С уходит один номер действующего договора. Несколько договоров одного ИНН остаются карточками. Связь со справочником получает только один, самый поздний по дате договора, при равенстве даты — с большим `id`.
5. Неполный бланк («не полные») печать Word/PDF по-прежнему запрещает. Отправку в 1С он не блокирует.
6. Имя в файле для 1С берётся из справочника, если КП уже связан (`party.name`), иначе с карточки КП. Это текущий код. Имя на экране КП остаётся именем карточки.

→ Если GUID контрагента всё же обязателен для приёмки файла в 1С — это отдельная выгрузка, в этой спеке его нет.

## Decisions locked

| # | Тема | Решение |
|---|------|---------|
| L1 | Связь | У договора с пустым `counterparty_id` и ИНН ровно одного активного клиента проставить `counterparty_id` этого клиента |
| L2 | Какой договор | Самый поздний `contract_date`, при равенстве — больший `id`. Остальные договоры этого ИНН не связываются: индекс одного действующего договора на клиента |
| L3 | Неоднозначный ИНН | Две и больше строк справочника или ноль строк — договор не связывается, КП само не уходит |
| L4 | Поиск при отправке | Сначала договор по `counterparty_id`. Если нет — действующий договор с тем же ИНН справочника по правилу L2, и эта найденная строка тут же получает `counterparty_id` |
| L5 | КП без ссылки | Если на КП пустой `counterparty_id`, а `customer_inn` совпадает ровно с одним активным клиентом и у этого клиента по L1–L4 есть договор — на КП пишется этот `counterparty_id`, имя на КП не затирается |
| L6 | Код 1С | Из справочника, в JSON `Контрагент.Код`. Менеджер его при этой отправке не вводит |
| L7 | GUID | В JSON `Контрагент.GUID` как есть. Пустой GUID отправку не останавливает |
| L8 | Бланк | `requisites_complete = false` не повод для «Нет действующего договора» |

## Objective

Менеджер отправляет в 1С КП контрагента, у которого договор уже лежит в `supply_contract`. Программа сама соединяет договор и строку справочника по однозначному ИНН и ставит номер договора в файл счёта. Повторный ввод кода 1С и номера не нужен.

### Сценарии

1. **Караван.** КП №15, контрагент id 1362, договор `0882/09/25`. «Отправить в 1С» больше не отвечает «Нет действующего договора поставки». В файле есть номер `0882/09/25`, имя, ИНН, КПП и код `00-00003032`.
2. **Один ИНН, несколько договоров.** У Секлюцкого три номера. В 1С уходит номер самой поздней даты. Две более ранние карточки остаются в списке без связи.
3. **Два контрагента на один ИНН.** Договор не связывается. Кнопка по-прежнему объясняет, что договор не найден. Менеджер выбирает строку справочника сам.
4. **Нет ИНН в справочнике.** ООО «Прогресс» не уходит в 1С, пока в справочнике не появится клиент с этим ИНН.
5. **Новая карточка без кода.** Раздел «Контрагенты» по-прежнему не спрашивает код 1С. Код берётся из уже существующей строки справочника в момент отправки.

## Code Style

Связь только при одном активном клиенте на ИНН. Чужой `counterparty_id` не переписывается.

```python
def link_contract_to_unique_client(contract: dict, client_id: int | None) -> int | None:
    if contract.get("counterparty_id") is not None:
        return int(contract["counterparty_id"])
    if client_id is None:
        return None
    return int(client_id)
```

## Testing Strategy

pytest, временная база. Живую `plita.db` тест не открывает.

- Договор с пустым `counterparty_id` и КП на единственного клиента с тем же ИНН: экспорт не бросает «Нет действующего договора», в документе номер этого договора и `Контрагент.Код` из справочника.
- Два договора одного ИНН: в документ попадает номер более поздней даты, ранний `counterparty_id` остаётся пустым.
- Две строки справочника на ИНН: экспорт по-прежнему «Нет действующего договора», ни одна строка договора не получает `counterparty_id`.
- Пустой `guid_1c` не приводит к отказу.
- Карточка с пустым бланком доходит до сборки документа.
- Уже связанный `0001/10/26` не перепривязывается.

## Boundaries

- Always: не создавать строки `counterparties`; не затирать имя на КП; не связывать договор при неоднозначном ИНН.
- Ask first: помечать старые договоры одного ИНН статусом «отмена не будем работать», чтобы связать все номера; требовать GUID контрагента.
- Never: подставлять выдуманный код или GUID; коммитить `plita.db`; ослаблять проверку GUID марок в составе заказа.
