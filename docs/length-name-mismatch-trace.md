# Где теряется точная длина: трассировка 59,8 → 59,9 и 61,2 → 61,1

Цепочка: **длина в метрах** → **имя плиты** (make_plate_name).  
5.98 м → "59,8", 5.99 м → "59,9".  
Расхождение появляется, когда в плане оказывается 5.99 вместо 5.98.

---

## 1. Источник длины: БД и заказы

| Файл | Функция/место | Что происходит |
|------|----------------|----------------|
| **core/kp_db.py** | `save_kp_to_db` | `length_m` из КП сохраняется как есть (точность 0.01 м) |
| **bot/handlers/production_execution.py** | ~стр. 202–230 | Загрузка из `kp_plates`: `length_m` идёт в `orders_2d` без изменений |

Длина из БД корректная (5.98 для 59,8-12-8п).

---

## 2. Оптимизация: где появляется другая длина

| Файл | Функция/место | Что происходит |
|------|----------------|----------------|
| **core/optimization.py** | `_optimize_2d_with_lengths` | `demand_2d` строится из `orders_2d`: ключи `(length, width, load_code)` |
| **core/optimization.py** | ~стр. 351–370 | `primary_options` создаются по ключам `demand_2d`: длина берётся из ключа |
| **core/optimization.py** | ~стр. 313 | `tolerance_length = 0.01` — 5.98 и 5.99 считаются разными |
| **core/optimization.py** | Solver (PuLP) | При конкурирующих спросах (5.98 vs 5.99) solver выбирает одну длину |
| **core/optimization.py** | ~стр. 910, 924, 934 | Выход: `opt['length']` — длина выбранной опции, не обязательно из заказа |

Проблема: solver может выбрать опцию с длиной 5.99, даже если в БД и заказах в основном 5.98. В результат уходит `length = 5.99`.

---

## 3. Формирование имени из длины

| Файл | Функция/место | Что происходит |
|------|----------------|----------------|
| **core/config_and_data.py** | `make_plate_name(length_m, width_m)` | `length_dm_raw = length_m * 10` → 5.98→"59,8", 5.99→"59,9" |
| **viz_modules/layout_sequence.py** | `plate_label(L, W)` | Вызывает `cfg.make_plate_name(L, W)` |
| **bot/handlers/production_completion.py** | ~стр. 411 | Fallback: `plate_name = cfg.make_plate_name(length, ...)` если lookup пустой |

Имя полностью определяется длиной. Если в плане `length = 5.99`, получается "59,9-12-8п".

---

## 4. Lookup: когда plate_name уже не совпадает с БД

| Файл | Функция/место | Что происходит |
|------|----------------|----------------|
| **bot/handlers/production_execution.py** | ~стр. 398–414 | `plate_lookup_exact` по ключу `(round(length, 2), width)` |
| **bot/handlers/production_completion.py** | `get_plate_info_smart` | Поиск по `(length, width)` в lookup |

Lookup строится из `orders_2d` по ключу `(length, width)`.  
Если в item пришла длина 5.99, ищется `(5.99, 1200)`. Для заказов с 5.98 ключ будет `(5.98, 1200)` — не совпадёт. Тогда `plate_name` берётся из fallback: `make_plate_name(5.99)` → "59,9".

---

## 5. Сводка: где именно «ломается» длина

| Этап | Файл | Причина расхождения |
|------|------|---------------------|
| 1. Solver | **core/optimization.py** | При конкурирующих 5.98/5.99 solver выбирает одну длину; в результат идёт `opt['length']` выбранной опции |
| 2. Имя | **core/config_and_data.py** | `make_plate_name(5.99)` → "59,9" вместо "59,8" |
| 3. Lookup | **production_execution.py**, **production_completion.py** | Ключ `(5.99, 1200)` не находит `(5.98, 1200)` → используется fallback по длине |

Корень: в **optimization.py** в выход попадает длина выбранной опции, а не длина из заказа/БД.

---

## 6. Возможные исправления

1. **В optimization.py** при формировании `plate_assignments` / `primary_cuts`:
   - использовать длину из `order_info` / `target_order_key`, если она есть;
   - или при конкурирующих длинах (в пределах 0.02 м) всегда брать длину из заказа с большим qty.

2. **В make_plate_name** (не рекомендуется):
   - вводить «эквиваленты» 5.98↔5.99 — это скрывает источник проблемы и может дать побочные эффекты.

3. **В production_completion** (уже есть):
   - эквиваленты 59,8↔59,9 в `find_one_row` (kp_db) — компенсируют расхождение при списании, но не устраняют причину в оптимизации.

---

## 7. Конкурирующие длины (из логов)

```
5.98 vs 5.99: demands 46 и 11
6.11 vs 6.12: demands 22 и 16
```

Solver может выбрать 5.99 или 6.11, даже если в БД в основном 5.98 и 6.12. В итоге в плане оказываются "59,9" и "61,1" вместо "59,8" и "61,2".
