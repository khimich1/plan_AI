# Список проблем: почему плиты 61,2-12-8п и 59,8-12-8п не списались

По логам `.cursor/debug.log` и коду выявлены следующие проблемы.

---

## Оставшиеся плиты в БД

| id | kp_id | plate_name | length | width | qty |
|----|-------|------------|--------|-------|-----|
| 153 | 3 | Плиты ПБ 61,2-12-8п | 6.12 | 1.2 | 3 |
| 232 | 4 | Плиты ПБ 59,8-12-8п | 5.98 | 1.2 | 4 |

---

## Проблема 1: Разные плиты 61,2 — путаница 61,2-5-8п и 61,2-12-8п

**Суть:** В плане есть плиты **61,2-5-8п** (ширина 500 мм) и **61,2-12-8п** (ширина 1200 мм). Это разные позиции.

**Из логов:**
- Списаны: `61,2-5-8п` (width 0.5) — КП #1 и #3
- Не списаны: `61,2-12-8п` (width 1.2) — КП #3

**Причина:** В БД КП #3 есть обе позиции. Вторичные резы `О Плиты ПБ 61,2-5-8п` (6.12 м × 500 мм) из родительской плиты 71-7-8п корректно списываются. Цельные плиты 61,2-12-8п (6.12 м × 1200 мм) в плане либо отсутствуют, либо привязаны к другим КП.

---

## Проблема 2: РЕСКЬЮ — 6.11 м привязывается к ключу 6.12, но kp_id берётся из заказа

**Из логов (H_rescue_norm):**
```
input_key: [6.11, 1200, 8] → chosen: [6.12, 1200, 8]
remaining: (6.11, 1200, 8)=22, (6.12, 1200, 8)=16
```

Плиты 6.11 м в треках считаются как 6.12 м. При сборе плит для списания `plate_to_kp_info` ищет по ключу (length, width). Для 6.11 м возвращается kp_id из первого заказа с 6.11 м, для 6.12 м — из заказа с 6.12 м. Если 61,2-12-8п есть только в КП #3, а заказы 6.11/6.12 м в основном из КП #1, #2, #4, то при списании `prefer_kp_id` будет 1, 2 или 4. В этих КП 61,2-12-8п нет, и списание идёт через шаги 5–7 `find_one_row` по всем КП. Теоретически плита должна находиться, но порядок обработки по `kp_id` может приводить к тому, что спрос закрывается за счёт других КП, а КП #3 не доходит.

---

## Проблема 3: 59,8-12-8п — плита «не в этом дне»

**Из логов (H7b):**
```
"Плита 59,8-12-8п не в этом дне; в плане она в днях [2, 8, 11]"
day_confirmed: 1, 2, 3, 4, 5, 6, 7
```

Подсказка показывается при подтверждении дней 1–7, хотя 59,8-12-8п есть в днях 2, 8, 11. Возможные причины:
- Неверная проверка «плита в этом дне» (сравнение по дате/дню)
- Пользователь подтвердил не те дни, где реально лежит 59,8-12-8п

---

## Проблема 4: Lookup даёт kp_id из «первого» заказа

**Из логов (H_LOST_lookup):**
```
item_plate_name: "59,9-12-8п", item_kp_id: 1
plate_name_used: "59,8-12-8п", kp_id_used: 1 или 4
```

Для 59,9-12-8п lookup возвращает kp_id 1 или 4. Плита 59,8-12-8п в БД есть в КП #1 и #4. При `prefer_kp_id=1` списание идёт сначала из КП #1. Если там достаточно плит 59,8-12-8п, КП #4 не трогается, и 4 шт. в КП #4 остаются.

---

## Проблема 5: Конкурирующие длины 5.98 и 5.99, 6.11 и 6.12

**Из логов (H_opt_competing):**
```
5.98 vs 5.99: demands 46 и 11
6.11 vs 6.12: demands 22 и 16
```

Оптимизатор выдаёт 5.99 м и 6.11 м, в БД — 5.98 м и 6.12 м. Эквиваленты 59,8↔59,9 и 61,1↔61,2 в `find_one_row` должны это учитывать, но привязка к КП через lookup может оставлять часть плит не списанной.

---

## Проблема 6: В КП #3 для 61,2-12-8п — только «в производстве»

**Из логов (H5, rows_in_db_for_kp):**
```
kp_id: 3, rows_in_db: 61,2-5-8п (width 0.5), 63,7-5,3-8п, ...
```

В выборке по КП #3 для дня видны 61,2-5-8п, 63,7-5,3-8п и др. Плиты 61,2-12-8п (width 1.2) в этих логах не фигурируют. Возможно, при сборе `completed_plates` для дня плиты 61,2-12-8п не попадают в список (нет в треках этого дня или не проходят фильтр).

---

## Рекомендации по исправлению

1. **Проверить сбор плит по дням**  
   Убедиться, что 61,2-12-8п и 59,8-12-8п действительно попадают в `completed_plates` для дней 2, 8, 11.

2. **Сбалансировать списание по КП**  
   При равном спросе не списывать только из «первого» КП. Варианты:
   - распределять списание пропорционально остаткам по КП;
   - при `find_one_row` при равных кандидатах выбирать КП с большим остатком.

3. **Расширить эквиваленты в find_one_row**  
   Убедиться, что 59,8↔59,9 и 61,1↔61,2 обрабатываются во всех шагах поиска, в т.ч. при поиске по длине/ширине.

4. **Логика «плита не в этом дне»**  
   Перепроверить условие H7b: при каких именно `day_confirmed` и `days_with_plate` показывается подсказка и не блокирует ли это списание.

5. **Ручное списание оставшихся плит**  
   Для текущих 7 шт. (3 + 4) можно добавить админ-команду принудительного списания по id записи в `kp_plates` или по (kp_id, plate_name, qty).
